Standard Library

kv — a key-value store, served and sharded

Module kv (lib/kv.lora) exports 101 declarations. Import with use kv;.

Overview

kv is a sharded, concurrent, embeddable and networkable key-value store supporting scalars (text, bytes, integer, float, json), deques (list), sets (set), per-key TTL expiration, LRU/random/refuse memory eviction, append-only durable logging with compaction and disk residency, a RESP-compatible TCP/socket server (serve) and client (connect, call), and a consistent-hashing multi-node cluster.

A kv::store is thread-safe and sharded across a power-of-two number of shards (shards = 0 defaults to 64 per processor) using SipHash-2-4. Calling kv::close(&s) flushes the log (if configured) and frees resources.

Valid Usage & Examples

In-memory scalars, atomic counters, lists, and sets

Open an in-memory sharded store, store typed values, increment counters, and manipulate deques and sets.

lora Allowed 
use kv;
use strings;

export fn main() void = {
	let s = kv::open(kv::options { shards = 4, ... })!;
	defer kv::close(&s)!;

	kv::set_text(&s, "greeting", "hello")!;
	kv::append_text(&s, "greeting", " world")!;
	assert(kv::incr(&s, "hits", 1)! == 1);
	assert(kv::incr(&s, "hits", 4)! == 5);

	kv::push_back(&s, "queue", strings::to_bytes("task-1"))!;
	kv::push_front(&s, "queue", strings::to_bytes("task-0"))!;
	let item: ^[]u8 = [];
	defer free(item);
	assert(kv::pop_front(&s, "queue", &item)!);
	assert(strings::from_bytes(item[..]) == "task-0");

	assert(kv::set_add(&s, "tags", strings::to_bytes("fast"))!);
	assert(kv::set_has(&s, "tags", strings::to_bytes("fast"))!);
}

Durable disk log with compaction and TTL expiration

Persist writes to a directory with residency::disk, set TTLs with set_options, and compact the append-only log.

lora Allowed 
use kv;

export fn main() void = {
	let opts = kv::options {
		dir = "/tmp/lora_kv_demo",
		residency = kv::residency::disk,
		sync = kv::sync_policy::every_second,
		max_memory = 16 << 20,
		eviction = kv::eviction::lru,
		...
	};
	let s = kv::open(opts)!;
	kv::set_text(&s, "session:1", "alice", kv::set_options { ttl_ms = 60000, ... })!;
	kv::sync(&s)!;
	kv::compact(&s)!;
	kv::close(&s)!;
}

RESP TCP server, remote client, and consistent-hash cluster

Expose a kv::store over TCP using kv::serve and query it via kv::connect / kv::remote_set / kv::remote_get.

lora Allowed 
use kv;
use net;
use strings;
use thread;

export fn main() void = {
	let s = kv::open(kv::options { ... })!;
	defer kv::close(&s)!;

	let l = net::listen_at("127.0.0.1:0")!;
	let addr = net::listener_addr(&l);
	let stop = thread::atomic { ... };

	// In production, run kv::serve(&s, &l, &stop, kv::server_options { ... }) in a coroutine/thread
	let c = kv::connect(addr, kv::client_options { timeout_ms = 2000, ... })!;
	defer kv::stop_serving(&stop);

	kv::remote_set(&c, strings::to_bytes("k"), strings::to_bytes("v"))!;
	let out: ^[]u8 = [];
	defer free(out);
	assert(kv::remote_get(&c, strings::to_bytes("k"), &out)!);
	assert(strings::from_bytes(out[..]) == "v");
}

Disallowed Forms & Diagnostics

Do not apply list/set/numeric operations to a key of a different kind

Every key has a runtime kv::kind. Calling a list operation on a text key fails with kv::wrong_kind, and kv::incr on non-numeric text fails with kv::not_a_number.

kv::wrong_kind: the key holds a value of another kind
lora Rejected 
use kv;
use strings;

export fn main() void = {
	let s = kv::open(kv::options { ... })!;
	defer kv::close(&s)!;
	kv::set_text(&s, "k", "hello")!;
	kv::push_back(&s, "k", strings::to_bytes("item"))!; // error: kv::wrong_kind (want list, got text)
}

	kv::remove(&s, "k")!; // ok: removes text key before creating list at "k"

Constraints & Limits

Max server request size
64 MiB (`max_request = 64 << 20`), 65536 args (`max_args`)
Requests exceeding `server_options` limits are refused and the client connection is closed.
Consistent hash ring
160 points/node (`POINTS`), up to 8 replicas (`MAX_REPLICAS`)
Cluster writes are uncoordinated across reachable replicas; reads hit the first reachable replica.
Entry memory accounting
96 B per entry (`ENTRY_COST`), 32 B per item (`ITEM_COST`)
Used to enforce `options.max_memory` and trigger `eviction` (`refuse`, `lru`, or `random`).
Error text buffer
200 bytes (`bad_log`, `refused`)
Fixed inline message buffer so errors outlive the store or request.

Module Guide & Examples

A key-value store: values found by their keys, kept in memory for repeated access at low latency, and on disk if wanted.

A value is text, bytes, a 64-bit integer or float, JSON, a list of byte strings, or a set of them. Keys are byte strings. A key may expire after a time, and a store with a memory limit evicts what was used least recently (or at random) to stay under it.

The store is split into shards by a hash of the key, each with its own lock, so threads and coroutines on many processors seldom wait for one another. A store may keep a log on disk: every change is appended to it, and a store opened on it again is as it was. With residency::disk, the values live only in the log and the keys in memory, for more data than memory holds.

serve answers clients over the network with RESP, the protocol Redis clients speak; a client talks to one server, and a cluster shards keys across many by consistent hashing, keeping copies on more than one if asked.

let s = kv::open(kv::options { ... })!; kv::set_text(&s, "greeting", "hello", kv::set_options { ttl_ms = 60000, ... })!; let out: ^[]u8 = []; kv::get(&s, "greeting", &out)!; // found: out holds "hello" kv::push_back(&s, "queue", strings::to_bytes("job 1"))!; kv::set_add(&s, "tags", strings::to_bytes("fast"))!; kv::close(&s)!;

Values found by their keys, in memory for repeated access at low latency, and on disk if wanted: text, bytes, 64-bit integers and floats, JSON, lists of byte strings and sets of them. The store is split into shards by a keyed hash of the key, each with its own lock, so any number of threads and coroutines use one store at once through a *const store.

The store:

  • A shard's keys are in a table of slots holding part of each key's hash and its place in a slab of entries, so a probe seldom reads an entry it does not want, and removing shifts slots back rather than leaving marks.
  • An expired key goes when it is next used, and sweep takes those that are not. With max_memory, a write that needs room evicts the least recently used of five keys sampled (or one at random), or with eviction::refuse is full.
  • A list is two stacks, so both ends push and pop in constant time. A set has an index of its members, as the table has of keys.
  • get fills the buffer it is given, keeping its room: one buffer used for each get allocates only when a value is longer than before.

The log, with dir:

  • Each shard appends every change to its own log, kv-NN.log, and open replays them: a record cut short or damaged, and all after it, are cut off. Each record has its length and a CRC-32. kv.meta keeps the key of the hash and the number of shards, so a key's records stay in one log.
  • sync_policy says when the log is made durable; compact rewrites each log as its shard is now, to a new file renamed over the old.
  • A log is locked while a store has it open: a second store on it is a bad_log. What could not be written is a bad_log too, and no more is written until the store is opened again.
  • With residency::disk, text, bytes and JSON are read from the log when asked for, so a store may hold more than memory does.

Serving and clients:

  • serve gives each connection a coroutine. Requests are RESP arrays of bulk strings or inline commands, pipelined as the client likes, and limited by server_options; one that breaks the protocol or the limits is told why, and its connection closed. The commands are those of strings, numbers, expiry, lists, sets and whole JSON documents (JSON.SET and JSON.GET at $), and KEYS, DBSIZE, FLUSHDB, INFO, SAVE (sync) and BGREWRITEAOF (compact).
  • A client, and a cluster, belong to one coroutine or thread at a time: each makes its own. call sends any command and reads any reply.
  • A cluster puts 160 points for each server on a ring of SipHash-2-4 hashes under a fixed key, so every client places keys alike, and adding a server moves about a fair share of them. A key's value is written to each of its replicas that can be reached and read from the first that can; a server that fails is left alone for retry_ms. Writes are not coordinated: a replica that was down misses what was written meanwhile.

On an M-series Mac, one thread: a get takes about 270 ns with a million keys and 210 ns with ten thousand; an insert about 650 ns, and replacing a value 350 ns. Eight threads on one store, nine gets to a set, do about 11 million operations a second.
