Standard Library

process — starting programs

Module process (lib/process.lora) exports 38 declarations. Import with use process;.

Overview

process spawns and manages child OS processes with full control over arguments, environment, working directory, stdio redirection, extra file descriptors, process groups/sessions, credentials, and pseudo-terminals (PTY).

process::child implements rt::drop and automatically terminates and reaps an unwaited child on scope exit (unless release was called). process::pipe implements io::reader, io::writer, io::closer, and rt::drop. process::output pumps stdin, stdout, and stderr concurrently to avoid pipe deadlocks and supports byte limits and timeouts.

Valid Usage & Examples

Capturing stdout and stderr with process::output

Provide opts.input, a byte cap (limit), and a timeout (within_ms) to avoid deadlocks and runaway children.

lora Allowed 
use fmt;
use process;
use strings;

export fn main() void = {
	let cmd = process::command {
		program = "cat",
		...
	};
	let res = process::output(&cmd, process::options {
		input = strings::to_bytes("ping\n"),
		limit = 4096,
		within_ms = 2000,
	})!;
	process::check(&res.status)!;
	fmt::print(strings::from_bytes(res.stdout))!;
}

Interactive streaming with process::start and child pipes

Start a child, write to stdin, close it to signal EOF, read stdout, and wait for exit status.

lora Allowed 
use fmt;
use io;
use process;
use strings;

export fn main() void = {
	let cmd = process::command {
		program = "tr",
		args = ["a-z", "A-Z"],
		stdin = .pipe,
		stdout = .pipe,
		...
	};
	let c = process::start(&cmd)!;
	io::write_str(process::stdin(&c), "hello")!;
	process::close(process::stdin(&c))!;

	let out = io::read_all(process::stdout(&c), 1024)!;
	defer free(out);
	let st = process::wait(&c)!;
	fmt::printfn("code={} out={}", st.code, strings::from_bytes(out))!;
}

Running a command and checking exit status

Use process::run for commands whose stdio is inherited or discarded.

lora Allowed 
use fmt;
use process;

export fn main() void = {
	let cmd = process::command {
		program = "true",
		stdout = .discard,
		...
	};
	let st = process::run(&cmd)!;
	fmt::printfn("ok={}", process::success(&st))!;
}

Disallowed Forms & Diagnostics

Assuming process::output succeeds when exit code is non-zero

process::output returns result even for non-zero exit codes; call process::check(&res.status) to turn non-zero exit into process::failed.

Logic: non-zero exit code is reported in result.status, not as an error from output()
lora Rejected 
use process;

export fn bad() void = {
	let cmd = process::command { program = "false", ... };
	let _ = process::output(&cmd)!; // error: succeeds even on non-zero exit code
	// succeeds without noticing exit code 1!
}
lora Allowed 
use process;

export fn good() (void | process::start_failed | process::error | process::not_found | process::failed | io::failure | nomem) = {
	let cmd = process::command { program = "false", ... };
	let res = process::output(&cmd)?;
	defer free(res.stdout);
	defer free(res.stderr);
	process::check(&res.status)?; // ok: converts non-zero exit status into process::failed
}

Constraints & Limits

Drop kill grace period
1000 ms
`KILL_WAIT_MS`: dropping an unwaited `child` kills it and waits up to 1000 ms.
output() caps
limit / within_ms
`limit > 0` caps each stream (`io::too_large`); `within_ms > 0` caps runtime (`io::timed_out`).
PTY ownership
1 session per PTY
A `pty` becomes the controlling terminal of a new session; controller output must be drained.

Module Guide & Examples

Programs: starting them, talking to them through pipes, and waiting for them to end.

let out = process::output(&process::command { program = "git", args = ["rev-parse", "HEAD"], })!; assert(process::success(&out.status));

let c = process::start(&process::command { program = "sort", stdin = process::stdio::pipe, stdout = process::stdio::pipe, })!; io::write_all(process::stdin(&c), strings::to_bytes("b\na\n"))!; process::close(process::stdin(&c))!; // sort reads to the end let sorted = io::read_all(process::stdout(&c), 1 << 20)!; let st = process::wait(&c)!;

A program is looked up in PATH unless its name has a /. It gets only the descriptors it is given: its standard input, output and error, each the program's own, nothing (discard), a pipe, or a file, and files, its descriptors from 3 on. It starts with the signal mask empty and every signal at its default but those this program ignores.

A child is an owner. Dropping one that is still running kills it and waits for it, so no child is left behind unseen, and closes its pipes; release gives one up to run on, reaped when it ends. Waiting, reading and writing wait the way their caller runs: in a coroutine the others run meanwhile, and a cancelled scope ends a wait for a child by killing it.

use process;
use strings;

export fn main() void = {
	let out = process::output(&process::command {
		program = "sh",
		args = ["-c", "echo hello; echo oops >&2; exit 3"],
	})!;
	assert(out.status.code == 3);
	assert(strings::from_bytes(out.stdout) == "hello\n");
	assert(strings::from_bytes(out.stderr) == "oops\n");
}

A program gets only the descriptors it is given: its three standard streams and files. Every other descriptor this program holds stays here. It starts with an empty signal mask, and with every signal at its default except the ones this program ignores, which it keeps ignoring.

look_path looks only in PATH directories written from the root. An empty or relative entry such as . is skipped, so a program is never found in the current directory by chance. To run one from there, name it as ./name. With dir set, a relative path such as ./tool refers to a file in dir, because the program starts once it is there.

output feeds input and reads standard output and error together, so a program that writes a lot while it reads never stalls on a full pipe. It also stops the program if it goes past limit (io::too_large) or within_ms (io::timed_out). io::write_all to the stdin pipe of a program that has ended fails with EPIPE; this program is not stopped by a signal.

output stops collecting once the program has ended and what it wrote has been read. If it started something in the background that keeps its streams open, output doesn't wait for that, and anything written to them later is not kept.

A child owns its process. Dropping one that is still running kills it and reaps it, so no zombie is left behind. Its pipes close with it. release lets it run on, and it is reaped when it ends. After a child has been waited for, send and kill fail with ESRCH, since its id may belong to another process by then.

Waiting suspends a coroutine on kqueue, so the other coroutines keep running. In a scope that is cancelled, the wait kills the child, reaps it, and fails with ECANCELED.

A child killed by being dropped normally ends at once. The system can hold one, though: a program whose terminal has output nobody reads can't end until it is read. The drop waits a second for it, then leaves it to be reaped whenever it does end, so a drop never hangs.

credential runs the program as another user and group. Its supplementary groups are groups, or none, unless keep_groups keeps this program's. Running as anyone but this program's own user, and setting the groups, take a superuser's privileges; otherwise the start fails with EPERM. The user and groups are set before the program starts, after its session and group, and before it moves to dir, so dir is entered as that user.

terminal gives a program a controlling terminal. It leads a session of its own, its group is the terminal's foreground, and /dev/tty is that terminal. open_terminal makes a new pseudo-terminal. The program reads and writes terminal (give it as its standard streams too), and this program reads what it writes, and types to it, through controller. Two rules come with a terminal:

  • One session each. When the program given it ends, the system takes the terminal back from everything that has it open, so each program needs a terminal of its own.
  • Its output must be read. A program can't end until what it wrote to the terminal has been read from controller.

foreground puts a program's group in front of this program's own terminal, as a shell does for a job. It leads a group of its own, unless group names one to join. Once it has ended or stopped, set_foreground(t, os::group_id()) takes the terminal back. A terminal can't go with new_group, group or foreground, and foreground can't go with new_session: these fail with EINVAL.

lora 
use io;
use process;
use strings;

export fn main() void = {
	let t = process::open_terminal()!;
	let c = process::start(&process::command {
		program = "sh",
		args = ["-c", "test -t 0 && echo on a terminal > /dev/tty"],
		stdin = io::file { fd = t.terminal.fd },
		terminal = io::file { fd = t.terminal.fd },
	})!;
	let buf: [64]u8 = [0...];
	let n = io::file_read(&io::file { fd = t.controller.fd }, buf[..])!;
	assert(strings::from_bytes(buf[..n]) == "on a terminal\r\n");
	assert(process::success(&process::wait(&c)!));
}

A program to start.
