allocator — where memory comes from

Module allocator (lib/allocator.lora) exports 55 declarations. Import with use allocator;.

Overview

allocator defines a uniform allocator interface (alloc_bytes, resize_bytes, realloc_bytes, free_bytes), typed generic helpers (create, destroy, make, resize_slice, grow, free_slice, copy_str, free_str), and a suite of composable concrete allocators plus a global runtime hook (set_global / reset_global).

Valid Usage & Examples

Fixed buffer with typed helpers and mark/rewind

fixed_buffer_owned allocates an owned buffer that is freed automatically on drop, and supports fixed_buffer_mark / fixed_buffer_rewind for nested scopes.

lora Allowed 
use allocator;

export fn main() void = {
	let fb = allocator::fixed_buffer_owned(4096)!;
	let a: allocator::allocator = &fb;

	let xs = allocator::make::[u64](a, 8)!;
	xs[0] = 42;
	assert(xs[0] == 42);
	let m = allocator::fixed_buffer_mark(&fb);
	let tmp = allocator::copy_str(a, "scratch")!;
	assert(tmp == "scratch");
	allocator::fixed_buffer_rewind(&fb, m);

	allocator::fixed_buffer_reset(&fb);
}

Stack fallback and slab allocator for fixed-size objects

stack_fallback_owned handles small requests in a local buffer and transparently migrates larger ones to system_allocator(). slab_new recycles fixed-size slots.

lora Allowed 
use allocator;

type entity = struct { id: u64, x: f64, y: f64 }

export fn main() void = {
	let sf = allocator::stack_fallback_owned(256, allocator::system_allocator())!;
	let sb = allocator::slab_new(&sf, size_of(entity), align(entity), 16);
	defer allocator::slab_finish(&sb);

	let a: allocator::allocator = &sb;
	let e = allocator::create(a, entity { id = 1, x = 1.0, y = 2.0 })!;
	assert(allocator::slab_live(&sb) == 1 && e.id == 1);
	unsafe { allocator::destroy(a, e); }
	assert(allocator::slab_live(&sb) == 0);
}

Concurrent allocation with atomic_fixed_buffer and thread_safe

Use atomic_fixed_buffer_owned for lock-free bump allocation across @scope/@go workers, or thread_safe_new to guard a free_list.

lora Allowed 
use allocator;
use coro;

export fn main() void = {
	let af = allocator::atomic_fixed_buffer_owned(65536)!;
	let p_af = &af;

	@scope(workers = 4) {
		for (let w = 0z; w < 4; w += 1) {
			@go {
				let a: allocator::allocator = p_af;
				let p = allocator::create(a, @u64(w))!;
				assert(*p == @u64(w));
			};
		}
	}!;
	unsafe { allocator::atomic_fixed_buffer_reset(&af); }
}

Routing built-in alloc and append through set_global

set_global redirects built-in alloc, free, and append through a custom *allocator until reset_global is called.

lora Allowed 
use allocator;

export fn main() void = {
	let fl = allocator::free_list_owned(16384)!;
	let ts = unsafe { allocator::thread_safe_new(&fl) };
	let a: allocator::allocator = &ts;

	unsafe {
		allocator::set_global(&a);
		{
			let xs: ^[]u64 = alloc([10u64, 20]...)!;
			append(xs, 30)!;
			assert(len(xs) == 3 && allocator::free_list_used(&fl) > 0);
		}
		assert(allocator::free_list_used(&fl) == 0);
		allocator::reset_global();
	}
}

Disallowed Forms & Diagnostics

Allocating owning types with allocator::create or make

Allocators operate on raw bytes and do not invoke element destructors on reset or free, so create, make, grow, destroy, resize_slice, and free_slice reject @owns(T) at compile time.

Compile error: An allocator frees raw bytes and does not run drops, so T cannot own memory
lora Rejected 
use allocator;
use strings;

export fn main() void = {
	let a = allocator::system_allocator();
	let s = strings::concat("hi", "!")!;
	let p = allocator::create(a, s)!; // error: allocator::create rejects @owns(T)
}

Use allocator::copy_str (paired with allocator::free_str) to allocate string bytes in an allocator.

lora Allowed 
use allocator;

export fn main() void = {
	let a = allocator::system_allocator();
	let s = allocator::copy_str(a, "hi!")!; // ok: allocates borrowed str bytes in allocator
	assert(s == "hi!");
	unsafe { allocator::free_str(a, s); }
}

Module Guide & Examples

Allocators behind one interface, for code that is given where its memory comes from: the system heap, a region, a fixed buffer (and a lock-free one), a fixed buffer that falls back to another allocator, a slab of same-size slots, a free list with size classes, a ring for memory freed in the order it was taken, a lock around another allocator, and a way to route alloc, free and append through one.

let buf: [4096]u8 = [0...]; let fb = allocator::fixed_buffer_new(buf[..]); let a: allocator::allocator = &fb; let xs = allocator::make::[u32](a, 64)!; // views a, so fb and buf allocator::fixed_buffer_reset(&fb); // xs ends here

What create, make and copy_str give views the allocator: it can't outlive the allocator, nor the buffer an allocator hands out. Resetting or rewinding an allocator ends what it gave. Giving memory back one piece at a time (destroy, free_slice, free_str, grow and the methods that take a pointer) is unsafe: the caller makes sure the memory came from that allocator, at that size, and that nothing uses it after. So is making a free list or a ring, which keep their bookkeeping in the buffer given.

For code that is given where its memory comes from: one interface, allocator::allocator, and allocators behind it. These are the system heap; a region (from_region); a fixed buffer, which hands out its memory in order, and a lock-free one for threads; a fixed buffer that falls back to another allocator when it is full (stack_fallback); a slab of same-size slots; a free list with size classes; a ring, for memory given back in the order it was taken; a lock around another allocator (thread_safe); and set_global, which routes alloc, free and append through one. The allocators guide says when to use each, with examples.

lora 
use allocator;

export fn main() void = {
	let fb = allocator::fixed_buffer_owned(4096)!;  // 4096 bytes of its own
	let a: allocator::allocator = &fb;
	let xs = allocator::make::[u32](a, 64)!;        // views a, so fb
	xs[63] = 7;
	let name = allocator::copy_str(a, "ada")!;
	assert(name == "ada" && xs[63] == 7);
	assert(allocator::fixed_buffer_used(&fb) >= 64 * 4 + 3);
	allocator::fixed_buffer_reset(&fb);              // xs and name end here
	assert(allocator::fixed_buffer_used(&fb) == 0);
}

What create, make and copy_str give is a view of the allocator, checked as any view is: it can't outlive the allocator, nor the buffer the allocator hands out (L0608). Resetting or rewinding an allocator ends what it gave (L0609). A fixed buffer's mark and rewind give back everything taken since the mark, as a region's do.

Buffers. The fixed buffer, atomic fixed buffer, stack fallback, free list and ring each take their memory one of two ways. X_owned(n) gives them n zeroed bytes of their own, freed when they are dropped: nothing else can write those bytes, so it is safe. X_new(buf) lends them a buffer you have, as an array on the stack, so that nothing is allocated: it is unsafe, as what they hand out lives in buf, and nothing else may write buf while any of it is in use. These allocators are moved, never copied: two copies would hand out the same bytes.

Sealed. The allocator types are @sealed: only this module reads and writes their fields. Each one's zero value, T { ... }, holds nothing, and anything asked of it fails with nomem.

Unsafe. Giving memory back one piece at a time is unsafe: destroy, free_slice, free_str, grow and resize_slice, slab_free, and the interface's resize_bytes, realloc_bytes and free_bytes, which are @unsafe methods. The caller makes sure the memory came from that allocator, at that size and alignment, and that nothing uses it after (L0800). For memory freed all at once, by a reset, nothing is unsafe.

Threads. system and atomic_fixed_buffer guard themselves, and thread_safe puts a lock around another allocator: they are @synchronised, so @go children may share a pointer to one, and make the interface in the child. An interface value itself can't be shared: what it points to may be of any type. thread_safe_new is unsafe, as every use of the allocator it wraps must go through its lock, and atomic_fixed_buffer_reset is unsafe, as the compiler can't see what other threads still hold.

A fixed buffer takes memory from its buffer in order, each piece aligned as asked, and fails with nomem when the buffer is used up: it never asks the system for more. Giving back the last piece taken, or growing it, works where it is; anything else waits for rewind or reset. For one piece of work, scratch::with needs no buffer and never runs out; for typed values that never move, expanse::reserve.

Which to use. The default alloc and growing ^[]T for most things; scratch for what a piece of work needs only while it runs; expanse for many values that live and die together; pool for values that refer to each other. Use an allocator from this module when code must be told where its memory comes from: a fixed buffer with a hard limit, a slab for many values of one size, or a ring for a queue of messages.
