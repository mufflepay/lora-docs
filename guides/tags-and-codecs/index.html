Structure Tags & Codecs

Compile-time struct field tags (@tag, @shorthand, @rule), compile-time validation rules across json, csv, xml, cbor, toml, yaml, and sql, and generic config::load traversal (docs/tags.md).

Status: built, except what is listed under "Not built yet" below. This is the design and the rules behind it; the language reference has the short version, and its examples are checked against the compiler.

A tag is a typed, compile-time value attached to a struct field, a type or a function. Libraries define tags as ordinary structs and read them in generics, which expand at compile time into direct field code. There is no run-time reflection, and an untagged type costs nothing.

lora 
use config;
use json;

type server_config = struct {
	@config("port", env = "PORT", default = 8080) port: int,
	@config("host", env = "HOST", default = "127.0.0.1") host: str,
	@config("db_url", env = "DB_URL") db_url: str,
}

type user = struct {
	@json("id") id: int,
	@json("name", omit_empty) name: str,
	@json(skip) pw_hash: str,
}

export fn main() (void | config::error | nomem) = {
	let cfg = config::load::[server_config]()?;
	let u = user { id = 1, name = "ada", pw_hash = "x" }
	let text = json::marshal(&u)?;
}

1. Decisions

DecisionRule
The mechanismOne: @tag(value), where value is a constant of a library's struct type
Shorthand@json("id") is exactly @tag(json::field { name = "id" }), with no behaviour of its own
Who defines shorthandThe library, on its tag type; the compiler knows no tag names
The long formAlways valid; never replaced by shorthand
Unknown tagA compile error, never ignored
ConsumptionCompile-time generation in generics; tags do not reach @typeinfo

2. Tag syntax

text 
tags      = { tag } ;
tag       = "@tag" "(" constant ")"
          | "@" [ module "::" ] name [ "(" arguments ")" ] ;
arguments = argument { "," argument } [ "," ] ;
argument  = constant                 (* positional *)
          | name "=" constant        (* named *)
          | name ;                   (* a bool field, set to true *)

Tags go directly before what they describe:

PositionExample
A struct or union field@json("id") id: int,
A type declaration (not built yet)@db_table("users") type user = struct { ... };
A function declaration (not built yet)@route("GET", "/users/{id}") fn get_user(...) ...

Several tags stack, on one line or several. export comes first, as with other attributes: export @route(...) fn f() .... Tags are not allowed on locals, parameters or expressions.

Tags are read in their own namespace: a name in tag position is never looked up as a macro, so @json cannot collide with macro json. The compiler's attributes (@symbol, @init, @unsafe, @synchronised, @threadlocal, ...) are reserved, and cannot be tag names.

Defining a tag

A tag type is an exported struct whose fields all have defaults, or are given at every use. @shorthand(name) registers the shorthand on it:

lora 
// in lib/json.lora
export @shorthand(json) type field = struct {
	name: str = "",
	omit_empty: bool = false,
	omit_zero: bool = false,
	skip: bool = false,
	string: bool = false,
	ignore_case: bool = false,
	strict_case: bool = false,
	format: str = "",
	inline: bool = false,
	unknown: bool = false,
}

There is deliberately no expansion language: shorthand always builds the tag type it is declared on. It stays exact because arguments have one meaning each:

  1. Positional arguments set the type's fields in order.
  2. name = value sets that field.
  3. A bare name that is a field of the tag sets it to true, so it must be a bool field. Any other bare name is a positional constant.
  4. The result is the struct literal, so every field check of a literal applies: no such field, wrong type, a field set twice.

So @json("name", omit_empty) is @tag(json::field { name = "name", omit_empty = true }), and @json(skip) is @tag(json::field { skip = true }). Bare-word and keyword forms are the same field: there is no second shorthand style.

@config(default = 8080) needs a field of a union type, default: (void | int | bool | str) = void, in which void means no default. Being a union, it converts as any union does.

Resolving a name

@json is looked up among the shorthands of the modules this file imports.

  • Found in one: that tag.
  • Found in two or more: an error at the use, listing them. Write @json::field(...), or the long form. There is no silent shadowing.
  • Found in none: an unknown tag (L0900), with a near match as a suggestion (@josn → @json), or use json; if a core library has that shorthand.

Tag values

  • A value must be a compile-time constant, evaluated as def is. Calling functions is allowed under the same rules as @comptime.
  • A value may not hold pointers to memory made at compile time, or owners.
  • @tag(x) requires x to be a value of a declared struct type. A tag of a plain int or str is an error: a typed value is what makes tags checkable.

3. Tags and types

Identity. Struct types are shared by shape, so two structs alike except for their tags would otherwise become one, and lose them. Tags are therefore part of a struct's identity: its type hash and equality include each field's tags. Declared types are nominal already, so this changes nothing a program sees, except that @T(x) between two structs that differ only in tags stays allowed, as they have the same layout.

Typedefs. Tags are written into .td files, in long form with module-qualified types, so importers see them on fields, types and functions. Template source carries them too, so generic types may be tagged.

Run time. Tags emit nothing. @typeinfo does not include them, and a program that never calls a generator carries none of their strings.

4. Compile-time generation

Generics share one body for every instantiation, and a body is checked for each. Walking fields needs more, so there is a compile-time loop and branch. They are for the body of a generic function, and run at each instantiation.

ConstructMeaning
@fields(T)The fields of struct T, in order; any other T is an error
@for (f .. @fields(T)) { ... }Expands the body once per field, as a block of its own
f.nameThe field's name, a constant str
f.typeThe field's type, usable wherever a type is
x.@(f)Field f of x, the same as writing x.name
@tag_of(f, tagtype)The tag of that type on f, a constant; an error if there is none
@has_tag(f, tagtype)Whether f has one, a constant bool
@tag_of(T, tagtype), @has_tag(T, tagtype)The same for a type's own tags, struct @table("x") { ... }
@same(A, B)Whether two types are the same, a constant bool
@owns(T)Whether a value of T owns memory, and so must be dropped, a constant bool
@cycles(T)Whether a value of T could own itself through rc or arc, a constant bool
@has_zero(T)Whether zero is a value of T (no non-null pointer, enum or pattern without zero, tagged union), a constant bool
@kind(T)T's rt::type_kind, a constant, to tell structs and slices apart
@sealed(T)Whether T is another module's @sealed type, whose fields only that module reads, a constant bool: a generator treats it as a whole
@if (constant) { ... } else { ... }Expands one branch; the other is not checked
@error("message")A compile error, when this code is expanded

An ordinary for or if over these would check every branch for every field, so read_int would be rejected on a str field. That is why @if drops the branch not taken, and it is the one rule here that plain code does not have. for and if stay what they are.

How config::load[T] walks the fields

lora 
// in lib/config.lora
export fn load[T]() (T | error | nomem) = {
	let out: T = @undefined;
	@for (f .. @fields(T)) {
		@if (!@has_tag(f, field)) {
			@error("this field has no @config tag");
		} else @if (@same(f.type, int)) {
			out.@(f) = read_int(@tag_of(f, field))?;
		} else @if (@same(f.type, bool)) {
			out.@(f) = read_bool(@tag_of(f, field))?;
		} else @if (@same(f.type, str)) {
			out.@(f) = read_str(@tag_of(f, field))?;
		} else {
			@error("@config takes int, bool or str");
		}
	}
	return out;
}

load[server_config] then is, as if written by hand:

lora 
fn load_server_config() (server_config | config::error | nomem) = {
	let out: server_config = @undefined;
	out.port = read_int(config::field {
		key = "port", env = "PORT", default = 8080,
	})?;
	out.host = read_str(config::field {
		key = "host", env = "HOST", default = "127.0.0.1",
	})?;
	out.db_url = read_str(config::field {
		key = "db_url", env = "DB_URL",
	})?;
	return out;
}

The steps, at each instantiation:

  1. T must be a struct. @fields gives its named fields: embedded and _ fields are left out.
  2. The compiler substitutes each field for f and expands the body, in declaration order, then checks the result as ordinary code. Safety checks all apply: L0104, leaks, effects.
  3. A tag used in @tag_of becomes a constant in the code, so its strings are in the program only where it is really used.
  4. An error in the expansion names the field and the instantiation: in load[server_config], field db_url with a note at the field.

@undefined is zero, so a field left unset, as with skip, is zero.

Owners. In the first version, a generator may not set a field that holds an owner (^T, ^str, ^[]T): out.@(f) = ... on one is an error. Writing to @undefined memory, and dropping what was set when a later ? fails, need rules of their own. Fields are plain data or borrow, as below.

5. Checks

What the compiler checks

These hold for every tag, and need nothing from the library.

CodeCheck
L0900Unknown tag: no shorthand of that name, with a suggestion
L0901Ambiguous tag: two imported modules define the name
L0902Bad tag value: not constant, not a struct, holds a pointer or an owner
L0903Bad tag arguments: no such field, wrong type, set twice, a bare name on a non-bool field, too many positional arguments
L0904Repeated tag: the same tag type twice on one field
L0905A library's rule failed (see below)
L0906@error in generated code, or a misused @fields, @for or @if

What libraries check

Rules such as "a default of the field's type" belong to the library that gives them meaning, or new libraries would need compiler changes. They must also fail where the tag is written, even if load[T] is never called, so they cannot live in the generator alone.

So a tag type may name a rule function, which the compiler runs at compile time once for each struct using the tag, and reports as L0905 at the field. It must be exported, since importers' structs call it too:

lora 
export @shorthand(config) @rule(check_tags) type field = struct { ... }

export fn check_tags(fields: []rt::tagged[field]) (void | rt::tag_problem) = {
	for (let f .. fields) {
		if (!f.tagged) continue;
		if (f.tag.env == "" && f.tag.default is void && !f.optional) {
			return rt::tag_problem {
				field = f.name,
				why = "nothing can set it: give it an env or a default",
			}
		}
	}
}

rt::tagged[T] and rt::tag_problem are plain values:

lora 
export type tagged[T] = struct {
	name: str,               // the field's name
	kind: type_kind,         // INT, STR, POINTER, ...
	optional: bool,          // ?T, or a nullable pointer
	has_default: bool,       // the field has a default: x: int = 5
	tagged: bool,            // it has the tag; if not, tag is T's defaults
	tag: T,
}
export type tag_problem = struct { field: str, why: str }

They hold values and not a *rt::typeinfo, because compile-time evaluation cannot follow @typeinfo pointers today. A rule gets every field of a struct that uses the tag at once, tagged or not, so it can compare them: a name a tag gives can be checked against another field's own name. A field with no tag has tagged false and the tag type's defaults. why must be a string constant: memory made at compile time cannot leave it.

The rules of each library

RuleApplies toError when
nothing can set itconfiga field with no env, no default, and not ?T
default typeconfigdefault's type is not the field's, as default = "x" on int
two defaultsconfiga field default as well as a tag
keyconfiga tag with no key
no tagconfig, at loada field has no @config
field typeconfig, at loadnot int, bool, str, or ? of one
duplicate keyconfigtwo tagged fields with one key
duplicate namejson, csvtwo fields with one JSON or column name, a field with no tag going by its own
skipconfig, jsonskip with env, a name or any other option
omit_emptyjsonon what has no empty value: bool, a number, or a struct
stringjsonon what is not a number
ignore_casejsonwith strict_case
field typejson, at marshala type with no JSON form

Meanings, for the generated code:

  • skip: the generator leaves the field alone in both directions. It is zero after decoding.
  • omit_empty: left out when encoding if it is "", [], void or null. Zero numbers and false are real values, so it is an error on them.
  • Optional (?T): absent means void, and is never an error. With a default, absent means the default. On null in JSON, it is void.
  • Must be set: a field with no default that is not optional. Absent, it is an error naming the key and the environment variable. There is no flag for this: a default says it may be absent, ?T says it may be empty, and anything else must be set.
  • str fields do not own. config strings are views of the environment or the tag. json::unmarshal takes an expanse::region, and copies strings and slices into it: a JSON string with escapes cannot be a view of the input, and owners are not allowed yet. They live as long as the region.

6. Errors at run time

Each library declares a real error type, so ? works and failures name the field:

lora 
export type error = !struct { key: str, env: str, why: str }
"config: {key}: {why} {env}";
export type mismatch = !struct { at: place, typename: name, want: name }
describe_mismatch;
text 
error: config: db_url: not set in DB_URL
error: cannot read str from JSON at byte 42 (/email): expected a string

Generated code uses ? as hand-written code does, so traces and notes work.

7. Not built yet

Tags on fields, shorthand, generators, rules, config::load[T], json::marshal[T]/unmarshal[T], and http::bind[T] with @path, @query, @header, @form and @body are built (http::router routes by pattern, without tags). Still to do:

WorkEnables
Tags on type and function declarations@db_table, @route

Known limits.

  • A rule sees only tagged fields, so @json("b") a: int next to an untagged b: int is not reported as a duplicate name.
  • A generator may not set an owner field (see above).
  • @same compares exact types, so json and config list the ?T they take.
  • Error traces show a generator's lines by their place in the .td file.

8. Open questions

  • Names. json::marshal here, from the design decision; the earlier table said json::encode.
  • Unions. @fields is for structs. Tagged unions may need a matching @members(T).
