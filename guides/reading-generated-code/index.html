Reading Generated QBE & Assembly

Step-by-step walkthrough of compiling a Lora module into QBE .ssa intermediate code and Darwin ARM64 machine assembly (docs/reading-generated-code.md).

A walkthrough of what one line of Lora becomes: the commands to see it, their output (from λexamples/hello.lora, on arm64 macOS), and what each part means. It is how to answer "what does this cost?" or "why does this behave like that?" by looking, and step 6 of Debugging.

The program:

lora 
use fmt;

export fn main() void = {
	fmt::println("hello from Lora")!;
}

1. Build it

sh 
lora build examples/hello.lora
text 
hello

The hello printed is the path of the program built (./hello, named after the source file), not the program's output. Run it with:

sh 
./hello
text 
hello from Lora

lora build and lora run keep what they compiled the program to in .build/app/, replaced by the next build: program.ssa, QBE's intermediate code, and Cprogram.s, the assembly. The core library's are .build/<module>.ssa and .s. (λapp.lora in other examples stands for your own file. Build into somewhere else with -o, as in lora build -o /tmp/hello examples/hello.lora.)

2. QBE's intermediate code

less .build/app/program.ssa

:

You're inside less, a pager. Press q to quit, space to page down, and / then a word (e.g. /function) to search.

What you're looking at:

  • Data first, then functions. Each dbgfile line names the source file for what follows ("<unknown>" for compiler-made data). Each data $name = { ... } is a constant.
    • $strdata.1 = { b "examples/hello.lora" } is the raw bytes of a string.
    • $strliteral.0 = { l $strdata.1, l 19, l 19 } is the str value itself: a pointer to those bytes, then its length (19) and capacity (19).
  • The core library's typedef paths (.build/fmt.td, .build/io.td, and so on) are stored as strings because some code compiled into the program comes from those modules. The program needs a file name to report locations in it, for example in an error trace.
  • Gaps inside some of them (fmt.t d), if your terminal shows any, are only how less drew the line. The lengths prove the strings are intact: fmt.td is 36 bytes, matching the l 36.
  • Your code comes further down. Search /function to jump to it.

3. Just the functions

To see the functions without paging through data:

sh 
grep -n -A12 "^export function\|^function" .build/app/program.ssa
text 
97:function $.main() {
98-@start.16
99-	%binding.46 =l alloc8 32
100-	%object.47 =l alloc8 16
101-@body.17
102-	dbgloc 3, 25
103-	dbgloc 4, 41
104-	dbgloc 4, 21
105-	dbgloc 4, 21
106-	dbgloc 4, 38
107-	%.20 =:type.21 call $fmt.println(:type.24 $strliteral.26)
108-@tag_valid.29
109-	%tag.30 =w loaduw %.20

Here's how it maps onto the program:

text 
3  export fn main() void = {
4  	fmt::println("hello from Lora")!;
5  };
text 
function $.main() {

Your main. The program's own functions get a . prefix, which is why nm shows a private half as _.half. The runtime's real _main sets things up (init functions, argument handling), then calls .main.

text 
@start.16
	%binding.46 =l alloc8 32
	%object.47 =l alloc8 16

Stack space reserved up front:

  • 32 bytes to hold an io::error if println fails;
  • 16 bytes for a pointer plus its type info, which is how the error is handed to the runtime for printing.

@name lines are labels (basic blocks), and %name are temporaries.

text 
	dbgloc 4, 41

These source positions (line, column) become the .loc line info in the assembly. Column 41 is the ! on line 4.

text 
	%.20 =:type.21 call $fmt.println(:type.24 $strliteral.26)

The call. "hello from Lora" is passed as $strliteral.26: a str value (pointer, length, capacity) stored as data at the top of the file. The result %.20 is a (void | io::error) tagged union, :type.21, a struct type defined above.

The rest of the function is the !, which the compiler lowered to a match on that result:

text 
function $.main() {
@start.16
	%binding.46 =l alloc8 32
	%object.47 =l alloc8 16
@body.17
	dbgloc 3, 25
	dbgloc 4, 41
	dbgloc 4, 21
	dbgloc 4, 21
	dbgloc 4, 38
	%.20 =:type.21 call $fmt.println(:type.24 $strliteral.26)
@tag_valid.29
	%tag.30 =w loaduw %.20
@begin_match.28
	%subval.35 =l copy %.20
	%.36 =w ceqw %tag.30, 0
	jnz %.36, @subtype.38, @next.33
@subtype.38
	jmp @match.34
@match.34
	dbgloc 4, 41
	jmp @.32
@next.33
	%subval.41 =l copy %.20
	%.42 =w ceqw %tag.30, 1589436883
	jnz %.42, @subtype.44, @next.39
@subtype.44
	jmp @match.40
@match.40
	%.45 =l add %.20, 8
	blit %.45, %binding.46, 32
	dbgloc 4, 41
	dbgloc 4, 41
	%field.49 =l add %object.47, 0
	# gen lowered cast
	dbgloc 4, 41
	storel %binding.46, %field.49
	%field.49 =l add %object.47, 8
	dbgloc 4, 41
	storel $.typeinfo.5ebce1d3, %field.49
	%.50 =l loadl %object.47
	%.52 =l add %object.47, 8
	%.51 =l loadl %.52
	call $rt.abort_error(l $strliteral.0, l 4, l 41, l %.50, l %.51)

In outline:

text 
	%tag.30 =w loaduw %.20                  # which member is it?
	%.36 =w ceqw %tag.30, 0                 # tag 0: void, it succeeded
	jnz %.36, @subtype.38, @next.33         #   → jump on to the end
...
	%.42 =w ceqw %tag.30, 1589436883        # io::error's type id
	jnz %.42, @subtype.44, @next.39
@match.40                                  # it's an io::error:
	blit %.45, %binding.46, 32              #   copy the 32-byte error out
	storel %binding.46, ...                 #   pair it with its type info
	storel $.typeinfo.5ebce1d3, ...
	call $rt.abort_error(l $strliteral.0, l 4, l 41, l %.50, l %.51)

On failure it calls rt.abort_error with:

  • the file name ($strliteral.0 is "examples/hello.lora", the first string in the file);
  • line 4, column 41;
  • the error and its type info.

That call is what prints examples/hello.lora:4:41: abort: error occurred: … with the error's own message.

So one line of Lora becomes:

  • a call;
  • a check of which member came back (no exceptions or unwinding, just a tag compare);
  • a slow path that only runs when writing to stdout fails.

4. The assembly

sh 
less .build/app/program.s
text 
.file 1 "<unknown>"
.section __DATA,__data
.balign 8
_strdata.1:
	.ascii "examples/hello.lora"
/* end data */

.section __DATA,__data
.balign 8
_strliteral.0:
	.quad _strdata.1+0
	.quad 19
	.quad 19
/* end data */

.section __DATA,__data
.balign 8
_strdata.3:
	.ascii "/Users/israelndou/lora/.build/fmt.td"
/* end data */

.section __DATA,__data
.balign 8
_strliteral.2:
:

Each data from the .ssa becomes a labelled block in __DATA,__data. _strliteral.0 is the str for "examples/hello.lora": three 8-byte words (.quad), a pointer to the bytes plus length 19 and capacity 19.

main, in order:

asm 
_.main:
	hint	#34                    ; BTI landing pad (Apple's branch protection)
	stp	x29, x30, [sp, -112]!  ; save frame pointer + return address, 112-byte frame
	mov	x29, sp
	.loc 2 4 41                    ; line info: file 2, line 4, column 41
asm 
	adrp	x0, _strliteral.26@page        ; ...3 times, one per word:
	add	x0, x0, _strliteral.26@pageoff
	ldr	x0, [x0]                       ; load a word of the str
	str	x0, [x1]                       ; store it into the frame at x29+16

The 24-byte str argument is copied onto the stack. Arguments larger than 16 bytes are passed by pointer on arm64, so the caller makes a copy.

asm 
	add	x0, x29, #16       ; x0 = pointer to that copy (the argument)
	add	x8, x29, #40       ; x8 = where to put the result (a struct return)
	bl	_fmt.println
asm 
	ldr	w0, [x0]           ; the result's tag
	cmp	w0, #0
	beq	L4                 ; 0 = void: success, skip to the end
	mov	w1, #57811
	movk	w1, #0x5ebc, lsl #16   ; build 0x5ebce1d3, io::error's type id
	cmp	w0, w1
	beq	L3                 ; an io::error → L3, which calls rt.abort_error
	...
	bl	_rt.abort_fixed    ; any other tag: "no arm matches" (kind 9), impossible here
	brk	#1000              ; trap if it ever returned

0x5ebce1d3 is the same number as the 1589436883 in the .ssa file, in hex, and it matches the $.typeinfo.5ebce1d3 symbol. The .loc lines are what a debugger uses to map instructions back to hello.lora:4:41 (see the DWARF limit under Debugging).

L3, the error path (only runs if writing to stdout fails):

asm 
L3:
	add	x0, x29, #40       ; the result; its io::error starts 8 bytes in,
	add	x0, x0, x1         ;   after the tag
	ldr	x1, [x1]           ; copy the 32-byte error, 8 bytes at a time
	str	x1, [x2]           ;   into the frame at x29+80   (×4)

That's the blit %.45, %binding.46, 32 from the .ssa. Then the call that prints it:

asm 
	adrp	x4, _.typeinfo.5ebce1d3@page   ; arg 4: io::error's type info, so the
	add	x4, x4, ...                   ;   runtime can describe it
	add	x3, x29, #80                  ; arg 3: the error itself
	mov	x2, #41                       ; arg 2: column 41 (the `!`)
	mov	x1, #4                        ; arg 1: line 4
	adrp	x0, _strliteral.0@page        ; arg 0: "examples/hello.lora"
	bl	_rt.abort_error               ; prints "examples/hello.lora:4:41: abort: ..."
	brk	#1000                         ; never returns; trap if it did

The arguments go in x0 to x4, the arm64 calling convention, matching rt.abort_error(path, line, col, value, typeinfo) in the .ssa.

L4, success:

asm 
L4:
	ldp	x29, x30, [sp], 112   ; restore frame pointer + return address, free the frame
	ret

The whole picture: on the normal path main runs about 40 instructions:

  • set up the frame;
  • copy the string argument;
  • bl _fmt.println;
  • one tag compare;
  • return.

Everything in L3 is cold code for the failure case.

An optimisation opportunity. Copying the string constant takes 15 instructions, recomputing the same address (adrp/add) for each of the three words and adding zero offsets (mov x2, #0 … add x1, x1, x2). Each 8-byte copy recomputes the base address and adds a constant through a register (mov x3, #8 → add x2, x29, #80 → add x2, x2, x3), where arm64 could write str x1, [x29, #88] in one instruction: QBE doesn't fold constant offsets into addressing modes for these copies. A peephole pass in the vendored qbe/ would cut such sequences to about a third, in every function that passes or copies structs, slices or strings.

Try it yourself

  • Change the ! to ?, with main returning (void | io::error), and rebuild: the slow path becomes copying the error into the return value and adding a trace entry. Diffing program.ssa before and after is a good way to see what each feature costs.
  • Build any program of your own the same way, and find its functions with the grep and awk commands above.
  • The core library's code is in .build/<module>.ssa and .s: for fmt::println itself, .build/fmt.ssa.
