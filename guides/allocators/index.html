Allocators & Memory Strategies

Where memory comes from: the heap, scratch, expanse regions, pool, rc/arc, and the allocator interface with its fixed buffer, atomic fixed buffer, stack fallback, slab, free list, ring, thread_safe and set_global: what each is, when to use it, and examples (docs/allocators.md).

Every value that outlives the call that made it lives in memory that came from somewhere: the heap, a region, a scratch frame, a pool, or a buffer you handed over. Lora gives one way to ask for memory for each kind of lifetime, and the compiler checks each of them: memory can't be used after it is given back, and memory nothing gives back is reported (see the language reference's Memory and Ownership).

Choosing

You haveUseGiven back
a value or a list with one owneralloc, append: the heapwhen its owner ends
what one piece of work needs while it runsscratchwhen the work returns
many values that live and die togetherexpanseall at once: reset or finish
values that point at each otherpoolone at a time, by handle
one value with several ownersrc, arcwhen the last owner ends
code that must be told where its memory comes froman allocatoras that allocator gives it back

Start with the heap. Reach for the others when a profile or a design asks for them: a request handler that makes a thousand small strings wants a region; a graph wants a pool; a device with no heap wants a fixed buffer.

The heap: alloc, free, append

alloc puts a value on the heap and gives its owner, ^T; the owner frees it when it ends, or free does it sooner. A growing slice, ^[]T, is the same for many values: append and insert make room as it grows.

lora 
type user = struct { name: str, age: int }

export fn main() void = {
	let u = alloc(user { name = "ada", age = 36 })!;   // freed at the end of main
	let ids: ^[]int = [];                              // freed with it
	for (let i = 0; i < 100; i += 1) append(ids, i)!;
	let zeros = alloc([0u8...], 4096)!;                // 4096 zeroed bytes
	assert(u.age == 36 && len(ids) == 100 && zeros[4095] == 0);
}
  • When: almost always. One owner per value is the default, and the compiler frees what nothing else takes.
  • Growth: a slice that needs more room doubles its capacity; one that starts empty gets at least 16 bytes of elements, so a short slice built one element at a time is allocated once. reserve(s, n) makes room for n more in one step when you know how many are coming.
  • Zero fills: alloc([0...], n), with any value that is all zero bytes, takes memory the system gives already zeroed and writes nothing: a large buffer costs only the pages that are used.
  • Failure: every allocation can fail with nomem; ! stops the program, ? passes it on, match handles it.

scratch: memory for a piece of work

scratch::with runs a function with a frame to take memory from, and gives all of it back when the function returns. Each coroutine and thread has its own scratch, which keeps its pages, so taking from it is one pointer move with no lock.

lora 
use scratch;
use strings;

// the longest word, after trimming: the trimmed copies are needed only here
fn longest(words: []str) usize = scratch::with(fn(s: *scratch::frame) usize = {
	let n = 0z;
	for (let w .. words) {
		let t = scratch::copy(s, strings::trim(w))!;
		if (len(t) > n) n = len(t);
	}
	return n;
});

export fn main() void = assert(longest(["  ada ", "lovelace"]) == 8);
  • When: a function builds things it only reads before it returns: parsing a line, formatting a key, sorting a copy.
  • Checked: what the frame gives views it, so returning it or keeping it past the body is an error (L0608).
  • Nesting: an inner with gives back only what it took.

expanse: regions that grow in place

A region reserves address space up front and commits pages as it fills, so what it holds never moves. expanse::auto() sizes itself; reserve asks for a size. Everything in a region is given back at once.

lora 
use expanse;

type point = struct { x: int, y: int }

export fn main() void = {
	let r = expanse::auto();                  // given back when main ends
	let first = expanse::new(&r, point { x = 1, y = 2 })!;
	for (let i = 0; i < 10000; i += 1) {
		expanse::new(&r, point { x = i, y = i })!;
	}
	assert(first.x == 1);                     // nothing it holds ever moves
	let m = expanse::here(&r);
	let note = expanse::copy(&r, "only needed for a moment")!;
	assert(len(note) == 24);
	expanse::rewind(&r, m);                   // back to the mark: note ends
	assert(expanse::used(&r) >= 10001 * size_of(point));
}
  • When: many values with one lifetime: everything one request, one document or one frame of a game builds. Freeing them is one step, and nothing is freed one by one.
  • Marks: here and rewind give back everything taken since a mark, for a loop that builds and discards.
  • Checked: what a region gives views it: it can't outlive the region, and reset, rewind, shrink and finish end it (L0608, L0609).
  • Many at once: an auto region starts with 64 MiB of address space, which costs no memory until used, and takes more ranges as it fills, so thousands of regions (one per connection) can be in use together.

pool: values reached by handles

A pool keeps values of one type in slots, and gives a handle for each: the slot and its generation, not a pointer. A removed value's handles find nothing, never what took its place.

lora 
use pool;

type person = struct { name: str, boss: pool::handle[person] }

export fn main() void = {
	let people = pool::new::[person]();
	let ceo = pool::put(&people, person { name = "grace", ... })!;
	let dev = pool::put(&people, person { name = "alan", boss = ceo })!;
	let d = pool::get(&people, dev) as *person;
	assert(pool::get(&people, d.boss) != null);
	pool::remove(&people, ceo);
	assert(pool::get(&people, ceo) == null);   // gone, and its handles see that
}
  • When: values that refer to each other (graphs, trees with parent links, a game's entities), with no unsafe code and no owners in a cycle.
  • Checked: a pointer from get views the pool; a put may move the slots, so it can't be used after one (L0609).

rc and arc: several owners

rc counts its owners and drops the value with the last one; weak refers to it without keeping it alive. arc is the same with atomic counts, for values shared between threads.

lora 
use rc;

type config = struct { name: str, retries: int }

export fn main() void = {
	let a = rc::new(config { name = "prod", retries = 3 })!;
	let b = rc::share(&a);                     // a second owner
	assert(rc::count(&a) == 2 && rc::get(&b).retries == 3);
}
  • When: a value genuinely has several owners and no one of them outlives the rest. One owner and borrows are simpler and cost nothing.
  • Cycles: rc::new refuses a type that could own itself; a link back is a weak.

The allocator interface

Code that must be told where its memory comes from takes an allocator::allocator: a library that serves a device with no heap, a parser whose caller decides, a hot path given a buffer on the stack.

lora 
type allocator = interface {
	fn alloc_bytes(n: usize, alignment: usize) (*opaque | nomem);
	@unsafe fn resize_bytes(p: *opaque, old_n: usize, new_n: usize, alignment: usize) bool;
	@unsafe fn realloc_bytes(p: *opaque, old_n: usize, new_n: usize, alignment: usize) (*opaque | nomem);
	@unsafe fn free_bytes(p: *opaque, n: usize, alignment: usize) void;
}

fn create[T](a: allocator, v: T) (*T | nomem)       // views a
fn make[T](a: allocator, n: usize) ([]T | nomem)    // zeroed; views a
fn copy_str(a: allocator, s: str) (str | nomem)     // views a
@unsafe fn destroy[T](a: allocator, p: *T) void
@unsafe fn free_slice[T](a: allocator, s: []T) void
@unsafe fn free_str(a: allocator, s: str) void
@unsafe fn grow[T](a: allocator, s: []T, n: usize) ([]T | nomem)
@unsafe fn resize_slice[T](a: allocator, s: []T, n: usize) ([]T | void)

A function that takes an allocator works with any of them:

lora 
use allocator;
use strings;

// "key=value", in memory from a
fn pair(a: allocator::allocator, k: str, v: str) ([]u8 | nomem) = {
	let out = allocator::make::[u8](a, len(k) + 1 + len(v))?;
	let kb = strings::to_bytes(k), vb = strings::to_bytes(v);
	for (let i = 0z; i < len(kb); i += 1) out[i] = kb[i];
	out[len(kb)] = '=';
	for (let i = 0z; i < len(vb); i += 1) out[len(kb) + 1 + i] = vb[i];
	return out;
}

export fn main() void = {
	let fb = allocator::fixed_buffer_owned(256)!;
	let line = pair(&fb, "port", "8080")!;
	assert(len(line) == 9 && line[4] == '=');
}

What is checked. What create, make and copy_str give is a view of the allocator: it can't outlive it, nor the buffer the allocator hands out (L0608), and resetting or rewinding the allocator ends it (L0609). Giving memory back one piece at a time is unsafe: the caller vouches that the memory came from that allocator, at that size, and that nothing uses it after (L0800). Allocators freed all at once, by reset, need no unsafe code at all.

Owned or lent. The allocators that hand out a buffer (a fixed buffer, an atomic one, a stack fallback, a free list and a ring) take it one of two ways. X_owned(n) gives them n zeroed bytes of their own, which nothing else can write, freed when they are dropped: safe. X_new(buf) lends them a buffer you have, as an array on the stack, so that nothing is allocated: unsafe, as what they hand out lives in buf, and you vouch that nothing else writes buf while any of it is in use. Either way they are moved, never copied, as two copies would hand out the same bytes.

Sealed. Every allocator type is @sealed: only the allocator module reads and writes its fields, so its position and bookkeeping are always as its functions keep them. Its zero value, T { ... }, holds nothing, and anything asked of it fails with nomem.

system: the heap

allocator::system_allocator() is the heap behind an allocator, for code that takes one when the caller has no reason to choose.

lora 
use allocator;

export fn main() void = {
	let a = allocator::system_allocator();
	let xs = allocator::make::[int](a, 100)!;
	xs[99] = 7;
	unsafe { allocator::free_slice(a, xs) };   // this size, from this allocator
}

from_region: a region behind the interface

allocator::from_region(&r) lets code that takes an allocator fill an expanse region, which gives everything back at once.

lora 
use allocator;
use expanse;

export fn main() void = {
	let r = expanse::auto();
	let ra = allocator::from_region(&r);
	let name = allocator::copy_str(&ra, "ada")!;
	assert(name == "ada" && expanse::used(&r) >= 3);
}

fixed_buffer: memory in order, with a hard limit

A fixed buffer hands out its memory in order, each piece aligned as asked, and fails with nomem when it is used up: it never asks for more. Giving back the last piece, or growing it, works where it is; anything else waits for rewind or reset, which give back everything at once.

lora 
use allocator;

export fn main() void = {
	let fb = allocator::fixed_buffer_owned(4096)!;     // freed with fb
	let a: allocator::allocator = &fb;
	for (let round = 0; round < 3; round += 1) {
		let m = allocator::fixed_buffer_mark(&fb);
		let xs = allocator::make::[u32](a, 64)!;
		let name = allocator::copy_str(a, "ada")!;
		assert(xs[63] == 0 && name == "ada");
		allocator::fixed_buffer_rewind(&fb, m);        // xs and name end here
	}
	assert(allocator::fixed_buffer_used(&fb) == 0);
	assert(allocator::make::[u8](a, 8192) is nomem);  // more than it holds
}

Lent a stack array, it allocates nothing at all:

lora 
use allocator;

export fn main() void = {
	let buf: [1024]u8 = [0...];
	// nothing writes buf while fb hands it out
	let fb = unsafe { allocator::fixed_buffer_new(buf[..]) };
	let xs = allocator::make::[u64](&fb, 16)!;
	xs[15] = 7;
	assert(allocator::fixed_buffer_used(&fb) == 128);
}
  • When: a hard limit on memory, or a hot loop that should not call the system: reset it each turn.

atomic_fixed_buffer: a fixed buffer for many threads

The same as a fixed buffer, taking each piece with one compare-and-swap, so it guards itself: it is @synchronised, and @go children may share a pointer to it, making the interface in the child. Pieces are given back only by atomic_fixed_buffer_reset, which is unsafe, as the compiler can't see what other threads still hold.

lora 
use allocator;
use coro;

export fn main() void = {
	let af = allocator::atomic_fixed_buffer_owned(65536)!;
	let p = &af;                                    // shared by the children
	@scope(workers = 4) {
		for (let w = 0z; w < 4; w += 1) {
			@go {
				let a: allocator::allocator = p;
				for (let i = 0z; i < 64; i += 1) {
					let x = allocator::create(a, @u64(w * 1000 + i))!;
					assert(*x == @u64(w * 1000 + i));
				}
			};
		}
	}!;
	assert(allocator::atomic_fixed_buffer_used(&af) >= 4 * 64 * 8);
	// the children are done, and nothing they took is used now
	unsafe { allocator::atomic_fixed_buffer_reset(&af) };
}
  • When: worker threads that each build a little, all thrown away together when the work is done.
  • Not the interface: an interface value can't be shared with a child, as what it points to may be of any type; share &af and make it there.

stack_fallback: a buffer first, then another allocator

A fixed buffer that, when it is full, takes from another allocator instead: small cases use the buffer, and large ones still work.

lora 
use allocator;

export fn main() void = {
	let sf = allocator::stack_fallback_owned(256, allocator::system_allocator())!;
	let a: allocator::allocator = &sf;
	let small = allocator::make::[u64](a, 8)!;       // from its buffer
	let large = allocator::make::[u64](a, 1000)!;    // from the heap
	small[0] = 1;
	large[999] = 2;
	unsafe { allocator::free_slice(a, large) };      // the heap's, given back
	allocator::stack_fallback_reset(&sf);            // and the buffer's, all at once
}

Lent a stack array with unsafe { allocator::stack_fallback_new(buf[..], fallback) }, the small cases allocate nothing.

  • When: sizes that are usually small but have no hard limit: a path, a header, a short list.

slab: many values of one size

A slab cuts chunks from another allocator into slots of one size, and gives a freed slot to the next request. Slots never move.

lora 
use allocator;

type point = struct { x: i64, y: i64 }

export fn main() void = {
	let sb = allocator::slab_new(allocator::system_allocator(), size_of(point), align(point), 64);
	defer allocator::slab_finish(&sb);
	let a: allocator::allocator = &sb;
	let p = allocator::create(a, point { x = 1, y = 2 })!;
	let q = allocator::create(a, point { x = 3, y = 4 })!;
	assert(allocator::slab_live(&sb) == 2 && p.x + q.y == 5);
	unsafe { allocator::destroy(a, p) };              // its slot is reused next
	assert(allocator::slab_live(&sb) == 1);
}
  • When: many short-lived values of one type, made and given back in any order: messages, nodes, sessions. A request of another size fails with nomem.

free_list: any size, given back in any order

A free list keeps freed blocks by size and joins neighbours, so memory given back in any order is used again. It keeps that bookkeeping in its buffer, which is why a lent buffer must be written by nothing else.

lora 
use allocator;

export fn main() void = {
	let fl = allocator::free_list_owned(4096)!;
	let a: allocator::allocator = &fl;
	let xs = allocator::make::[u64](a, 32)!;
	let ys = allocator::make::[u64](a, 32)!;
	unsafe { allocator::free_slice(a, xs) };          // in any order
	unsafe { allocator::free_slice(a, ys) };
	assert(allocator::free_list_used(&fl) == 0);
}
  • When: a bounded budget with pieces of many sizes given back in any order, such as a cache with a fixed size.

ring: given back in the order it was taken

A ring takes pieces in order and wraps around, for memory given back about as it was taken: a queue of messages, a log's lines. Like a free list it keeps its bookkeeping in its buffer.

lora 
use allocator;

export fn main() void = {
	let rg = allocator::ring_owned(512)!;
	let a: allocator::allocator = &rg;
	for (let i = 0; i < 100; i += 1) {             // far more than 512 bytes in all
		let msg = allocator::make::[u8](a, 64)!;
		msg[0] = 'm';
		unsafe { allocator::free_slice(a, msg) };
	}
	assert(allocator::ring_live(&rg) == 0);
}

thread_safe: a lock around another allocator

thread_safe_new(inner) puts a lock around every call to another allocator, so threads can share one that can't be shared by itself. It is @synchronised: @go children share a pointer to it. Making one is unsafe, as the lock guards inner only if every use of inner goes through it: you vouch that nothing uses inner directly while it is in use. It is moved, never copied, so there is one lock.

lora 
use allocator;
use coro;

export fn main() void = {
	let fb = allocator::fixed_buffer_owned(65536)!;
	// only through ts while the children run
	let ts = unsafe { allocator::thread_safe_new(&fb) };
	let p = &ts;
	@scope(workers = 4) {
		for (let w = 0z; w < 4; w += 1) {
			@go {
				let a: allocator::allocator = p;
				let xs = allocator::make::[u64](a, 16)!;
				xs[15] = @u64(w);
			};
		}
	}!;
	assert(allocator::fixed_buffer_used(&fb) >= 4 * 16 * 8);
}

The system allocator needs no lock: it guards itself, and each child can take it with allocator::system_allocator().

set_global: every allocation through one allocator

set_global sends what alloc, free and append do through an allocator until reset_global. Code that knows nothing of allocators then takes its memory from yours: a test that counts, a program that must stay inside a budget. It is unsafe: memory taken through one allocator must be given back to the same one, so nothing made before set_global may be freed after it, nor the other way round.

lora 
use allocator;

export fn main() void = {
	let buf: [16384]u8 = [0...];
	let fl = unsafe { allocator::free_list_new(buf[..]) };
	let a: allocator::allocator = &fl;
	unsafe {
		allocator::set_global(&a);
		{
			let xs: ^[]int = [];
			for (let i = 0; i < 100; i += 1) append(xs, i)!;
			assert(allocator::free_list_used(&fl) > 0);
		}                                          // xs freed into fl
		allocator::reset_global();
	};
	assert(allocator::free_list_used(&fl) == 0);
}

Raw bytes: mem

mem::new gives zeroed bytes that no owner frees: the caller gives them back with mem::release. Both are unsafe; they are for building the allocators above and for memory handed to C. mem::copy and mem::zero are safe, on slices.

lora 
use mem;

export fn main() void = {
	let src: [5]u8 = [1, 2, 3, 4, 5];
	let dst: [5]u8 = [0...];
	mem::copy(dst[..], src[..]);
	assert(dst[4] == 5);
	mem::zero(dst[..]);
	assert(dst[0] == 0);
}

Leaks

Memory nothing gives back is reported. At compile time, an owner that is never freed or moved is an error. At run time, lora run --leaks (or LORA_LEAKS=1) lists every block still allocated when the program ends, with where it was made and how to give it back; memory from an allocator is named by the call that made it, allocator::make, with the call that returns it, allocator::free_slice(a, x).
