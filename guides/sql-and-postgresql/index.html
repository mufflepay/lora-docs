Typed SQL, PostgreSQL & SQLite

Compile-time checked @sql(...) queries, live PostgreSQL schema checks (lora sql schema), embedded sqlite via dlopen, transactions, pooling, prepared pipelines, large objects, and logical replication (docs/sql.md).

Lora talks to PostgreSQL itself: pg speaks the wire protocol in Lora, with no C library, and sql is what programs use: a pool of connections, transactions, rows read into structs, and @sql, queries written as Lora and checked when compiling, against the database's own schema.

lora 
use expanse;
use pg;
use sql;

type customer = struct @table("customers") {
	@column(key, auto) id: i64,
	name: str,
	@column("nr_orders") orders: i32,
	country: ?str,
}

fn report(db: *pg::db) (void | sql::error | nomem) = {
	let r = expanse::reserve(1 << 20)!;
	let n = @sql(db) count customer where .country == "uk"?;
	let uk = @sql(db, into = &r) from customer where .country == "uk" && .orders > 0
		order .name?;
	defer free(uk);
	let id = @sql(db) insert customer { name = "Bob", orders = 10, ... }?;
	@sql(db) update customer set .orders += 1 where .id == id?;
}

export fn main() void = void;

Every value from the program is a bound parameter: .country == "uk" sends "country" = $1 and "uk" apart, in PostgreSQL's binary form where it has one. A string is never spliced into SQL, so injection can't happen.

1. Connecting

pg::open(url, limits) gives a pool, pg::db; pg::connect(url) one connection, for the driver's own functions.

lora 
use pg;
use sql;

fn connect() (void | sql::error | nomem) = {
	let db = pg::open("postgres://app:secret@db.example:5432/shop?application_name=web",
		sql::limits { max_open = 20, max_idle = 5, max_lifetime_ms = 30 * 60 * 1000, ... })?;
	defer sql::close(&db);
}

export fn main() void = void;

The URL is libpq's: postgres://user:password@host:port/database?options, each part optional, and the PG* environment variables (PGHOST, PGPORT, PGUSER, PGPASSWORD, PGDATABASE, PGAPPNAME, PGSSLMODE, PGSSLROOTCERT, PGSSLCERT, PGSSLKEY, PGCHANNELBINDING, PGCONNECT_TIMEOUT, PGPASSFILE) give what it leaves out.

OptionMeaning
host=/tmpa directory: the server's local socket in it, /tmp/.s.PGSQL.5432
a:5432,b:5433 (or host=a,b)several servers, tried in order until one answers
target_session_attrs=any, read-write, read-only, primary, standby, prefer-standby

A password not given is read from the password file (PGPASSFILE, or ~/.pgpass), as libpq reads it, if only its owner may read the file.

Logging in: SCRAM-SHA-256 (PostgreSQL's default), and over TLS SCRAM-SHA-256-PLUS, which binds the login to the server's certificate; MD5, and a plain password; over TCP or the local socket.

TLS is tls's, TLS 1.3, over TCP; a local socket is private as it is and never uses it. As libpq has them, prefer uses TLS when the server speaks it, require always (checking the certificate's chain when there is a root file), verify-ca with the chain checked, and verify-full with the certificate also for the host connected to. pg::secure(&c) says whether a connection is over TLS; what fails is sql::insecure, saying why.

2. Tables and rows

A row is a struct. Its fields are its columns, named as the fields are or as @column("name") says; @column(skip) leaves a field out of rows, and @column(key, auto) marks a key the database fills in (an identity or serial), which insert gives back. struct @table("name") { ... } names the table, which is otherwise the struct's own name.

A column that may be NULL is read into ?T. Arrays, records and ranges are read into the region too: their elements are copied into it. Each is written the same way, from the same Lora types: a slice of slices is a two-dimensional array, a struct a record, a span a range. The driver asks the server, once a connection, about the types it has not met: an array of a composite type of your own, say.

lora 
use expanse;
use pg;
use sql;

type cash = struct { amount: i64, currency: str }

type stay = struct @table("stays") {
	@column(key, auto) id: i64,
	grid: [][]i64,
	price: cash,
	nights: sql::span[sql::date],
	route: []sql::point,
}

fn book(db: *pg::db, r: *expanse::region, grid: [][]i64) (void | sql::error | nomem) = {
	let id = @sql(db) insert stay {
		grid = grid,
		price = cash { amount = 1250, currency = "EUR" },
		nights = sql::span { lower = sql::date { days = 9000 }, upper = sql::date { days = 9003 },
			lower_inc = true, ... },
		route = [sql::point { x = 0.0, y = 0.0 }, sql::point { x = 3.0, y = 4.0 }],
		...
	}?;
	let s = (@sql(db, into = r) first stay where .id == id)? as stay;
}

export fn main() void = void;

3. @sql

@sql(db) or @sql(&t) (a transaction). The rows a query keeps (from, first, returning, text read as a struct) are copied out of the connection: the rows into an owned slice, and their text and bytes into a region. With no into, @sql keeps a region of its own for the block the query is in: nothing is reserved until a row needs room, it grows in place as rows come, with no size to choose, and it is freed when the block ends. So the rows live as long as the block, which the compiler checks:

lora 
use pg;
use sql;

type user = struct { id: i64, name: str }

fn count_names(db: *pg::db) (usize | sql::error | nomem) = {
	let users = @sql(db) "select id, name from users" as user?;
	let n = 0z;
	for (let u .. users) n += len(u.name);
	return n;            // returning users[0].name would be an error
}

export fn main() void = void;

To keep rows longer, give into = &r a region the caller owns: sql::auto_region() sizes itself the same way, or expanse::reserve(n) holds at most n bytes. A ? or ! at the end is @sql's own. To compare its result, put it in parentheses: (@sql(db) count customer where ...)? == 3.

lora 
use expanse;
use pg;
use sql;

type order = struct @table("orders") {
	@column(key, auto) id: i64,
	shopper: i64,
	total: f64,
}
type shopper = struct @table("shoppers") { @column(key, auto) id: i64, name: str }
type spent = struct { name: str, n: i64, total: f64 }

fn top(db: *pg::db, r: *expanse::region) (void | sql::error | nomem) = {
	let rows = @sql(db, into = r) from order join shopper on .order.shopper == .shopper.id
		group .shopper.name
		having sql::sum(.order.total) > 100.0
		order .shopper.name
		select spent { name = .shopper.name, n = sql::count(), total = sql::sum(.order.total) }?;
	defer free(rows);
}

export fn main() void = void;

4. Checked against the database

lora sql schema <url> writes λlora.schema: the database's tables, their columns, which may be NULL and which have defaults. The compiler finds it in the source's directory or one above, or at LORA_SCHEMA, and checks each @sql against it while building, with no database needed then:

  • the table, and each column the struct reads;
  • each field's type against its column's;
  • a column that may be NULL read into a field that is not ?T;
  • an insert that leaves out a column the database needs.

SQL written as text is checked too, as far as can be told for certain: the tables a select, insert, update or delete names, the columns it names in them (by a table's alias too, and excluded of on conflict), and, read as a struct, that each field has a column of the result. The error is on the name in the text, with the nearest one the database has:

text 
app.lora:6:47: error: Table users has no column nme.
  = help: Did you mean name?	name

What can't be told for certain is left to the server: a query inside the query, with, union, tables of a schema other than public, rows of a function, and the types of what the text computes.

A string written anywhere else that reads as a query, starting with select, insert, update or delete, is checked the same way, but warned of rather than refused, and only once it names a table the database has (or one a letter or two from it): "update the readme first" is let be.

text 
table customers
	id int8 key default
	name text
	nr_orders int4
	country text null

Write it again when the database changes. In the editor there is no need: with lora.databaseUrl set, the language server reads the schema from the database itself, and again every lora.schemaRefresh seconds (30), and checks against that, so an error shows as the query is typed and goes when the database gains the column. lora.schemaSource picks between the two: auto (the database when there is a URL, else λlora.schema), file or database.

In the editor, SQL in strings is highlighted as SQL, and completes: table names after from, join, into and update, and the columns of the tables the query names (an alias's after u.), each with its type.

5. Transactions

lora 
use pg;
use sql;

type account = struct { @column(key) id: i64, cents: i64 }

fn transfer(db: *pg::db, from: i64, to: i64, cents: i64) (void | sql::error | nomem) = {
	let t = sql::begin_with(db, sql::tx_options { isolation = sql::isolation::serializable, ... })?;
	@sql(&t) update account set .cents -= cents where .id == from?;
	@sql(&t) update account set .cents += cents where .id == to?;
	sql::commit(db, &t)?;
}

export fn main() void = void;
  • sql::transaction(db, fn(t) ...) commits when the closure gives void and rolls back when it fails.
  • sql::savepoint(&t, "name"), sql::rollback_to, sql::release_savepoint.
  • tx_options: isolation (read_committed, repeatable_read, serializable), read_only, deferrable.

6. The pool

sql::db is safe for any number of coroutines and threads at once: each query takes a connection and gives it back. limits are Go's: max_open (0: as many as needed), max_idle (2), max_lifetime_ms, max_idle_ms. At max_open, a query waits for a connection to come back; in a coroutine others run meanwhile, and cancelling it ends the wait.

Without @sql: sql::exec, sql::scalar::[T], sql::first::[T], sql::all::[T] and sql::each, with SQL and a []sql::value of its parameters, $1, $2, ...

7. The driver: pg

On one connection, pg::conn:

  • pg::query, pg::next, pg::values: rows as views of the connection's buffer; pg::exec, pg::exec_script (several statements).
  • Each query is prepared once per connection, and kept (least used goes).
  • pg::copy_in, copy_row, copy_end, copy_abort: COPY FROM STDIN; pg::copy_out and copy_next: COPY TO STDOUT.
  • pg::listen, pg::notify, pg::wait: LISTEN and NOTIFY.
  • pg::cancel(&c): stops what c runs, from another connection.
  • Errors: sql::server with its SQLSTATE (sql::sqlstate(&e.d)), message, detail, hint, constraint, table, column and position; a unique or exclusion violation is sql::conflict.

Pipelines

Queries sent at once run one after another in a single round trip, as one transaction unless they begin their own: one that fails undoes those before it, and those after it are sql::skipped. sql::batch runs statements so through the pool and gives how many rows each changed; on a connection, pg::send_pipeline sends them, pg::next_result gives each one's rows in turn (what is not read of one is skipped), and pg::end_pipeline reads to the end.

lora 
use pg;
use sql;

fn tidy(db: *pg::db) (void | sql::error | nomem) = {
	let n: [3]u64 = [0...];
	sql::batch(db, [
		sql::statement { text = "insert into log (what) values ($1)", args = ["tidy"] },
		sql::statement { text = "delete from sessions where expires < now()" },
		sql::statement { text = "update counters set runs = runs + 1" },
	], n[..])?;
}

export fn main() void = void;

Large objects

Data kept apart from tables, by number, read and written in parts as a file is, inside a transaction: pg::lo_create, lo_open (lo_mode::read, write, read_write), lo_read, lo_write, lo_seek (from whence::set, current, end), lo_tell, lo_truncate, lo_close and lo_unlink.

Logical replication

A connection opened with replication=database streams the changes a publication makes, from a slot, decoded from pgoutput:

lora 
use fmt;
use pg;
use sql;

fn follow(url: str) (void | sql::error | nomem) = {
	let c = pg::connect(url)?; // ...?replication=database
	defer pg::close(&c);
	let from = pg::create_slot(&c, "shop_slot", false)?;
	let s = pg::begin_replication(&c, "shop_slot", ["shop_pub"], from)?;
	for (true) match (pg::receive(&c, &s)?) {
		done => break,
		let i: pg::inserted => {
			let table = pg::relation_of(&s, i.rel) as *pg::relation;
			for (true) match (pg::next_column(&i.new)?) {
				done => break,
				let text: str => fmt::println(text)!,
				void => fmt::println("NULL")!,
				pg::unchanged => void,
			}
		},
		let k: pg::committed => pg::acknowledge(&c, &s, k.end)?,
		_ => void,
	}
}

export fn main() void = void;
  • pg::create_slot (temporary or not), drop_slot, log_position.
  • Changes: begun and committed around each transaction's inserted, updated (with the old row's key, or all of it, when the table's replica identity sends it), deleted and truncated; described when a table's columns are told, then relation_of(&s, oid) has them.
  • A row's columns come as text, pg::next_column: void for NULL, pg::unchanged for a large value that stayed as it was.
  • Keepalives are answered as they come; pg::acknowledge tells the server what it may let go, and where the slot starts from next time.
  • pg::end_replication stops streaming; the connection takes replication commands again.
