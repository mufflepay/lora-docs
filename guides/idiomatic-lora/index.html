Guides

Idiomatic Lora & Style Guide

Complete 1,500-line handbook on memory ownership, error reporting, type invariants, performance optimization, concurrency patterns, and codebase formatting conventions (docs/idioms.md).

How to write Lora that is memory safe, robust, fast, reusable and easy to read. The language reference (language.md) says what each feature does; this guide says which to reach for, and why. Every example here compiles and runs; scripts/check-doc-examples.py docs/idioms.md checks them.

The short version:

  1. Let types carry the rules. Owners free themselves, errors can't be dropped, nullable must be checked, pattern types keep values in range. Code that compiles has already passed most reviews.
  2. Borrow by default, own on purpose. Take *T, *const T, str and []T; return ^T, ^str and ^[]T when the caller gets new memory.
  3. Fail loudly, with context. Return errors with ? and a note, give fallbacks with or and ??, and stop with ! only where failing is a bug.
  4. Make the fast path the plain path. Slices instead of copies, capacity up front, pointers into arrays instead of copied elements, generics instead of indirection.
  5. Keep the unsafe edge small. unsafe { ... } around the one expression that needs it, with a comment saying why it is right.

Memory

Own with ^T; never free by hand

An owner, ^T, ^str or ^[]T, frees what it holds when its scope ends, on every path out: a return, a failed ?, a break. There is nothing to forget.

lora 
use strings;

fn greeting(name: str) (^str | nomem) = strings::concat("hello, ", name);

export fn main() (void | nomem) = {
	let g = greeting("ada")?;      // g owns the new string
	assert(g == "hello, ada");
}                                 // freed here, on every path

Avoid release(p), which turns an owner into a raw pointer that you free yourself. Use it only to hand memory to code that frees it itself (C, a runtime structure), and free it with defer on the next line:

lora 
type node = struct { v: int }

export fn main() void = {
	let raw = unsafe { release(alloc(node { v = 1 })!) }
	defer unsafe { free(raw) }               // right after it is made
	raw.v = 2;
	assert(raw.v == 2);
}

Borrow: *T, *const T, str, []T

A function that only reads or changes a value takes a pointer to it, not an owner and not a copy. *const T says it only reads, which is checked. str and []T are views: passing one copies two words, never the data.

lora 
type account = struct { owner: str, cents: i64 }

fn balance(a: *const account) i64 = a.cents;        // reads
fn deposit(a: *account, cents: i64) void = { a.cents += cents; } // changes

export fn main() void = {
	let a = account { owner = "ada", cents = 0 }
	deposit(&a, 250);
	assert(balance(&a) == 250);
}

Take a view, *T.{fields}, when a function needs only some fields. The signature documents what it touches, and callers can lend other fields at the same time:

lora 
type player = struct { name: str, hp: int, score: int }

fn heal(p: *player.{hp}) void = { p.hp += 10; }
fn total(p: *player.{const hp, const score}) int = p.hp + p.score;

export fn main() void = {
	let p = player { name = "kit", hp = 50, score = 7 }
	heal(&p);
	assert(total(&p) == 67);
}

Return what the caller owns; borrow what they gave you

The result type tells the caller who frees what. Returning a slice of an argument is a borrow: it lives as long as the argument. Returning new memory is an owner:

lora 
use strings;

// A view into s: nothing to free, lives as long as s.
fn first_word(s: str) str = match strings::cut(s, ' ') {
	let parts: (str, str) => parts.0,
	void => s,
}

// New memory: the caller owns it.
fn shout(s: str) (^str | nomem) = strings::toupper(s);

export fn main() (void | nomem) = {
	let line = "hello world";
	assert(first_word(line) == "hello");
	let loud = shout(line)?;
	assert(loud == "HELLO WORLD");
}

Don't keep pointers to locals

A pointer to a local is valid only while its function runs. The compiler follows them through calls, so storing one where it outlives the function is an error: allocate instead, or keep a copy of the value.

lora 
let last: nullable *int = null;

fn remember(p: *int) void = { last = p; }

fn f() void = {
	let x = 5;
	remember(&x); // error: A pointer to `x` is kept by remember after it returns, but `x` is gone once f returns.
}

export fn main() void = f();

Copies of a pointer are the same memory

let q = p does not copy what p points to. Free memory once, through one name, and don't use any copy afterwards: the compiler checks this too, through calls that return what they are given.

Errors

Give each module its own error type, with a message

An error type says what failed in words, and carries the values needed to understand it. Callers match on it, and main prints it.

lora 
type over_limit = !struct { user: str, limit: int }
"user {user} is over the limit of {limit}";

fn charge(user: str, n: int) (int | over_limit) = {
	if (n > 5) return over_limit { user = user, limit = 5 }
	return n * 100;
}

export fn main() void = {
	assert(charge("ann", 2) is int);
	assert(charge("ann", 9) is over_limit);
}

? to pass an error up, with a note saying what you were doing

A note turns "file not found" into "file not found, while loading the settings". Add one where the caller's context matters:

lora 
use strconv;

fn port(s: str) (u16 | strconv::invalid_number) = {
	let n = strconv::parse_int(s) ? "reading the port";
	return @u16(n);
}

export fn main() void = {
	assert(port("8080") is u16);
	assert(port("http") is strconv::invalid_number);
}

For a private helper, (T | !) infers the errors from the body, so you don't have to list them. Exported functions write their errors out: they are part of the API.

or and ?? for a fallback

When failing has an obvious answer, say it where the value is made:

lora 
use strconv;

fn find(xs: []int, v: int) ?usize = {
	for (let i = 0z; i < len(xs); i += 1) if (xs[i] == v) return i;
	return void;
}

export fn main() void = {
	let workers = strconv::parse_int("x") or 4;   // an error: a default
	let at = find([1, 2, 3], 9) ?? 0z;             // nothing: a default
	assert(workers == 4 && at == 0);
}

! only where failing is a bug

x! stops the program with the error. Use it where an error means the program is wrong, not the world: in main of a small tool, in tests, or after a check that rules the error out. Everywhere else, return it.

Never hide an error

A _ => arm that swallows errors is warned about. Name the error and do something with it, or let it go up:

lora 
use os;
use strconv;

fn workers(s: str) int = match strconv::parse_int(s) {
	let n: int => n,
	let e: strconv::invalid_number => {
		fmt::eprintfn("ignoring {}: {}", s, e)!;
		yield 4;
	},
}

export fn main() void = {
	assert(workers("8") == 8);
}

Types that keep invariants

Tagged unions for "one of these"

A tagged union holds exactly one of its types, and match must handle each. Prefer it to a struct of flags or a nullable field per case:

lora 
type shape = (circle | rect);
type circle = struct { r: f64 }
type rect = struct { w: f64, h: f64 }

fn area(s: shape) f64 = match s {
	let c: circle => 3.14159 * c.r * c.r,
	let r: rect => r.w * r.h,
}

export fn main() void = {
	assert(area(rect { w = 2.0, h = 3.0 }) == 6.0);
}

Pattern types for ranges

A pattern type is an integer with a range. It costs nothing at run time, and values are checked where they come in, so functions taking it need no checks of their own:

lora 
type percent = u8 is 0..=100;

fn bar(p: percent) usize = @usize(p) / 10;   // no check needed here

export fn main() void = {
	let finished: percent = 70;              // checked when compiling
	let input: u8 = 40;
	let p = @percent(input);                 // checked when running
	assert(bar(finished) == 7 && bar(p) == 4);
}

nullable only when absence is normal

*T is never null. Use nullable *T only where "no value" is part of the meaning, and ?T for optional values. The compiler makes you check either before use.

Enums for closed sets of names

lora 
type level = enum { DEBUG, INFO, WARN }

fn loud(l: level) bool = match l {
	level::WARN => true,
	level::DEBUG | level::INFO => false,
}

export fn main() void = assert(loud(level::WARN) && !loud(level::INFO));

Unit functions

State what a function needs and what it promises with requires and ensures. They are checked on every call, document the API better than prose, and calls with constant arguments are checked when compiling:

lora 
fn clamp(v: int, lo: int, hi: int) int
	requires(lo <= hi)
	ensures(r => lo <= r && r <= hi)
= if (v < lo) lo else if (v > hi) hi else v;

export fn main() void = {
	assert(clamp(15, 0, 10) == 10);
}

Put them on exported functions and interface methods: they are where the caller and the implementation meet. Use assert inside a function for what must hold at a point in it.

Performance

Borrow instead of cloning

The fastest copy is the one you don't make. Pass str and []T down, and clone (strings::clone, alloc(x...)) only when you need an independent value that outlives the original.

Give slices their capacity up front

alloc([], n) makes an empty slice with room for n items, so append never reallocates on the way:

lora 
fn squares(n: usize) (^[]usize | nomem) = {
	let out: ^[]usize = alloc([], n)?;     // one allocation
	for (let i = 0z; i < n; i += 1) append(out, i * i)?;
	return out;
}

export fn main() (void | nomem) = {
	let s = squares(100)?;
	assert(len(s) == 100 && s[9] == 81);
}

Loop over pointers to large elements

for (let x .. xs) copies each element; for (let p &.. xs) borrows it. Use the pointer form for structs, and to change elements in place:

lora 
type particle = struct { x: f64, v: f64, mass: f64, id: u64 }

fn step(ps: []particle, dt: f64) void = {
	for (let p &.. ps) p.x += p.v * dt;    // no copies, in place
}

export fn main() void = {
	let ps = [particle { x = 0.0, v = 2.0, mass = 1.0, id = 1 }];
	step(ps, 0.5);
	assert(ps[0].x == 1.0);
}

Use a region for data that dies together

When many values have the same lifetime, a request, a frame, a parse tree, allocate them from an expanse::region. Making a value is a pointer bump, freeing them all is one call, and they never move. For ten million small nodes it takes about a third of the time of alloc and free.

lora 
use expanse;

type token = struct { text: str, line: int }

fn tokens(r: *expanse::region, src: str)
		([]token | expanse::full | expanse::uncommitted) = {
	let out = expanse::make::[token](r, 2)?;
	out[0] = token { text = expanse::copy(r, src[..2])?, line = 1 }
	out[1] = token { text = expanse::copy(r, src[3..])?, line = 1 }
	return out;
}

export fn main() void = {
	let r = expanse::reserve(expanse::GIB)!;     // no memory yet
	defer expanse::finish(&r);                   // all of it, at once
	let ts = tokens(&r, "hi there")!;
	assert(ts[1].text == "there");
}

Use expanse::array[T] for an array others point into: growing it never moves its elements, where append may move them all.

Keep small buffers on the stack

A fixed array is free to make and free to drop. Use one for scratch space of a known size, and slice it:

lora 
fn digits(n: u64) usize = {
	let buf: [20]u8 = [0...];               // no allocation
	let i = len(buf);
	for (true) {
		i -= 1;
		buf[i] = '0' + @u8(n % 10);
		n /= 10;
		if (n == 0) break;
	}
	return len(buf) - i;
}

export fn main() void = assert(digits(12345) == 5);

Prefer generics to function pointers in hot code

Generics are compiled once per type, so calls inline and nothing is boxed. Interfaces and function pointers are for when the type is chosen at run time.

lora 
fn sum[T: numeric](xs: []T) T = {
	let t = xs[0];
	for (let x .. xs[1..]) t += x;
	return t;
}

export fn main() void = {
	assert(sum([1, 2, 3]) == 6);
	assert(sum([1.5, 2.5]) == 4.0);
}

Compute constants once

Values known when compiling go in def, or @comptime(...) for a call: the program carries the result, not the work.

lora 
fn fib(n: u64) u64 = if (n < 2) n else fib(n - 1) + fib(n - 2);

def FIB_20: u64 = @comptime(fib(20));

export fn main() void = assert(FIB_20 == 6765);

Wrap on purpose, nowhere else

Arithmetic that overflows stops the program. Hashes and random number generators wrap by design: say so with +%, -% and *%.

lora 
use strings;

fn fnv1a(s: str) u64 = {
	let h = 14695981039346656037u64;
	for (let b .. strings::to_bytes(s)) {
		h ^= @u64(b);
		h *%= 1099511628211;
	}
	return h;
}

export fn main() void = assert(fnv1a("a") == 0xaf63dc4c8601ec8c);

Buffer I/O

Each write to a file or socket is a system call. Write through a bufio::writer when writing many small pieces, and flush it once at the end.

Reusable code

Constrain generics by what they use

A constraint says what a type parameter must support, so the function works for every type that fits and fails clearly for one that doesn't:

lora 
fn largest[T: ordered](xs: []T) T = {
	let best = xs[0];
	for (let x .. xs) if (x > best) best = x;
	return best;
}

export fn main() void = {
	assert(largest([3, 9, 4]) == 9);
	assert(largest([2.5, 7.5, 1.0]) == 7.5);
}

Small interfaces

An interface with one or two methods fits many types. Implement it with impl, and take it as a constraint (compiled per type) or as a value (chosen at run time):

lora 
type describer = interface {
	fn describe() str;
}

type cat = struct { name: str }
type car = struct { model: str }

impl describer for cat { fn describe(c: *cat) str = c.name; }
impl describer for car { fn describe(c: *car) str = c.model; }

fn label[T: describer](x: *T) str = x.describe();

export fn main() void = {
	let c = cat { name = "tom" }
	let v = car { model = "mini" }
	assert(label(&c) == "tom" && label(&v) == "mini");
	let any: describer = &v;          // chosen at run time
	assert(any.describe() == "mini");
}

Modules: small, named for what they do

A module is a file of one purpose (strings, json, http). Export the few names callers need, keep helpers private, and put a comment above each exported declaration: editors show it on hover.

Accept the most general input

Take []T rather than [N]T, str rather than ^str, *const T rather than *T, and a view rather than the whole struct. Each makes a function usable from more places at no cost.

Concurrency

Channels to pass data, atomics and shared to share it

Prefer sending values over channels to sharing memory. When memory is shared, make it thread-safe: a thread::atomic, or a value behind a lock with thread::new_shared and thread::with. The compiler reports threads changing other shared data.

lora 
use coro;

export fn main() void = {
	let c = coro::chan_new::[int](0);
	defer coro::chan_finish(&c);
	let pc = &c;
	let total = 0;
	let pt = &total;
	@scope {
		@go {
			for (let i = 1; i <= 3; i += 1) coro::send(pc, i);
			coro::close(pc);
		}
		@go for (let v => coro::recv(pc)) *pt += v; // one writer: the result
	}!;
	assert(total == 6);
}
lora 
use coro;
use thread;

export fn main() void = {
	let hits = thread::atomic { ... }
	let ph = &hits;
	@scope {
		for (let i = 0; i < 4; i += 1) @go thread::add(ph, 1);
	}!;
	assert(thread::load(&hits) == 4);
}

Start work in @all and @scope

Work that is part of what a function does belongs in @all, @first or @scope, which wait for it: it can use the function's locals, its first failure comes back as an error, and the rest is cancelled. Keep coro::detach and thread::spawn for work that lives on its own, and give it what it owns (coro::detach_with, thread::spawn_with).

No mutable globals

A mutable global is shared by every thread and every test. Pass state in parameters instead. If a module must keep global state, guard it and mark it @synchronised.

Unsafe code

Raw pointer conversions, [*]T indexing, and calls to C or to @unsafe functions need unsafe. Keep the block around the one expression that needs it, wrap it in a safe function, and say in a comment why it is right:

lora 
@symbol("abs") fn c_abs(x: i32) i32;

// Absolute value through C; safe: abs reads its argument only.
fn abs(x: i32) i32 = unsafe { c_abs(x) }

export fn main() void = assert(abs(-3) == 3);

The rest of the program then calls abs, which is safe. Mark a function @unsafe only when its callers must make sure of something the compiler can't check, such as a raw pointer pointing to the right type, and say what in its comment. A function that checks its own inputs is safe, however much of its body is unsafe: io::write passes the right length to the system itself, so it is safe, with an unsafe { ... } around the call.

Testing and checking

  • Tests are programs under tests/, run by lora test: each main asserts on results. Test the error paths too, not only the happy one.
  • Leaks: lora run --leaks reports memory never freed, with where it was made.
  • Units: --units=observe reports false conditions without stopping, for trying a change on real input.
  • Warnings are bugs. Fix L0100 (leak) and L0006 (dropped error) warnings; they are certain, not guesses.

Style

The highlights; the style guide has every rule, with correct and incorrect examples.

  • Names are lower_snake_case; constants and enum members are UPPER_CASE. Name things for what they mean, not their type.
  • Small functions with one job, and an expression body (= expr;) when it fits on a line.
  • Comments say why, not what. Put one above every exported declaration.
  • match over chains of if for tagged unions and enums: the compiler checks every case is handled.
  • defer right after acquiring: a free, a close or an unlock sits next to what it undoes.
  • Tabs for indentation; one statement per line.
lora 
use fs;

// Counts the lines of a file; an error says which file and why.
fn count_lines(path: str) (usize | fs::error | nomem) = {
	let data = fs::read_file(path)?;
	let n = 0z;
	for (let b .. data) if (b == '\n') n += 1;
	return n;
}

export fn main() void = {
	assert(count_lines("/nonexistent/file") is fs::error);
}

Checklist

Before calling code done:

  • New memory is held by an owner, or freed by a defer next to it.
  • Functions borrow (*T, *const T, str, []T) unless they keep.
  • No pointer to a local outlives its function.
  • Every error is returned with context, handled, or given a fallback.
  • ! appears only where an error is a bug.
  • Types rule out bad states: tagged unions, enums, pattern types.
  • Exported functions say what they require and ensure, and have a comment.
  • No copies in hot loops: slices, &.. loops, capacity up front.
  • Shared data is atomic, shared, channel-passed or guarded.
  • Every unsafe is one small block with a reason.
  • lora run --leaks is clean, and there are no warnings.

Style guide

The rules for code in the Lora repository, and a good default for any Lora project. Consistent code is quicker to read, review and change.

How to read the rules

The words are used as in RFC 2119:

WordMeaning
mustrequired: code that breaks the rule is wrong
must notforbidden
shouldthe default: break it only for a reason you can state
should notavoid, unless there is a reason you can state
mayallowed, at the writer's choice

Each rule comes with an incorrect example and a correct one. The compiler enforces some rules (the incorrect example is then an error or a warning); the rest are for people.

1. Files and layout

1.1 Indentation must be tabs, one per level. Alignment within a line may use spaces.

Incorrect:

lora 
export fn main() void = {
	let n = 1;
	assert(n == 1);
}

Correct:

lora 
export fn main() void = {
	let n = 1;
	assert(n == 1);
}

1.2 Lines should fit in 80 columns, counting a tab as 8. Break a long signature after a parameter list or before its result, and indent the continuation by two tabs, so it stands apart from the body.

Incorrect:

lora 
fn transfer(from_account: *u64, to_account: *u64, cents: u64, note: str) (void | nomem) = {
	*from_account -= cents;
	*to_account += cents;
}

export fn main() (void | nomem) = {
	let a = 100u64, b = 0u64;
	transfer(&a, &b, 40, "rent")?;
	assert(a == 60 && b == 40);
}

Correct:

lora 
fn transfer(from_account: *u64, to_account: *u64, cents: u64, note: str)
		(void | nomem) = {
	*from_account -= cents;
	*to_account += cents;
}

export fn main() (void | nomem) = {
	let a = 100u64, b = 0u64;
	transfer(&a, &b, 40, "rent")?;
	assert(a == 60 && b == 40);
}

1.3 There must be one statement per line, and every statement ends in ;, a block's closing } included (};).

Incorrect:

lora 
export fn main() void = {
	let a = 1; let b = 2; assert(a + b == 3);
}

Correct:

lora 
export fn main() void = {
	let a = 1;
	let b = 2;
	assert(a + b == 3);
}

1.4 use lines must come first, one module per line, and should be sorted by name.

Incorrect:

lora 
use strings;
use fmt;
use strconv;

export fn main() void = {
	let n = strconv::parse_int("2")!;
	assert(strings::has_prefix("lora", "lo") && n == 2);
	fmt::println("ok")!;
}

Correct:

lora 
use fmt;
use strconv;
use strings;

export fn main() void = {
	let n = strconv::parse_int("2")!;
	assert(strings::has_prefix("lora", "lo") && n == 2);
	fmt::println("ok")!;
}

1.5 Top-level declarations should be separated by one blank line. Lines must not end in whitespace. A file must end in one newline.

1.6 A file should be ordered for its reader: the module comment, use lines, exported types and constants, then exported functions, each followed by the private helpers it uses.

2. Naming

2.1 Functions, variables, parameters, types and modules must be lower_snake_case.

Incorrect:

lora 
type HttpRequest = struct { Path: str }

fn ParsePath(rawPath: str) HttpRequest = HttpRequest { Path = rawPath }

export fn main() void = assert(ParsePath("/").Path == "/");

Correct:

lora 
type http_request = struct { path: str }

fn parse_path(raw_path: str) http_request = http_request { path = raw_path }

export fn main() void = assert(parse_path("/").path == "/");

2.2 Constants (def) and enum members must be UPPER_SNAKE_CASE.

Incorrect:

lora 
def max_retries: int = 3;
type color = enum { red, dark_green }

export fn main() void = assert(max_retries == 3 && color::red != color::dark_green);

Correct:

lora 
def MAX_RETRIES: int = 3;
type color = enum { RED, DARK_GREEN }

export fn main() void = assert(MAX_RETRIES == 3 && color::RED != color::DARK_GREEN);

2.3 Names should not repeat their module. Callers write the module already: strings::concat, not strings::strings_concat; http::request, not http::http_request.

2.4 Names should say what a value means, not its type. Short names (i, n, s, p) may be used in a scope a few lines long.

Incorrect:

lora 
fn f(arr: []int, int_val: int) bool = {
	for (let x .. arr) if (x == int_val) return true;
	return false;
}

export fn main() void = assert(f([1, 2], 2));

Correct:

lora 
fn contains(haystack: []int, needle: int) bool = {
	for (let x .. haystack) if (x == needle) return true;
	return false;
}

export fn main() void = assert(contains([1, 2], 2));

2.5 Booleans should read as a fact: finished, has_header, is_empty. They should not be negative (not_found), which makes !not_found hard to read.

2.6 Error types should be named for what went wrong, as nouns: over_limit, invalid_number, not_found. They should not end in _error unless the module has one general error type, which is then error (io::error, fs::error).

3. Comments

3.1 Every exported declaration must have a comment directly above it. It should start with what the declaration does or is, as a sentence, and name parameters in backticks. Editors show it on hover.

Incorrect:

lora 
export fn clamp(v: int, lo: int, hi: int) int =
	if (v < lo) lo else if (v > hi) hi else v;

export fn main() void = assert(clamp(9, 0, 5) == 5);

Correct:

lora 
// Limits `v` to `lo` ... `hi`, inclusive.
export fn clamp(v: int, lo: int, hi: int) int =
	if (v < lo) lo else if (v > hi) hi else v;

export fn main() void = assert(clamp(9, 0, 5) == 5);

3.2 Comments should say why, not what. The code says what.

Incorrect:

lora 
export fn main() void = {
	let retries = 0;
	retries += 1; // add one to retries
	assert(retries == 1);
}

Correct:

lora 
export fn main() void = {
	let retries = 0;
	retries += 1; // the first attempt counts as a retry for the log
	assert(retries == 1);
}

3.3 Code must not be left commented out. Delete it: version control remembers.

3.4 A file should start with a comment saying what the module is for, with a short example when it helps.

4. Functions

4.1 A function should do one thing, and fit on one screen (about 40 lines). Split it where you would add a comment naming a step.

4.2 A function whose body is one expression should be written = expr;, without a block.

Incorrect:

lora 
fn square(n: int) int = {
	return n * n;
}

export fn main() void = assert(square(3) == 9);

Correct:

lora 
fn square(n: int) int = n * n;

export fn main() void = assert(square(3) == 9);

4.3 Parameters should go from what is acted on to how: the target first (the receiver, the buffer written to), then inputs, then options. Related functions must order the same parameters the same way.

4.4 Parameters should be as general as the function allows: []T over [N]T, str over ^str, *const T over *T, a view over the whole struct.

Incorrect:

lora 
fn total(xs: [3]int) int = xs[0] + xs[1] + xs[2];

export fn main() void = assert(total([1, 2, 3]) == 6);

Correct:

lora 
fn total(xs: []int) int = {
	let t = 0;
	for (let x .. xs) t += x;
	return t;
}

export fn main() void = assert(total([1, 2, 3]) == 6 && total([4]) == 4);

4.5 Only what callers need should be exported. Helpers stay private, so they can change freely.

4.6 A boolean parameter should not change what a function does. Two functions, or an enum, read better at the call.

Incorrect:

lora 
fn round(x: f64, up: bool) int = if (up) @int(x) + 1 else @int(x);

export fn main() void = assert(round(2.5, true) == 3); // true what?

Correct:

lora 
fn round_up(x: f64) int = @int(x) + 1;
fn round_down(x: f64) int = @int(x);

export fn main() void = assert(round_up(2.5) == 3 && round_down(2.5) == 2);

5. Bindings and values

5.1 A binding should be declared where it is first needed, not at the top of the function.

5.2 A value that never changes should be const; a binding that changes must be let. The compiler checks const.

Incorrect:

lora 
export fn main() void = {
	const total = 0;
	total += 1; // error: Cannot change this
}

Correct:

lora 
export fn main() void = {
	const limit = 10;
	let total = 0;
	total += limit;
	assert(total == 10);
}

5.3 Programs should not have mutable globals. Pass state in parameters. A module that must keep global state must guard it and mark it @synchronised.

5.4 Literals should carry their type when it is not obvious: 0z for a usize, 1u64, 0.5f32.

Incorrect:

lora 
export fn main() void = {
	let count: usize = 0;
	for (let i: usize = 0; i < 3; i += 1) count += 1;
	assert(count == 3);
}

Correct:

lora 
export fn main() void = {
	let count = 0z;
	for (let i = 0z; i < 3; i += 1) count += 1;
	assert(count == 3);
}

5.5 Strings should be built with $"...", not chains of concat.

Incorrect:

lora 
use strings;

export fn main() (void | nomem) = {
	let name = "ada";
	let a = strings::concat("hello, ", name)?;
	let msg = strings::concat(a, "!")?;
	assert(msg == "hello, ada!");
}

Correct:

lora 
export fn main() void = {
	let name = "ada";
	let msg = $"hello, {name}!";
	assert(msg == "hello, ada!");
}

6. Control flow

6.1 Functions should return early for errors and special cases, so the main path is not nested.

Incorrect:

lora 
fn ratio(a: int, b: int) int = {
	if (b != 0) {
		if (a >= 0) {
			return a / b;
		} else {
			return 0;
		}
	} else {
		return 0;
	}
}

export fn main() void = assert(ratio(6, 3) == 2 && ratio(1, 0) == 0);

Correct:

lora 
fn ratio(a: int, b: int) int = {
	if (b == 0 || a < 0) return 0;
	return a / b;
}

export fn main() void = assert(ratio(6, 3) == 2 && ratio(1, 0) == 0);

6.2 An if or for body may go on the same line without braces when it is one short statement. A body that spans lines must have braces.

6.3 match should be used for tagged unions and enums, not is chains: it checks that every case is handled, and new cases become compile errors instead of silent misses.

Incorrect:

lora 
type token = (int | str | void);

fn describe(t: token) str = {
	if (t is int) return "number";
	if (t is str) return "word";
	return "end";
}

export fn main() void = assert(describe(1) == "number");

Correct:

lora 
type token = (int | str | void);

fn describe(t: token) str = match t {
	int => "number",
	str => "word",
	void => "end",
}

export fn main() void = assert(describe(1) == "number");

6.4 Loops should iterate values, not indices, unless the index is needed.

Incorrect:

lora 
export fn main() void = {
	let xs = [1, 2, 3];
	let t = 0;
	for (let i = 0z; i < len(xs); i += 1) t += xs[i];
	assert(t == 6);
}

Correct:

lora 
export fn main() void = {
	let xs = [1, 2, 3];
	let t = 0;
	for (let x .. xs) t += x;
	assert(t == 6);
}

7. Errors

7.1 Errors must not be ignored. The compiler rejects a dropped error.

Incorrect:

lora 
use strconv;

export fn main() void = {
	strconv::parse_int("x"); // error: Cannot ignore an error here
}

Correct:

lora 
use strconv;

export fn main() void = {
	let n = strconv::parse_int("x") or 0;
	assert(n == 0);
}

7.2 A match must not hide errors behind _ =>. Name them.

Incorrect:

lora 
use strconv;

fn workers(s: str) int = match strconv::parse_int(s) {
	let n: int => n,
	_ => 4, // error: This `_ =>` arm drops a strconv::invalid_number error, and goes on
}

export fn main() void = assert(workers("x") == 4);

Correct:

lora 
use strconv;

fn workers(s: str) int = match strconv::parse_int(s) {
	let n: int => n,
	strconv::invalid_number => 4,
}

export fn main() void = assert(workers("x") == 4);

7.3 ! should be used only where an error is a bug: in tests, in a small tool's main, or after a check that rules the error out. Library code must return its errors.

Incorrect:

lora 
use strconv;

// Parses a port number.
export fn port(s: str) int = strconv::parse_int(s)!;

export fn main() void = assert(port("80") == 80);

Correct:

lora 
use strconv;

// Parses a port number.
export fn port(s: str) (int | strconv::invalid_number) = strconv::parse_int(s)?;

export fn main() void = assert(port("80") as int == 80);

7.4 An error message must be lower case, without a final period, and say what failed and why: cannot open {path}: {errno}. It is read inside other messages.

7.5 A note on ? should say what the code was doing, as an -ing phrase: ? "reading the settings".

8. Memory

8.1 New memory must have an owner, or be freed by a defer on the line after it is made. The compiler warns about memory never freed.

Incorrect:

lora 
use strings;

fn greet(name: str) void = {
	let s = unsafe { release(strings::concat("hi ", name)!) } // error: `s` holds the memory allocated on line 4, and nothing frees it: it leaks when its block ends
	assert(len(s) > 0);
}

export fn main() void = greet("x");

Correct:

lora 
use strings;

fn greet(name: str) void = {
	let s = strings::concat("hi ", name)!;   // an owner: freed with s
	assert(len(s) > 0);
}

export fn main() void = greet("x");

8.2 A function should borrow unless it keeps. It must not take an owner (^T) only to read it.

Incorrect:

lora 
type doc = struct { title: str }

fn title_len(d: ^doc) usize = len(d.title);

export fn main() void = {
	let d = alloc(doc { title = "lora" })!;
	assert(title_len(d) == 4);
}

Correct:

lora 
type doc = struct { title: str }

fn title_len(d: *const doc) usize = len(d.title);

export fn main() void = {
	let d = alloc(doc { title = "lora" })!;
	assert(title_len(&d) == 4);
}

8.3 Clones should be rare and deliberate. Each strings::clone or copying alloc should be needed for a value that outlives its source.

9. Types

9.1 A type should make bad states impossible: a tagged union for "one of", an enum for a closed set of names, a pattern type for a range, nullable only where absence is normal.

Incorrect:

lora 
type conn = struct {
	connected: bool,
	fd: int,          // meaningless unless connected
}

export fn main() void = {
	let c = conn { connected = false, fd = -1 }
	assert(!c.connected);
}

Correct:

lora 
type open = struct { fd: int }
type closed = void;
type conn = (open | closed);

export fn main() void = {
	let c: conn = closed;
	assert(c is closed);
}

9.2 Struct fields should be ordered by meaning, not by size. A struct may give fields defaults (port: u16 = 80) for values most callers don't set.

10. Unsafe code

10.1 Unsafe operations must be inside the smallest unsafe { ... } that holds them, with a comment saying why they are right. @unsafe on a function is for what its callers must make sure of, not for what its body does.

Incorrect:

lora 
@symbol("abs") fn c_abs(x: i32) i32;

@unsafe fn distance(a: i32, b: i32) i32 = {
	let d = a - b;
	let r = c_abs(d);
	return r;
}

// every caller now needs unsafe, for nothing it must make sure of
export fn main() void = assert(unsafe { distance(2, 5) } == 3);

Correct:

lora 
@symbol("abs") fn c_abs(x: i32) i32;

fn distance(a: i32, b: i32) i32 = {
	let d = a - b;
	// abs only reads its argument
	return unsafe { c_abs(d) }
}

export fn main() void = assert(distance(2, 5) == 3);

11. Concurrency

11.1 Concurrent work is waited for before the locals it uses go away: @all, @first and @scope always do; thread::spawn and coro::detach take only what they own.

11.2 Data shared between running threads must be thread-safe: a channel, a thread::atomic, a thread::new_shared value, or code between thread::lock and thread::unlock. The compiler checks this.

Incorrect:

lora 
use thread;

let hits = 0;

export fn main() void = {
	let t = thread::spawn(fn() void = { hits += 1; })!; // error: `hits` is changed by a thread
	thread::join(t);
}

Correct:

lora 
use coro;
use thread;

export fn main() void = {
	let hits = thread::atomic { ... }
	let ph = &hits;
	@scope { @go thread::add(ph, 1); }!;
	assert(thread::load(&hits) == 1);
}

12. Tests

12.1 Every exported function should be tested, its error paths included, by a program under tests/ that asserts on results.

12.2 A test must not depend on another test's state, or on the order tests run in.

12.3 Tests should run clean under lora run --leaks.

12.4 A test should assert on values, not print them: a printed value is checked by nobody.

Incorrect:

lora 
fn double(n: int) int = n * 2;

export fn main() void = {
	fmt::printfn("{}", double(2))!;
}

Correct:

lora 
fn double(n: int) int = n * 2;

export fn main() void = {
	assert(double(2) == 4);
	assert(double(-3) == -6);
}
