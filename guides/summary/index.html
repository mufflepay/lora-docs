Stdlib & Compiler Architecture Notes

Deep engineering design notes across HTTP/1.1, HTTP/2, TLS 1.3, DNS, @sql, regions, scratch allocators, and LSP type inference (docs/summary.md).

Each section below sums up one piece of work, in the order it was done: what it added or changed, what it found and fixed on the way, and how it is tested. The networking libraries came first, in phases: streams, then addresses, sockets, names, URLs and HTTP, then the server and client on top, compression, mail, and TLS for servers. Every change after them gets a section here too.

Every piece of work ends with the whole test suite passing: the library tests, the compiler's checks, error messages, leak checks, the language server, the fuzzers, the tree-sitter grammar, the examples and the stack frame estimates.

Phase 1 — io: readers and writers

Commit 67eedb4.

  • Interfaces every stream shares: reader, writer, closer, seeker, reader_at, writer_at and byte_reader, the interfaces made of them, and one error set, io::failure, that every stream returns.
  • Helpers: copy, limit, join, tee and section streams. Writers take several buffers in one call (write_vec, a single system call on files and sockets). There is also a fixed-size writer, take and reserve.
  • bufio, rebuilt over any reader or writer: lines, slices, runes, peek, take, and a scanner with split functions. A line longer than the buffer is too_large, never cut.
  • Everything speaks it:
    • fs::open and fs::create give an owned file that closes when it is dropped.
    • Files, sockets and TLS connections implement the interfaces.
    • json, csv, xml and pack read and write any stream.
    • fmt::fprintf prints to any writer.
  • Compiler fixes:
    • An interface value converts to any interface it embeds, not only the first.
    • A type with an impl of each part implements the interface made of them.
    • Default methods of exported impls link from other modules.
    • A default parameter may be a function's address.
    • An owned temporary in a loop is made once (it caused a false double free).

Phase 2 — netip: addresses as values

Commit 57feabe.

  • Small values that allocate nothing: IPv4 and IPv6 addresses (with their zones), an address with a port, prefixes, and MAC addresses.
  • Parsing: strict, with errors that name the byte at fault.
  • Writing: as RFC 5952 has it.
  • Classes: private, loopback, multicast, link-local and global unicast.
  • Operations: stepping, comparing, and hashing for maps.
  • Encodings: json, xml, csv and pack carry them through their text and binary forms.
  • Tests: checked against a reference implementation on 20,606 inputs. The few differences are deliberate:
    • a port with a leading zero is refused, so each value has one text;
    • a zone is at most 15 bytes.

Phase 3 — net: TCP, UDP and local sockets

Commits 770d573 and 327d0c0.

  • Connections:
    • Dial and listen over TCP (IPv4 and IPv6) and local sockets, and accept.
    • Datagrams over UDP and local sockets.
    • Socket pairs, passing descriptors, sendfile, writev, half-close.
    • Socket options: no-delay, keep-alive, linger, buffer sizes, reuse, v6-only.
    • The system's interfaces and their addresses.
  • Waiting: sockets are non-blocking. In a coroutine they wait on kqueue so other coroutines run; outside one they poll.
  • Deadlines: every read, write, accept and dial can have one. A cancelled coroutine's wait ends at once.
  • Errors: writing to a peer that has gone is EPIPE, never a signal. Errors name the operation and the address.
  • dial_host: looks a name up and tries its IPv6 and IPv4 addresses by turns.
  • Compiler:
    • @go f(x) moves an owned x into the child, so a server gives each connection its own coroutine.
    • The race checker tells pointers to two different locals apart.
  • Stack use:
    • Recursion across the library is now loops, or bounded with @depth, so programs that use coroutines have a known stack bound.
    • Readers of untrusted input fail with their own error first.
    • The vendored QBE shares stack slots, which made large frames up to 13 times smaller.
    • scripts/test-stack-frames.py checks that no estimate is below the real frame.

Phase 4 — dns: a resolver of its own

Commits cb33564, f46cc2b, 40fbb8e and f7f6265.

  • Where it asks: the servers /etc/resolv.conf names, after /etc/hosts.
    • Queries go over UDP, and over TCP when the answer is cut short.
    • Each server is asked in turn, a few times, each within a timeout.
    • Queries use EDNS (dropped for a server that doesn't know it) and random ids. An answer must be to the question asked.
    • Short names are tried in the search domains.
    • .local names, and everything when there is no configuration, are asked of the system.
  • Lookups:
    • hosts, sorted as RFC 6724 asks;
    • reverse names and CNAME;
    • MX by preference, and SRV by priority and weight;
    • TXT, NS, and whole answers of any kind.
    • Errors say the name, why it failed, and the last server asked.
  • Messages: decoded safely (compressed names may only point backward, and impossible counts are refused first), and written with a builder.
  • Bugs fixed on the way:
    • Lexer: string tokens shared one buffer, so a literal after a ? could compile as another string's bytes.
    • Stack guards: a frame larger than the guard page could step over it. QBE now enters large frames a page at a time, on arm64, amd64 and rv64.
    • Stack overflows off the main thread died silently. Now they're reported on every stack, naming the coroutine or thread.
    • rv64: a copy-elimination bug.
    • tree-sitter: a string starting with // was read as a comment.

Phase 5 — url and textproto

Commit dade5bf.

  • url parses URLs and relative references strictly, as RFC 3986 has them, with errors that say what is wrong and at which byte.

    • A URL owns one copy of its text, and its parts are views of it.
    • resolve follows section 5; every example of 5.4 is tested.
    • There is also build, join_path, remove_dots, redacted and request_target, escaping and unescaping for each part, and query values (encoded with their keys sorted).

  • textproto reads what HTTP, SMTP and mail share:

    • lines, and lines folded across several;
    • headers with canonical keys, looked up in any case and bounded by limits;
    • bodies ended by a line of .;
    • three-digit replies.

    It writes headers so that no value can start a field of its own.

Phase 6 — http: HTTP/1.1 messages

Commit 3103db3.

  • Reading: requests and responses are read from a buffered reader as RFC 9110 and 9112 have them.

    • Every target form; keep-alive by version and Connection; 1xx responses; no body for HEAD, 204 and 304.
    • Bodies are readers: of a length, chunked with trailers, or to the end.

  • Strictness: reading refuses anything that would let two readers see different messages:

    • Content-Length together with Transfer-Encoding, or lengths that disagree;
    • codings other than chunked;
    • a missing or repeated Host;
    • bad chunk sizes or line ends;
    • versions other than 1.0 and 1.1.

    The error carries the status to answer with.

  • Writing: request and response heads, a chunked writer with trailers, status texts, and HTTP dates in all three forms.

  • Bug fixed: reading a header waited for a byte after the blank line, which hung every server on its first request.

Phase 7 — http server

Commits 6be8813 and 645d8c2.

  • Serving: http::serve answers each connection in its own coroutine, one request after another, through a handler (an interface, or a plain function).
  • The responder buffers:
    • A response that fits gets its Content-Length; a larger one goes in chunks. A length the handler sets is kept to.
    • It adds Date, and sends no body for HEAD, 1xx, 204 and 304.
    • It answers 100 Continue when the handler first reads the body.
    • A body the handler leaves unread is drained, so the next request can be read.
  • Time limits and stopping: limits for the header, the body and writing. A message that isn't HTTP gets its status. serve stops when its flag is set, after each connection's current response.
  • No unsafe code: the handler call no longer needs it. The compiler now knows that flat values (no pointers, slices or strings) and its own method tables don't move when changed.
  • Compiler fixes:
    • A lambda read a module's function rather than a local of the same name.
    • The race checker compared a child's captures with themselves.
  • coro fix: a scope's helper thread was detached, and the leak check sometimes saw 32 bytes left at exit. It's joined now.

Phase 8 — routing, forms, cookies and binding

Commit de78f2f.

  • Router: routes by method and path.
    • Wildcards: {name}, {name...} and {$}.
    • The most specific route wins.
    • 405 with Allow for other methods; HEAD is served by GET.
    • Paths that aren't clean are redirected (301, or 308 to keep the method).
    • Patterns that clash are refused.
  • Forms: from urlencoded bodies and the query. Multipart bodies are read part by part, each part streamed.
  • Cookies: read from requests. Set-Cookie checks the name, value, path and domain, and that SameSite=None or Partitioned come with Secure.
  • bind: http::bind[T] fills a struct from @path, @query, @header, @form and @body (JSON) tags. Its errors name where and why.

Phase 9 — file server

Commit 5b405dd.

  • What it sends:
    • a type from the name or the first bytes, with nosniff;
    • Last-Modified and a strong ETag;
    • Cache-Control;
    • the bytes by sendfile.
  • Conditions: answered with 304 or 412, in the order RFC 9110 gives.
  • Ranges:
    • one range is 206, several are multipart/byteranges, and one past the end is 416;
    • malformed or abusive ranges get the whole file;
    • If-Range is honored.
  • Directories: served by their index file or a listing with names escaped. A directory without its trailing / is redirected. A prefix can be stripped for mounting.
  • Safety: each part of a path is opened inside the one before it without following links (unless allowed, and then only to inside the root). So .., an escaped / or a link swapped in can't lead out. Hidden names are 404 unless allowed.
  • fs: stat, lstat, read_dir, open_dir, open_in, real_path and symlink.

Phase 10 — http client

Commits ec576c5 and b9bf915.

  • Requests: over HTTP and HTTPS, verifying certificates against the system's roots or your own.
  • Connections: a few are kept open to each server and reused. One the server closed in the meantime is detected, and the request goes again on a new one.
  • Time limit: one, covering connecting, sending and the response.
  • Redirects, as RFC 9110 has them:
    • 301, 302 and 303 turn a POST into a GET without its body;
    • 307 and 308 keep both;
    • a redirect to another server drops Authorization and Cookie.
  • Reading: get, post and fetch read the whole response; send streams the body; release gives the connection back.
  • Sharing: the pool is guarded, so coroutines can share one client.
  • Also added: TLS deadlines, and thread::lock_shared.
  • Compiler fix: a temporary lent to a call could be freed while the result still viewed it; a request's URL was freed under it.

Phase 11 — compression, gzip in HTTP, testing handlers, proxy

Commit 7ce1ce8.

  • compress: reads and writes DEFLATE, gzip and zlib.
    • Every checksum is checked when reading: gzip's CRC-32 and length, zlib's Adler-32.
    • A gzip file holding several streams reads as one.
    • Levels 0–9, each block written in whichever of three encodings comes out smallest.
    • A stream flushed partway can be read up to the flush.
    • Output stays within about 1% of zlib's size.
  • hash: CRC-32 and Adler-32.
  • http:
    • Server: with gzip on, text responses are gzipped for clients that accept it. Short, non-text, partial and already-encoded responses go as they are.
    • Client: fetch asks for gzip and gives the body back decompressed.
    • Testing: record and record_raw run a handler in memory.
    • Proxy: proxy forwards requests to another server, with X-Forwarded-* headers and connection headers removed. It answers 502 when the server can't be reached and 504 when it doesn't answer in time.
  • Bugs fixed:
    • Compiler: append(a, b...) leaked b.
    • QBE: macOS arm64 refused addresses just before a symbol.
    • Lookup tables: made const, as a large def table was rebuilt at every lookup.
    • Stack: the decompression window moved to the heap so client calls fit in a coroutine's stack.

Phase 12 — smtp: sending mail

Commit baf00c2.

  • Connecting: dial (port 587), dial_tls (465), or new_client over a connection you already have.

  • Commands: one at a time, each reply awaited within a time limit:

    • EHLO, learning the server's extensions, with a HELO fallback for old servers;
    • STARTTLS, MAIL, RCPT, DATA (from bytes or a reader), RSET, NOOP, VRFY and QUIT.

  • Login: PLAIN, LOGIN, CRAM-MD5 and XOAUTH2. A password or token goes only over TLS or to this machine.

  • Safety:

    • Addresses with line breaks or angle brackets are refused, so they can't inject commands.
    • Bytes that arrive between STARTTLS and the handshake are refused.

  • Refusals: carry the server's code and text. is_temporary tells a 4xx from a 5xx.

  • Sending in one call: send_mail, and send_message (which also composes).

  • Composing:

    • Date, Message-ID and the usual headers;
    • subjects and names that aren't ASCII, encoded;
    • quoted-printable bodies;
    • text and HTML as alternatives;
    • attachments.

    A header value with a line break is refused, and Bcc is never written.

  • Tests: a scripted SMTP server on loopback. They include RFC 2195's worked CRAM-MD5 example.

Phase 13, part 1 — TLS servers and HTTPS

Commit ad63690.

  • TLS 1.3 server: tls::server and tls::server_on.
    • Key exchange: X25519, P-256 or P-384. If the client sent no share the server takes, a HelloRetryRequest asks for one.
    • Cipher suites: all three of TLS 1.3's.
    • Certificates: ECDSA or RSA. The server signs with ECDSA or RSA-PSS, as the client accepts.
    • Protocols: chosen by ALPN in the server's order of preference.
    • The client's side: server_name gives the name the client asked for (SNI).
    • Refusals: each failure goes to the client as the alert RFC 8446 names: protocol version, handshake failure, no application protocol, certificate required, and so on.
    • TLS 1.2: clients that speak only TLS 1.2 or older are refused.
  • Client certificates: a server can ask for one and take a connection without it, or require it. A certificate must lead to the server's roots and be meant for clients. peer_certificate gives it to the server. x509 gains verify_client and knows the clientAuth key usage.
  • Deadlines: server_on and client_on take the socket instead of its descriptor, and keep to the socket's read and write deadlines as they are each time they wait.
  • Clients: alpn takes several protocols, best first ("h2,http/1.1").
  • Read-only settings: certificates, keys and root pools are now *const and []const in every config (tls, http, smtp, pg), so coroutines can share them.
  • HTTPS: http::server gains a tls field.
    • The handshake must finish within the header time limit.
    • req.secure says the request came over TLS, and a proxy sends X-Forwarded-Proto: https for it.
  • Compiler fixes found on the way:
    • Race checker: what an owned slice or pointer holds is as read-only as its owner when reached through *const. The checker also knows that memory an owned slice holds is inside no other type's value. Before, sharing a *const root pool beside a listener was refused.
    • Loans checker: a *const pointer to data that nothing can change (no mutable pointer, no thread-safe type, no interface inside) stays good across calls that change what holds it. Before, setting a client's roots made every later request an error.
    • Loans checker: a function's address stored in a struct no longer makes the struct look as if it lived forever. Before, a router given a function first refused any handler that viewed a local afterwards.
  • Tests:
    • TLS server (λtests/tls_server.lora):
      • ECDSA and RSA certificates, with 100 KB echoed both ways;
      • ALPN chosen by the server's preference, and refused when nothing is in common;
      • an untrusted root;
      • client certificates required, requested, missing, and of the wrong kind.
    • HTTPS (λtests/https.lora): the client trusts the server's root, keeps the connection and uses it again, the proxy says https, and a client that trusts another root is refused.
    • Interop with OpenSSL 4.1:
      • each of the three cipher suites;
      • P-384 key shares, and a HelloRetryRequest for X25519;
      • an RSA certificate;
      • ALPN choosing h2;
      • a client certificate, and the alerts for TLS 1.2 and for a missing client certificate.
    • curl over HTTPS: a 1 MB download and a 300 KB upload.
    • test-errors: a regression case for each compiler fix.

Phase 13, part 2 — HTTP/2

Commit 6036fc8.

  • hpack: a new module for HTTP/2's header compression (RFC 7541).
    • Decoder: keeps the dynamic table the peer builds, with eviction, and decodes Huffman strings. It refuses blocks it can't read safely: an index past the tables, bad Huffman, a table size that's too large or out of place, integers that overflow, and lists over their limit.
    • Encoder: uses the static table and Huffman codes but keeps no dynamic table, which it says in its first block. Sensitive fields (cookies, authorization) are marked never to be indexed.
  • HTTP/2 server:
    • When: spoken when TLS chooses h2 by ALPN, or over plain TCP when the client starts with HTTP/2's preface. HTTP/1.1 is still answered on the same port.
    • Streams: answered one at a time, in arrival order, up to 100 open. Frames for the other streams keep being read while one is answered, so large uploads and downloads can't deadlock on flow control.
    • Frames: windows are kept both ways. PING and SETTINGS are answered, padding and priority are read, and CONTINUATION frames rejoin header blocks.
    • Errors: protocol violations end the connection with GOAWAY and the right code. A refused or abandoned stream gets RST_STREAM.
    • Handlers: unchanged. req.major is 2, and the responder sends HEADERS and DATA frames, with gzip working as before.
  • HTTP/2 client:
    • It offers h2 by ALPN over HTTPS (turn it off with http2 = false).
    • Each request goes on a new stream of a pooled connection. The connection keeps its HPACK table and windows, and the bytes it read ahead, between requests.
    • A response body read only partway ends its stream with RST_STREAM, and the connection goes back to the pool.
    • response.major and fetched.major say which version was spoken.
  • Smaller stack: the exchange's 8 KiB header buffer moved to the heap and gzip decompression to its own function. A request's stack estimate dropped from 240 KB to 216 KB, which leaves room for HTTPS requests in coroutines.
  • Bug fixed on the way: telling HTTP/2's preface from HTTP/1 waited for 24 bytes, so a request shorter than that hung. The server now reads only as far as the bytes still match the preface: two bytes for any HTTP/1 request.
  • Compiler fixes found on the way (loans checker):
    • &x on a local that owns nothing and has no union holding pointers is now a pointer to the variable itself. Changing x doesn't move it, so such pointers stay good across calls that change it. Before, a server couldn't keep a buffered reader across a handler call.
    • The compiler's method tables, like functions, are never taken as places a view is stored in. Before, a reader made from an interface looked as if it outlived everything.
  • Tests:
    • hpack (λtests/hpack.lora):
      • every example of RFC 7541 C.4 and C.6, including eviction from a 256-byte table;
      • round trips through the encoder;
      • each kind of malformed block.
    • HTTP/2 (λtests/http2.lora):
      • the Lora client and server over TLS: GET, HEAD, a 300 KB POST, a 1 MB gzipped download, a streamed body with a flush, 404, connection reuse, a stream given up partway, and a client limited to HTTP/1.1;
      • frames written by hand over plain TCP: PING answered, SETTINGS acknowledged, GOAWAY with the right code for a frame that's too large, DATA on stream 0, a bad SETTINGS size and an unreadable header block;
      • a request made by hand answered in one HEADERS and one DATA frame.
    • Interop:
      • Go's HTTP/2 client: 50 requests at once over one connection, mixing 100 KB uploads and 1 MB downloads, all correct.
      • curl over TLS, and over plain TCP with prior knowledge.
      • The Lora client against Go's HTTP/2 server: a 3 MB download, a 200 KB upload, a redirect and a 404.
  • Not yet:
    • Streams of one connection are answered one after another, not at the same time.
    • There is no server push.
    • There is no upgrade from HTTP/1.1 to plaintext HTTP/2 (the h2c upgrade). Prior knowledge works.

HTTP/2 streams at once, server push, and the h2c upgrade

Commit 21fe852.

  • Streams at the same time: each HTTP/2 stream's request is now answered by the handler in its own coroutine. One slow handler no longer holds up the others: ten requests that each sleep 300 ms finish in 0.31 s on one connection.
    • The connection's coroutine alone reads and writes the connection. Handlers send it what they want (their head, their data, the body read so far) over channels and wait for its answer.
    • A small watcher coroutine says when the socket can be read. Data already decrypted and waiting inside TLS is read first (tls::pending).
    • A handler's write returns once flow control has let its data out, so a slow client slows only that handler.
  • Server push: http::push(w, path) sends a PUSH_PROMISE for a GET of path. The same handler then answers it beside the page, as if it had been asked for. It returns no_push when the client has turned pushes off, or over HTTP/1.
  • The h2c upgrade: a plain HTTP/1.1 request with Upgrade: h2c and HTTP2-Settings (and no body) gets 101 Switching Protocols. The connection goes on as HTTP/2, the request answered as stream 1 with the settings it brought. server.h2c turns this off.
  • Client: client.h2c speaks HTTP/2 to http:// URLs from the first byte, for servers known to speak it.
  • coro: channels move owned values. Channels copied their values in and out, so a value owning memory couldn't be sent: it would have been freed twice, or never.
    • A send now moves its value in (boxing it first, then freeing the box without what it held).
    • A receive owns what it gets.
    • Values still in a channel are dropped with it, and a send to a closed channel drops its value.
    • select's receive drops what its variable held before.
    • send_case refuses, while compiling, a value that owns memory, since it couldn't say whether it gave the value away.
  • Compiler bugs found on the way:
    • Leak: an owned value taken out of a union with as and used in place, as in assert(f() as ^str == "y"), was never freed. It's now dropped like any owned temporary.
    • Crash: unpacking a tuple of nothing, such as let (a, b) = @all(f(), g()) where both return only void, crashed the compiler. It now gets an empty slot.
    • Both have regression cases in λtests/owner_frees.lora.

@sql keeps rows with no into: a region of the block's own

Commit 919fdd8.

  • The change: a query that keeps rows (from, first, returning, or SQL text read as a struct) no longer needs into = &r. pool: values reached by generation-checked handles

Commit 2095dc8.

  • The change: a new pool module. pool[T] keeps values of one type in slots; put gives a handle[T] (slot number, generation, and the pool's id) instead of a pointer. Removing a value moves its slot's generation on, so its handles find nothing (get gives null) rather than whatever takes the slot later. Handles of another pool find nothing too, and the zero handle stands for none.
    • API: new, put, get, contains, take (moves a value out), remove (drops it), count, clear, finish, iter and next.
    • Holds owners, leak free: each slot holds (T | void), so removing a value, clearing the pool or dropping it drops what it holds, by the language's own drop rules; no custom drop code.
    • Cost: constant-time put, get, take and remove; removed slots are reused through a free list. A slot whose generation would run out is retired.
  • Why: things that point at each other (graphs, trees with parent links, entities) otherwise need rc (and risk cycles) or unsafe. A handle is a plain value that can't dangle.
  • Compiler bugs the pool's tests found, fixed:
    • A crash: the ownership check of for (let (a, b) => next(&it)) read the tagged union next gives as if it were a tuple. It now finds the union's tuple member.
    • Writes through a stale view went unchecked: L0609 caught reading through a view after its source grew, but not writing: *x = 5 or v[0] += 1 after append compiled, and wrote into freed memory. The target of an assignment now uses what it is reached through.
    • Growth through a pointer to an owner: let p = &b; append(p, x) didn't make views of b's elements stale. It does now.
    • Precision, so the stricter check stays usable: growing a place reached through a pointer (append(s.out, x), or a call given &s.fields) no longer counts as moving that pointer itself: s still points where it did, and only views of what moved go stale. Without this, the write check flagged correct code in http.
  • Tests: λtests/pool.lora (with leak checks): stale handles, slot reuse, take, owners removed, cleared and dropped, handles of another pool, iteration, a tree with parent links, a thousand slots reused. test-errors: a pool pointer used after a put is L0609; unpacking an iterator's tuple of owners compiles; seven stale-view cases, five refused and two allowed. docs/stdlib.md has a pool section with an example that runs; docs/errors.md says L0609 covers writes.

Regions that size themselves, a region per request, and region views checked

Commit f72ce78.

  • expanse::auto(): a region that chooses no size. It reserves nothing until something is put in it, then a tebibyte of address space (expanse::AUTO), which takes no memory until pages are used, and grows into it in place. A block, a coroutine's body or a request owns one for as long as it lives. sql::auto_region() is now this.
  • http::region(req): the request's region, public: memory that lives as long as the request is served, freed all at once after it. The HTTP/1.1 server keeps one per connection, lent to each request in turn (request.lent) and emptied after it, so a warm connection's requests cost no system call. A request with none lent (HTTP/2 streams, record) makes its own on first use. Binding uses it too.
  • Safety holes found and fixed on the way:
    • What a region held wasn't tied to it. expanse builds its pointers from addresses kept as numbers, so the checker saw no link: text from expanse::copy could be stored in a global, returned past its region, or used after finish (an unmapped page). Functions can now say, by parameter name, what their result views and what they change: @views(r) and @changes(r), kept in typedefs (for generics too). take, new, make, copy, push and items view their region; reset, rewind, shrink, finish, pop and the array's clear and finish change it. A region keeps its mapping as a pointer too, so it is no longer taken for a plain value that nothing can move.
    • A function value could keep its arguments. Calls through function pointers are taken not to keep what they are given, but nothing checked the function: &keep, or a handler saving req.target in a global, compiled, and read freed memory at run time. Making such a function a value is now an error (L0608), naming the parameter kept.
    • Precision, so the stricter checks fit real code: a function whose result is reached through a parameter records only that (not that it views the parameter itself); an owner moved into a struct or tuple takes views of what it owns with it, when moving it moves no memory (heap owners and regions), as json::document holds its region and the values in it; filling an empty auto region on first use sets its fields rather than replacing it, so taking more ends nothing taken before.
  • Making the region checks fit real code, as found by the library's own tests:
    • @changes(r) is its own effect ("moves"), carried in typedefs as @moves(n) and passed on to callers, and honoured even for a value that looks plain: a region's fields are numbers, so ordinary changes to it are still taken to move nothing. Only what is declared to end region memory (reset, rewind, shrink, finish, and their callers) does.
    • A field a struct owns (^T, ^[]T), read through a pointer, now counts as part of what that pointer reaches rather than memory of unknown lifetime: storing into it is storing into the struct.
    • Growing what a pointer variable points to changes that pointee, not the things whose views were stored in it.
  • map owns its table: the table is now a ^[]slot the map owns (it was raw memory freed by hand), new slots are zero bytes rather than a copy of the entry being added, and keys and values can't own memory: a map of owners is refused with an error, where before it leaked them. So map::put stores a key into the map instead of "keeping" it: a map of strings from the same scope, or of region text, compiles, and using the map after a key's source has ended is the error, where it belongs.
  • A trap found on the way (corrected below): comparing compilers, a build from git archive seemed to disagree with the working one; it was first taken for objects left built against an old header.
  • Tests: λtests/expanse.lora (auto: 20 MB with no size given, reset, rewind, finish); λtests/http_server.lora (the request's region over six requests on one connection, and through record_raw); test-errors: region text stored in a global, a region's slice too, text used after finish, reset and rewind (refused); taking more, and taking after a reset (allowed); a struct holding a region with views of it (allowed), a value returned past its region (refused); a function value and a handler that keep their argument (refused); a request's region kept past the request (refused); a map keyed by a string of the same scope (allowed); a map of owners (refused); a map used after its key's block ended (refused, "m views o"). docs/stdlib.md: expanse::auto, the request's region, and what a map owns, with examples that run.

  • The hole: the rule that a function keeping its argument can't be made a function value (from the region work) didn't cover interface values. A type's methods are called through an interface value without being seen, so impl http::handler for keeper with a serve that saved req.target in a global compiled, and read freed memory once the request ended, though the same handler written as a function was refused.
  • The fix: each method table the compiler makes remembers its impl; where a value is made an interface value (its table's address taken), each method is checked as a function value is: one that keeps a pointer or view it is given is an error, "Its method serve keeps req after it returns, so this can't be made an interface value" (L0608).
  • Tests: test-errors: a handler type whose method keeps the request (refused); one whose method keeps nothing it is given (allowed). The library builds with no method refused.

Named tuple parts

Commit 3971ae5.

  • The change: a tuple's parts can be named in its type, fn divmod(a: int, b: int) (quot: int, rem: int), and read by name, d.quot, as well as by number, d.0. A tuple is made with names, (quot = 3, rem = 1), or by position where the type is known, as in a return (lo, hi) from a function whose result names them.
  • Rules:
    • A named tuple and an unnamed one of the same parts take each other, both ways: let plain: (int, int) = d;. Two named differently don't, as their parts mean different things.
    • A literal's names must match the type's, in order: (rem = 1, quot = 2) where (quot: int, rem: int) is expected is an error saying so.
    • A tuple names all its parts or none, no name twice, and has two parts or more.
    • Reading a name from a tuple that names none says to read by number, or to name its parts.
  • @all names its results: let r = @all(user = load(id), orders = count(id))?; gives r.user and r.orders; all named or none, and @first, which gives one value, takes no names.
  • Everywhere a tuple goes: the names are part of the tuple's type (hashed and compared), printed in error messages and typedefs, so they cross modules; kept through generics and type aliases; and given by @typeinfo as its fields' names. Unpacking, match patterns and owners in named parts work as for any tuple.
  • Editors: the tree-sitter grammar parses named tuple types and literals, and Zed highlights the names as fields. The language server completes a tuple's parts after t. (by name, or by number for an unnamed tuple) and shows a part's type on hover. Extension 0.48.0; the Zed extension's grammar is pinned to this commit.
  • Tests: λtests/named_tuples.lora (with leak checks); test-errors: seven named-tuple errors and @all naming some results; test-lsp: completion and hover of named parts; docs/language.md has an example that runs.
  • A flaky test made steady: the stack-frames test rebuilt the library with make while a lora command (an editor's check) could be building it too, under the lock lora takes; the two wrote the same files, and the test failed on a half-written one, several times today. It now removes the old build and rebuilds under the same lock.

Patterns in let and for

Commit 9af28f7.

  • The change: what a let or for binds can be a pattern that takes a value apart:
    • tuples nested in tuples, let ((a, b), c) = ((1, 2), 3);
    • a tuple's named parts, by name and in any order, let (quot = q, ..) = divmod(9, 4);
    • a struct by its fields' names, nested too, a field bound to its own name or another, let point { x, y: height } = p;
    • .. for the parts or fields left out;
    • in for-each loops over slices: for (let (name, score) .. scores), for (let point { x, .. } .. pts).
  • Rules, each refused with its reason: a let always takes its value apart, so a value in its pattern (let (1, b) = t) is sent to match; a struct pattern names every field or ends with ..; a tuple pattern names its parts all by name or all by position; names and fields that aren't there are named; a pattern of the wrong shape says what the value is. Owners move into their names: a part that owns memory can't be left with _ or .. (it would be dropped unused), and a type that cleans up when dropped (impl drop) can't be taken apart. static let keeps to a flat tuple.
  • How: a pattern is flattened into the bindings unpacking already made, each name bound at its part's offset in the value, so code generation and the later checks (ownership, views, effects) needed no change; the ownership count of a flat tuple's parts is skipped for a pattern, which checked what it leaves itself. A flat list of names is parsed as it always was.
  • Editors: the tree-sitter grammar parses the patterns, and Zed highlights a named part's label and a struct pattern's type. The language server finds the names a pattern binds, not taking a part's label (quot = q), a field's (x: px) or the struct's name for one, so they hover and complete. Extension 0.49.0; the Zed extension's grammar is pinned to this commit.
  • Tests: λtests/let_patterns.lora (with leak checks, owners in nested tuples and structs included); test-errors: ten refusals; test-lsp: names bound in patterns in scope, labels not; docs/language.md has an example that runs.

Types for the names patterns bind, in the editor

Commit f0bb6be.

  • The change: hovering a name a let or for pattern binds shows its type (let px: int), and completion after px. offers its members.
    • Once the file is checked, the compiler's index already had each name's type: matched by name, line and function, it is shown.
    • Before then, or while the file doesn't build, the server works it out itself: each name a pattern binds records its path through the value (part 0, part quot, field x), and the type is followed along that path from the value's inferred type, or the element type of what a for walks.
  • Inference the server lacked, added for this: tuple literals, (1, "a") as (int, str) and (quot = 1, rem = 2) with its names; and array literals, [(a, 1)] as [1](T, int) ([_] with ...). Inlay hints show these too.
  • Tests: test-lsp: a struct pattern's name hovers with its type; test-lsp-types: completion of members of names from a nested tuple pattern, a struct pattern, a named tuple part and a for pattern (33 cases pass). Extension 0.50.0.

Errors inside interpolated strings, where they are

Commit c0d5638.

  • The bug: in $"{name} is {next.age}", an error about a name inside the braces was shown past it: the editor underlined is, .age, or the closing quote instead of name, next or x. Two slips added up:
    • A name's expression took the lexer's position (parse_access used lexer->loc), which by then was past the name and the token looked at after it. In ordinary code that was close to right; in an interpolated part, parsed by a lexer of its own whose source is just the expression, it landed after the whole name.
    • Each part started one character late: its position was taken after its first character had been read and pushed back, so the part's lexer counted that character a second time.
  • The fix: a name's expression is placed where the name starts; and a part's lexer starts at its {, so its first character is where it is. Errors about names in ordinary code are placed at the name's start too.
  • Tests: test-errors checks the exact columns of names after n + , after a {{x}} escape and a {n:x} format; test-lsp checks that the editor underlines exactly name, next and x in $"{name} is {next.age}, at {x}".

Sealing the library's types the runtime trusts

Commit c4c1026; the guidance on when to seal, in the language reference and on the site, followed it.

  • The rule: a type needs @sealed only when its own module's unsafe code trusts its fields. Code with no unsafe stays memory safe whatever its fields hold. Of the 58 modules, 16 have unsafe code, and two more needed seals:
    • coro: chan, case, waitq, group, scope, results, serial and arrivals. Safe code could build a case holding any pointer, which select treated as a channel; a channel's ring positions drive its byte copies; the rest hold the scheduler's queues or state only their locks may touch.
    • thread: thread, mutex, cond, atomic and shared. Writing an atomic's value, or reaching a shared value without its lock, was a data race the race checker couldn't see; a thread's id goes to the system's join.
  • Left open: crypto::aes, whose round count is checked before its assembly uses it; net, fs and io, which only pass descriptors to system calls; map, sql and pg, whose unsafe code doesn't depend on field values or whose type isn't exported.
  • What changed for programs:
    • thread::atomic { ... } is an atomic holding 0, and thread::new_atomic(n) one holding n; every { v = ... } in the library, tests, docs, examples and benchmarks was rewritten.
    • A thread is moved, never copied, and joined or detached once; one dropped with neither is detached. Several are kept in a ^[]thread and joined with thread::join_all; coro's worker pool works so.
  • Zero values: each sealed type's T { ... } works. Mutexes, conds, shared values, coro::notifier and sql::db default their locks to valid ones (a zero-filled lock failed its first use on macOS); a zero channel is unbuffered; a zero thread is none, which join and detach leave alone.
  • Found and fixed on the way: the first rewrite of coro's worker shutdown freed the pool's slice twice at exit; it is now emptied in place.
  • Docs and editors: docs/stdlib.md says which thread and coro types are sealed and how threads are joined; docs/language.md says when to seal a type and lists the library's sealed types, and the site's structs page shows it. Extension 0.63.0.
  • Tests: test-errors refuses a forged select case, setting channel fields, reaching an atomic's or a shared value's fields, and copying a thread; λtests/zero_values.lora uses each zero value plainly, under leak checks and in guard mode.
