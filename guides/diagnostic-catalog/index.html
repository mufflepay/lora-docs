Diagnostic Error Catalog (L0001–L1004)

Complete reference of every compiler error and warning code (docs/errors.md), matching lora explain <code> and IDE hover badges.

Each diagnostic with a code, such as error[L0003], is explained here. lora explain L0003 prints its entry.

L0001 Unknown name

A name is used that is not declared where it is used, or its module is not imported.

lora 
export fn main() void = {
	let n = lenght("abc"); // error: `lenght` is an unknown object
}

Check the spelling. A name from another module needs use module; first (fmt is the exception: its names are always known).

L0002 Wrong type

A value of one type is used where another is expected, and converting it could lose something or is not allowed implicitly.

lora 
export fn main() void = {
	let big: u64 = 300;
	let small: u8 = big; // error: Initializer of type u64 is not assignable to binding type u8
}

Convert explicitly with @u8(big), which keeps the low bits, or change the type the value goes to.

Lora's types are nominal: each type declaration is a type of its own, so two declarations with the same definition are not interchangeable.

lora 
type rect = struct { w: f64, h: f64 }
type square = struct { w: f64, h: f64 }

fn fill(r: rect) void = void;

export fn main() void = {
	fill(square { w = 1.0, h = 1.0 }); // error: Argument type square is not assignable to parameter type rect
}

Convert it, fill(@rect(s)); for a tagged union, convert it or add the type to the union.

L0003 Unhandled error

A call (or other expression) may give an error, and its value is dropped. Lora never drops an error silently: say what happens when it fails.

lora 
use io;

fn save() (void | io::error) = void;

export fn main() void = {
	save(); // error: Cannot ignore an error here
}
  • save()! stops the program with the error, if there is one.
  • save()? returns the error to the caller (in a function that can return it); save() ? "saving the settings" adds a note for the trace.
  • save() or |e| { ... } handles it here; x or y gives y instead.

Keeping the result in a variable that nothing reads drops it just the same:

lora 
use io;

fn load() (int | io::error) = 1;

export fn main() void = {
	let n = load(); // error: Cannot ignore an error here: `n` may hold one
}

L0004 No error can happen

! or ? is applied to a value that cannot be an error.

lora 
fn n() int = 3;

export fn main() void = {
	let x = n()!; // error: Cannot use error assertion on an int, which can never be an error
}

Drop the ! or ?.

L0005 Fallback with or

x or y handles errors: it gives x's value, or y when x is an error. It applies to values that may be errors, and what it gives must be of x's value's type, unless it leaves with return, break, continue or abort. For an optional (T | void), use ??.

lora 
use strconv;

export fn main() void = {
	let port = strconv::parse_int("80") or 8080;
	let name: ?str = void;
	let shown = name ?? "nobody";
}

L0006 Dropped error

A match arm _ takes errors no other arm names. An arm that goes on, giving a value or returning, is an error: the program carries on as if nothing had failed.

lora 
use strconv;

fn workers(s: str) int = match (strconv::parse_int(s)) {
	let n: int => n,
	_ => 4, // error: This `_ =>` arm drops a strconv::invalid_number error, and goes on
}

export fn main() void = assert(workers("8") == 8);

An arm that stops the program, with abort or a function that never returns, is warned about: it says where, but not what went wrong.

lora 
use net;
use os;

export fn main() void = {
	let l = match (net::listen_at("127.0.0.1:8080")) {
		let l: net::listener => l,
		_ => os::exit(1), // warning: This `_ =>` arm drops or hides errors
	}
}

Name the error and say something with it, or let main return it, which prints it with its trace:

lora 
use net;
use netip;

fn serve() (void | nomem | net::error | netip::invalid) = {
	let l = net::listen_at("127.0.0.1:8080") ? "listening on port 8080";
}

export fn main() (void | nomem | net::error | netip::invalid) = {
	if (false) serve()?;
}

L0007 Error message

An error type may declare its message: a template whose {placeholders} are fields of the error, or a function that describes a value of it.

lora 
type quota = !struct { user: str, limit: usize }
"user {user} is over the limit of {limit}";
type code = !u32 describe_code;

fn describe_code(c: *const code, buf: []u8) str = "a code";

export fn main() void = void;

Only an error type (!T) has a message; a placeholder must name a field; a describe function is fn(e: *const T, buf: []u8) str.

L0008 Error the function can't return

x? returns x's error, so the function's result type must include it.

lora 
use strconv;

fn port(s: str) int = strconv::parse_int(s)?; // error: Error type strconv::invalid_number is not assignable to function result type int

export fn main() void = void;

Add it to the result type, (int | strconv::invalid_number), or handle it here: strconv::parse_int(s) or 8080.

L0009 Integer overflow

A constant computation does not fit its type. At run time the same overflow stops the program, saying with what values.

lora 
fn main_count() i32 = 2147483647i32 + 1; // error: Integer overflow: 2147483647 + 1 is out of range for i32

export fn main() void = void;

Use a wider type, such as i64, or wrap on purpose with +%, -% or *%, as hashes and random number generators do.

L0100 Memory leak

Raw memory a local holds (what an owner gave up with release, or an empty slice grown with append) is certainly not freed on some path out of its scope: it leaks. Owners, ^T, ^str and ^[]T, free themselves.

lora 
use strings;

fn greet(name: str) void = {
	let s = unsafe { release(strings::concat("hi ", name)!) } // error: `s` holds the memory allocated on line 4, and nothing frees it: it leaks when its block ends
	fmt::println(s)!;
}

export fn main() void = greet("x");

Add defer free(s); right after it is made.

L0101 Owned result dropped

A library call returns new memory, and it is used where it cannot be freed afterwards: as a statement, an operand, or an argument that is only borrowed.

lora 
use strings;

export fn main() void = {
	assert(unsafe { release(strings::concat("a", "b")!) } == "ab"); // error: `strings::concat` returns memory the caller must free, and nothing frees it here: it leaks
}

Bind it, use it, and free it: let s = strings::concat("a", "b")!; defer free(s);.

L0102 Use after free

Memory is used after free on every path that reaches the use.

lora 
type node = struct { v: int }

export fn main() void = {
	let p = alloc(node { v = 1 })!;
	free(p);
	p.v = 2; // error: `p` is used here, but the memory it owned was freed on line 5: this would touch freed memory
}

Use it before freeing it, or free it later. A copy of the pointer is the same memory: let q = p, or let q = f(p) with an f that returns what it is given, so using q after free(p) is also a use after free.

L0103 Double free

Raw memory (a *T, or memory an owner gave up with release) is freed again, or freed when a defer frees it already. An owner, ^T, cannot be freed twice: free(p) moves it.

lora 
type node = struct { v: int }

export fn main() void = {
	let p = unsafe { release(alloc(node { v = 1 })!) }
	defer unsafe { free(p) }
	unsafe { free(p) } // error: `p` is freed here, and the defer on line 5 frees it again when its block ends: freeing it twice would crash
}

L0104 Dangling stack pointer

A pointer to a local, a parameter or a temporary is returned, stored where it outlives the function (a global, the heap, what a parameter points to), or given to a function that keeps it; the memory is gone once the function returns.

lora 
let saved: nullable *int = null;

fn stash(p: *int) void = { saved = p; }

fn counter() *int = {
	let n = 0;
	return &n; // error: This returns a pointer to `n`, which is gone when the function returns
}

fn f() void = {
	let x = 5;
	stash(&x); // error: A pointer to `x` is kept by stash after it returns, but `x` is gone once f returns.
}

export fn main() void = void;

Allocate it (alloc) and free it later, let the caller pass a pointer to fill in, or keep a copy of the value instead of a pointer. What a function keeps is inferred from its body (see "What calls do with pointers" in the language reference). Code that makes sure itself that the pointer is not used after the function returns says so with unsafe { &x }.

L0105 Not memory from alloc

free or adopt is given memory no allocation made: a local's, a global's, or a temporary's. Freeing it would fail, as the program ends at the latest, so it is an error in unsafe code too, when it is certain.

lora 
export fn main() void = {
	let p = &@int(12);
	let a = unsafe { adopt(p) }; // error: `adopt` takes memory from `alloc`, but `p` points to a temporary, `@int(12)` on line 2, which no allocation made
}

Give them memory from alloc, or from release of an owner. Adopting what an owner lends, adopt(&n) for an n: ^T, is a double free (L0103): n frees it too; move the owner instead.

L0106 Defer that runs at once

A defer runs when its own block ends. As the last thing in an unsafe { ... } it runs as soon as it is reached, which is never what it is written for: in unsafe { defer free(p) } the block is the unsafe { ... }, so p is freed on that line, and using it after is a use after free.

lora 
export fn main() void = {
	let p = unsafe { release(alloc(1)!) };
	unsafe { defer free(p) } // error: This `defer` runs right away
}

Put the unsafe inside the defer, defer unsafe { free(p) }, which then runs when the block around it ends.

L0200 Outside the view

A view, *T.{fields}, reaches only the fields it names.

lora 
type foo = struct { a: usize, b: u32 }

fn peek(f: *foo.{b}) usize = f.a; // error: `a` is not part of the view *foo.{b}: a view reaches only the fields it names

export fn main() void = void;

L0201 Overlapping views

A view promises its callee that the fields it names are reached no other way during the call.

lora 
type foo = struct { a: usize, b: u32 }

fn twice(f: *foo.{b}, b: *u32) void = void;

export fn main() void = {
	let x = foo { a = 1, b = 2 }
	twice(&x, &x.b); // error: Arguments 1 and 2 both reach 'x.b', and one can change it
}

L0202 Const field of a view

A view may let a field be read but not changed: *T.{const a}.

L0203 Can't change this

The value is const, or reached through a *const pointer or a view that only reads it.

L0300 Missing format value

lora 
export fn main() void = {
	fmt::printfn("{} and {}", 1)!; // error: This format string needs 2 values, but 1 is given
}

L0301 Bad format placeholder

Placeholders are {}, {0} (by position) or {:spec}, such as {:x}, {:>8}, {:.2} or {:?}; see the fmt reference.

L0400 Outside the pattern type

A constant given to a pattern type, such as type port = u16 is 1.., is outside its pattern. Values known only at run time are checked by @T(x).

L0500 Wrong number of arguments

A call passes more or fewer arguments than the function takes.

L0600 Used after move

An owner, ^T, moved (to a ^T parameter, a binding, a field, a return) and is used afterwards; or it moved on some path to the use. A move must be an owner's last use.

lora 
type node = struct { value: int }

fn keep(n: ^node) void = void;
fn show(n: *node) void = void;

export fn main() void = {
	let p = alloc(node { value = 1 })!;
	keep(p);
	show(&p); // error: `p` is used after it moved so it can't be used here
}

Lend it to the first call if it only reads it (show(&p) before keep(p)), or move it last.

L0601 Moved in a loop

An owner made outside a loop moves inside it: the second turn would move what the first already gave away.

L0602 Loan outlives its owner

A borrow of an owner (&p, or p passed as *T) is returned or stored in a global, which outlive the owner, freed when its scope ends.

L0604 Owned value not kept

alloc (or a function returning ^T) gives an owner that is neither bound nor moved anywhere: it would be freed at once.

lora 
type node = struct { value: int }

fn show(n: *node) void = void;

export fn main() void = {
	let raw: *node = alloc(node { value = 1 })!; // error: This owned value is not kept by anything
}

Lent to a call or a comparison, an owned value lives until it is done; kept as a raw pointer, it would be freed at once. Bind it first, let p = alloc(...)!;, or release(...) it to manage it yourself.

A temporary lent to a call lives only as long as the call, so a call whose result may view it, as a struct holding a str, is an error too, even when the result also owns memory of its own:

lora 
use strings;

type request = struct { url: str, body: ^[]u8 }

fn request_of(url: str) request = request { url = url, body = [] }

export fn main() void = {
	let r = request_of(strings::concat("https://", "example.com")!); // error: This owned value is not kept by anything
}

L0605 Move out of a field

A field ^T is owned by what holds it, which drops it; moving it out would drop it twice. Lend it (&x.f), or move what holds it.

L0606 Owner overwritten

An owner that still owns its value is given a new one, which would leak the old. Free it first (free(p)) or move it.

L0607 Would lose an owner

Code that would abandon something that owns memory, on a path where nothing could drop it: ? or another exit after an owner was handed to a call or literal still being built, or inside alloc; or with no name for an error that owns memory; if let on a temporary whose other members own memory; a closure capturing an owner; a delete of owners whose index calls something; append of several owners at once, which would copy them. Give the value a name first, so it is dropped on every path.

L0608 View outlives its source

A str, []T or *T is used, returned or stored after what it points into is freed, moved or out of scope, or where it would outlive it. What a region holds is a view of the region. A function that keeps what it is given can't be made a function value (&f), as calls through one are taken not to keep it; nor can a type be made an interface value if one of its methods does.

lora 
fn tail(s: str) str = s[1..];

fn f() str = {
	let o = $"owned";
	return tail(o); // error: This returns a view of `o`, which ends with f
}

export fn main() void = void;

Use it sooner, or keep a copy with strings::clone.

L0609 Source changed under a view

A view is used, read or written through, after what it points into may have moved: an append, insert or delete (of the owner, or through a pointer to it), an assignment, or a call that changes it.

lora 
export fn main() void = {
	let b: ^[]u8 = alloc([1u8], 1)!;
	let v = b[..1];
	append(b, 2)!;
	assert(v[0] == 1); // error: `v` views `b`, which grew on line 4
}

Take the view after the change.

The same holds inside one call: given a view of what another of its arguments changes, a function that uses the view after that change would see moved memory. Each function's typedef says which of its arguments it uses after changing which others, so a call is only an error when it uses the view after the change, not before:

lora 
fn grow(a: *^[]int, b: *int) void = {
	append(a, 1)!;
	*b = 5;
}

export fn main() void = {
	let xs: ^[]int = [];
	append(xs, 1)!;
	grow(&xs, &xs[0]); // error: This argument views `xs`, which `grow` may change through its argument 1
}

Give the value instead of a view of it, or make the change and the use two calls. Arguments that can't overlap are fine: different fields of one value (f(&b.items, &b.count)), and a field held in place beside what grows (next(c, &c.cur)).

L0700 Data race

Code started on another thread (a closure given to thread::spawn, coro::detach, @all's children and the like, or a function it calls) changes data other threads may use at the same time: a mutable global, or what a pointer shared by several running closures points to.

lora 
use thread;

let counter = 0;

export fn main() void = {
	let t = thread::spawn(fn() void = {
		counter += 1; // error: `counter` is changed by a thread while other threads may use it.
	})!;
	thread::join(t);
}

Make the data thread-safe: a thread::atomic, or a value guarded by a lock, thread::new_shared(v), reached with thread::with. Changes between thread::lock(m) and thread::unlock(m) are fine, as is a global its module guards itself, marked @synchronised.

Children that run at the same time may not reach the same data when one of them may change it, whatever pointer leads there:

lora 
use coro;

fn bump(p: *int) void = { *p += 1; };

export fn main() void = {
	let n = 0;
	let p = &n;
	@all(bump(p), bump(p))!; // error: `p` reaches data (an int) that may change while another thread uses it.
}

Give each child its own data and gather the results, share it read-only (*const T), or make it thread-safe. A value holding connections, such as a kv::client or kv::cluster, belongs to one child: each opens its own.

L0800 Unsafe operation

Converting between unrelated pointer types, from an integer or null to a non-nullable pointer (@*T(x)), changing ownership or slice element types by conversion, pointer arithmetic or subtraction, indexing or slicing a [*]T array, shrinking a non-owned slice with delete, calling C, and calling an @unsafe function or method can't be checked by the compiler, so each needs unsafe { ... }. The impls of an @unsafe interface method are @unsafe too, and only those.

lora 
export fn main() void = {
	let x = 1;
	let p = @*[*]u64(&x); // error: Converting *int to *[*]u64 can make a pointer to memory that isn't what it says, so it needs `unsafe { ... }`.
}

Make sure it is right, then mark it: unsafe { @*[*]u64(&x) }.

L0801 Unneeded unsafe block

An unsafe { ... } holds nothing unsafe: no unsafe operation, and no pointer it vouches for. Each block marks code to read with care, so one that needs no care is an error.

lora 
fn twice(x: int) int = unsafe { x * 2 } // error: This unsafe block does nothing unsafe.

export fn main() void = assert(twice(2) == 4);

Remove it, keeping what is inside: fn twice(x: int) int = x * 2;. A block inside an @unsafe function is unneeded for its operations, which the function allows already.

L0900 Unknown tag

A field has a tag no imported module defines. It is an error, so that a misspelt tag is never quietly ignored.

lora 
use json;

type user = struct {
	@josn("id") id: int, // error: @josn is an unknown tag
}

export fn main() void = void;

Check the spelling, and that the module defining it is imported.

L0901 Ambiguous tag

Two modules this file can see define the same shorthand. Name the one you mean, as @json::field(...), or write the long form, @tag(json::field { ... }).

L0902 Bad tag value

A tag must be a constant of a declared struct type: @tag(5) is not one, and neither is a value only known when the program runs.

L0903 Bad tag arguments

A tag's arguments name fields of its type, or set them in order.

lora 
use json;

type user = struct {
	@json("id", nope = 1) id: int, // error: @json has no argument `nope`
}

export fn main() void = void;

L0904 Repeated tag

A field has two tags of one type. Remove one.

L0905 A tag's rule failed

The library that defines a tag checks how it is used, while compiling.

lora 
use config;

type server = struct {
	@config("port", default = "8080") port: int, // error: Bad tag on field `port` of server: its default is not of the field's type
}

export fn main() void = void;

L0906 Generator error

A generator such as config::load[T] cannot handle a field of T, or @for, @fields or @if is misused.

text 
type server = struct { ratio: f64 };

let s = config::load::[server]()?;

error[L0906]: this field has no @config tag: field `ratio` of server.

L1000 A failure would lose an owner

With unit::error in the result, a false condition returns. A false ensures would drop an owner the function returned, and a false requires an owner passed to it.

lora 
use unit;

fn take(p: ^int, n: int) (int | unit::error) requires(n > 0) = { // error: A requires clause can't return a failure from a function that takes an owner
	free(p);
	return n;
}

export fn main() void = void;

Take unit::error out of the result, so that a false condition stops the program, or check it in the body and free the owner there.

L1001 A failure's message owns memory

A failure returned as a value holds its message, and nothing would free $"...".

lora 
use unit;

fn half(n: int) (int | unit::error) requires(n % 2 == 0, $"{n} is odd") = n / 2; // error: A failure returned as a value holds its message, so it must be a plain str

export fn main() void = void;

L1002 @expect with nowhere to fail

When its time runs out, @expect returns unit::expectation_failed, so the function's result must hold it.

lora 
fn ready() bool = true;

fn wait() void = {
	@expect(within = 100) { // error: @expect needs unit::error in the function's result
		assert(ready());
	}
}

export fn main() void = void;

Add unit::error to the result.

L1003 An @expect's time

Nothing waits forever by accident: within is required, and it and every are whole numbers of milliseconds, of any integer type.

lora 
use unit;

fn ready() bool = true;

fn wait() (void | unit::error) = {
	@expect(every = 10) { // error: @expect needs to know how long to wait
		assert(ready());
	}
}

export fn main() void = void;

L1004 A condition that can wait

requires and ensures are checked once, and never wait, so a condition can't call anything that runs an @expect, however many calls away it is. Calls through function pointers and closures can't be followed.

lora 
use unit;

fn ready(n: int) (bool | unit::error) = {
	return @expect(within = 10) {
		yield n > 0;
	}
}

fn check(n: int) bool = ready(n) or false;

fn half(n: int) int requires(check(n)) = n / 2; // error: This condition can wait

export fn main() void = void;

Wait in the body, with @expect, before the check.
