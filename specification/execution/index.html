Execution & Runtime

Runtime bootstrap (_main), Mach-O init/fini/test boundary arrays, allocator wrappers, signal crash handlers, Darwin syscall bindings, and abort internals (docs/runtime.md).

The runtime is the rt module (runtime/). It is small by design: it provides startup, libc bindings, allocation, and the abort machinery — everything the compiler and core library need, and nothing more.

Startup

Darwin entry (runtime/+darwin/start.lora):

lora 
export @symbol("main") fn _main(c_argc: int, c_argv: ..., c_envp: ...) void = {
	argc = c_argc; argv = c_argv; envp = c_envp;
	init();     // runs all @init functions
	main();     // @symbol(".main") — the program's main
	fini();     // runs all @fini functions
	exit(0);
}

The compiler is invoked with -m .main so user code declares @symbol(".main") fn main and the runtime owns the C main symbol.

@init/@fini/@test functions are enumerated through arrays of function pointers. On Mach-O these live in dedicated sections, __DATA,__lora_init, __DATA,__lora_fini and __DATA,__lora_test, with ___lora_init_array_start/end, ___lora_fini_array_start/end and ___lora_test_array_start/end boundary symbols defined in runtime/+darwin/sections.s.

Memory

runtime/malloc+libc.lora implements malloc, realloc and @symbol("rt.free") fn free_ directly on top of libc's allocator. The core library builds slice allocation (mem::new, alloc, append, …) on top of these, including growable slice headers via ensure/unensure (λruntime/ensure.lora).

The compiler calls malloc_at and ensure_at, which also take the source location of the alloc, append or closure being made. With LORA_LEAKS set, λruntime/leak.lora records every live block (size, location, and the return addresses of the running functions, found by walking frame pointers with rt_frame_address in +darwin/coro.S). At exit it names the functions from the executable's own symbol table, and reports every block still live, grouped by origin. What points to a block decides nothing. Freed blocks are poisoned and quarantined; realloc under the check copies to a new block, so the old one is quarantined too. With LORA_LEAKS=guard, guard_alloc gives each block pages of its own from mmap, ending against a PROT_NONE page, and a free maps fresh PROT_NONE pages over the block: the crash handler (+darwin/signals.lora) asks guard_explain whether a faulting address is a freed block or the page past a live one. Without LORA_LEAKS the cost is one test of a global per call.

System interface

stat_info holds what fs::info gives: the mode, length, change and read times, inode, device, owner, group and link count. They are read from each system's struct stat at offsets that +darwin/platform.lora and +linux/+<arch>/arch.lora give, since x86_64 and aarch64 lay out the link count and owner differently.

All OS access goes through libc bindings declared in λruntime/libc.lora and runtime/+darwin/syscalls.lora: open read write close lseek access unlink mkdir rmdir rename chdir getcwd fsync socket bind listen accept connect send recv setsockopt shutdown dup2 fork execve wait4 kill getpid exit nanosleep clock_gettime getenv strerror isatty plus constants (O_*, SEEK_*, AF_INET, SOCK_STREAM, SO_*, CLOCK_*, MAP_*, signal numbers).

On Linux the bindings are in runtime/+linux/, which serves x86_64 and aarch64 alike, but for what the two lay out differently: each has a runtime/+linux/+<arch>/arch.lora (O_NOFOLLOW and O_DIRECTORY, where st_mode sits in struct stat, and epoll_event, which x86_64 packs). C types the runtime only holds, such as pthread_mutex_t, are sized for the larger of the two and aligned as C aligns them. The atomics in +linux/coro.S are load-exclusive / store-exclusive loops on aarch64, so an ARMv8.0 processor runs them; AES uses the processor's instructions where it has them (getauxval on aarch64, cpuid on x86_64) and the library's constant-time rounds where it has not. LORA_NO_AES=1 makes a program use the library's rounds, which tests that path anywhere.

runtime/+darwin/process.lora holds what process and signal are built on:

  • Starting programs. spawn calls posix_spawn with POSIX_SPAWN_CLOEXEC_DEFAULT, so a child gets only the descriptors it is handed. The descriptors handed over are first copied above every target, so one hand-over can't overwrite another. Running as another user, or with a terminal or the foreground, is more than posix_spawn does. For those, spawn_forked forks. The child sets its session, group, controlling terminal (TIOCSCTTY), foreground (tcsetpgrp), groups, group and user, in that order. Then it becomes the program through posix_spawn with POSIX_SPAWN_SETEXEC, so descriptors and signals are handled as before. Every signal is blocked from the fork until the program starts, and the child calls nothing that allocates or locks. It reports a failure on a pipe that closes when the program starts. In this mode posix_spawn closes the close-on-exec descriptors before it hands any over, so the child clears that flag on the ones it hands over first.
  • Terminals. open_pty opens a pseudo-terminal pair, with the terminal's name from TIOCPTYGNAME. terminal_foreground and set_terminal_foreground read and set a terminal's foreground group, with SIGTTOU blocked while it is set.
  • The program itself. environ is the environment as it is now (_NSGetEnviron). executable_path is _NSGetExecutablePath with links followed. On Linux these are the C library's environ (read by rt_environ in +linux/coro.S) and /proc/self/exe, which is why os has them there too. start_environ is the environment the program started with. The C library rewrites that array in place (setenv replaces entries, unsetenv moves them up) but never the strings, so λstart.lora copies the array before @init runs and keeps it for the program's life, as it keeps argv.
  • Waiting. exit_watch is a kqueue holding EVFILT_PROC/NOTE_EXIT for one child, which a coroutine waits on as on any descriptor. The fdset_* functions are a kqueue of pipes, which process::output waits on to read and write them together.
  • Signals. on_signal is the handler for watched signals. It writes the signal's number to each watcher's pipe and reaps children that were released. It takes no lock, and it saves and restores errno. signal_unwatch waits until no handler is running before a watcher's pipe is closed.

These are macOS only for now. Linux has no process or signal runtime yet, so the build leaves out the process and signal modules there, and a program that uses either one does not build there.

Two Darwin-specific notes for anyone extending the bindings:

  • C-variadic functions must be declared with .... libc's open is int open(const char *, int, ...). Declare it as fn open(path: *const u8, flags: int, ...) int; — a fixed three-argument declaration mis-compiles the mode argument because Darwin's ARM64 variadic ABI does not read it from the fixed-argument registers. This was a real bug: file modes came out as garbage until open was declared variadic.
  • Mach-O C symbols are prefixed with an extra underscore (___lora_init_array_start), which @symbol declarations and Csections.s handle.

Errors and aborts

  • rt::errno is the system's error number, !u32, which describes itself as Broken pipe (EPIPE, errno 32). errno_now() reads the failing call's (__error). Library modules keep it inside their own error type, with the operation that failed; none returns it alone.
  • Runtime aborts call rt.abort with the source location and message, then raise SIGABRT. Fixed abort reasons (bounds check, type assertion, unreachable, capacity, assertion, error assertion) print canned messages from λruntime/abort.lora.

Building the runtime

make stdlib at the project root compiles rt first:

sh 
compiler/.bin/lorac -N rt -m .main -o .build/rt.ssa -t .build/rt.td runtime/*.lora runtime/+darwin/*.lora
# on Linux: runtime/*.lora runtime/+linux/*.lora runtime/+linux/+$ARCH/*.lora
compiler/scripts/qbe-darwin -t arm64_apple -o .build/rt.s .build/rt.ssa
compiler/scripts/darwin-as -o .build/rt.o .build/rt.s runtime/+darwin/sections.s

Consumers find the runtime's types through the typedef file: LORA_TD_rt=.build/rt.td. The same pattern applies to every core module; the lora driver exports all of the LORA_TD_* variables before invoking the compiler (see docs/tooling.md).
