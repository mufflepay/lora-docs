Safety

Borrow, Loan & View Safety

How Lora proves views (*T, []T, str, *T.{fields}) never dangle across calls, slice resizes, closure @clone, and cross-module @effects.

Overview

Cloans.c and Ceffects.c track up to 1,024 simultaneous loan sources (MAXSOURCES) and 32 parameter effect slots (MAXPARAMS) per function across module boundaries:

  • Lifetime & Escape (L0104, L0602, L0608): Pointers and views (*T, []T, str) cannot outlive the stack local, owner, or expanse region they borrow from.
  • Invalidation Under Mutation (L0609): Growing, deleting, or reassigning a ^[]T or ^str invalidates active views into its buffer—both across statements and between aliasing arguments of a single call.
  • Disjoint Partial Borrows (*T.{fields}, L0200–L0203): A partial view restricts a callee to named fields (and optional const fields), allowing callers to pass disjoint fields of the same struct simultaneously.

}

Dropping goes through a list of what is left to drop rather than recursion, so dropping a long chain cannot overflow the stack.

Views

str, []T and *T are views: they point into memory something else owns. A view is two or three words, and making one, slicing it or passing it costs no allocation. ^str and ^[]T are the owners. The compiler tracks what each view points into, so that a view can't dangle, and nothing needs to be written for this:

  • A view can't outlive what it views. It can't be used after its source is freed, moved or out of scope (L0608).
  • A view can't leave. It can't be returned from the function its source is local to, or stored where it outlives it: a global, a returned struct, or anything a call keeps.
  • A source can't change under a view. After an append, insert, delete or assignment that may move its memory, or a call that may, views taken earlier can't be used (L0609). Taking the view again is fine.
lora 
use strings;

fn word(s: str) str = match (strings::cut(s, ' ')) { // a view of s: the caller's
	let c: (str, str) => c.0,
	void => s,
}

export fn main() void = {
	let line = strings::clone("hello world")!;
	let w = word(line);                      // views line
	assert(w == "hello");
	let kept = strings::clone(w)!;           // lives on its own
	free(line);
	assert(kept == "hello");
}
lora 
use strings;

fn word(s: str) str = s[..1];

Cross-Module Effects & Aliasing Arguments

Freeing memory twice, or using it after free, is an error when it is certain on every path (a len of a freed slice is allowed, since the length is still known; a defer that frees a local counts as its free):

lora 
type node = struct { v: int }

export fn main() void = {
	let p = alloc(node { v = 1 })!;
	free(p);
	p.v = 2; // error: `p` is used here, but the memory it owned was freed on line 5: this would touch freed memory
	let q = alloc(node { v = 1 })!;
	defer free(q);
	free(q); // error: `q` is freed here, and the defer on line 8 frees it again when its block ends: freeing it twice would crash
}

As the program runs, lora run --leaks (or LORA_LEAKS=1 with any built program) records every live allocation and, at exit, reports the ones not freed by then, grouped by where they were made, as the compiler writes its errors: the place, what was never freed (the name it was given there, or the function whose memory it is), the source line, the functions that were running, and the fix. On a terminal it has the compiler's colors, under a LEAK badge:

text 
$ lora run --leaks leaky.lora

leaky.lora:13:28: leak: `buf` was never freed: the 1000 bytes allocated on line 13 were still allocated when the program ended, and nothing freed them.

13 |	let buf = unsafe { release(alloc([0u8...], 1000)!) };
   |	                           ^

  made in buffer, called from main

lib/strings.lora:66:9: leak: Memory from `strings::concat` was never freed: the 28 bytes in 2 allocations made on line 66 were still allocated when the program ended, and nothing freed them.

66 |	append(out, to_bytes(b)...)?;
   |	^

  made in strings::concat, called from greet <- main
  = help: Free what it returns when you are done with it	defer unsafe { free(x) }

lora: leak check: 3 allocations (1028 bytes) never freed

A use after free or double free that the run finds stops it with the same layout: what was misused, where it was made and freed, and the fix.

  • The exit status is 23 when there are leaks; LORA_LEAKS=report reports them but keeps the program's own status.
  • Every allocation not freed at exit is reported. What still points to it decides nothing, so memory a global keeps until the end counts too.
  • LORA_FAIL_ALLOC=n, with LORA_LEAKS set, makes the nth allocation fail, to test what happens when memory runs out. Try each n in turn.
  • Freed blocks are poisoned and kept in a quarantine of recent frees (up to 1024 blocks and 16 MiB) before they are given back. Freeing one again is reported as a double free, and a block whose poison changed (written after it was freed) as a use after free, with where it was allocated and freed; either stops the program. A block that grows and moves goes into the quarantine too, so a write through a pointer taken before it moved is found as well.
  • lora run --guard (LORA_LEAKS=guard) stops the program at the first touch of freed memory, a read as well as a write, and at any access past a block's end. Each block gets pages of its own, ending against a page nothing may touch, and a freed block's pages are given up and made untouchable; the report says which block it was and where it was allocated and freed. A system call and two pages per block make it slow, a check to run when a test or unsafe code is suspect, not every time.
  • Without --leaks there is no cost beyond one test per allocation.

Pointers to the stack. A pointer to a local or parameter, or to a temporary, may not leave its function: returning one (also inside a struct, a tuple, a slice of a local array or an rt::any) or storing one in a global is an error. An explicit conversion, @*T(&x), says it is meant, for a pointer that is not used after the function returns.

lora 
let last: nullable *int = null;

fn counter() *int = {
	let n = 0;
	return &n; // error: This returns a pointer to `n`, which is gone when the function returns
}

fn remember(x: int) void = {
	last = &x; // error: This stores in a global a pointer to 'x', which is gone when the function returns
}

export fn main() void = void;

What calls do with pointers

The compiler works out what each function does with the pointers it is given, its effects: which parameters it keeps after it returns (in a global, in the heap, or in what another parameter points to), which it may return, and which it frees. You don't write them; typedefs record them for other modules as @effects(...). Calls are checked against them:

lora 
let saved: nullable *int = null;

fn stash(p: *int) void = { saved = p; }

fn f() void = {
	let x = 5;
	stash(&x); // error: A pointer to `x` is kept by stash after it returns, but `x` is gone once f returns.
}

export fn main() void = f();

Valid Usage & Examples

Disjoint partial borrows (`*T.{fields}`) and view narrowing

A caller can hold &x.a while passing &x as *foo.{b} because {b} cannot reach a; wider views narrow automatically.

lora Allowed 
type foo = struct { a: usize, b: u32, label: str }

fn increment_b(f: *foo.{b}) void = {
	f.b += 1;
}

fn bump_both(f: *foo.{a, b}) void = {
	f.a += 10;
	increment_b(f); // *foo.{a, b} narrows to *foo.{b}
}

fn rename(f: *foo.{label}, a: *usize) void = {
	f.label = "renamed";
	*a += 1; // disjoint from {label}
}

export fn main() void = {
	let x = foo { a = 100, b = 42, label = "x" };
	let a = &x.a;
	increment_b(&x);
	*a += 1;
	bump_both(&x);
	rename(&x, &x.a);
	assert(x.a == 112 && x.b == 44 && x.label == "renamed");
}

Partial-view interface methods and explicit `@*T` recovery

Interface implementations may narrow their receiver to *T.{fields}, and @*T(view) recovers the full pointer when needed.

lora Allowed 
type counter = struct { n: int, name: str }
type step = interface { fn step() void; }

impl step for counter {
	fn step(c: *counter.{n}) void = { c.n += 1; }
}

export fn main() void = {
	let c = counter { n = 1, name = "hits" };
	c.step();
	let v: *counter.{n} = &c;
	let whole: *counter = @*counter(v);
	assert(whole.n == 2 && whole.name == "hits");
}

Cross-module `@effects` allowing non-overlapping keeper fields

Modifying k.vals does not invalidate args because k.vals and args are proven disjoint.

lora Allowed 
type keeper = struct { vals: ^[]str }

fn keep_all(k: *keeper, args: []const str) (^[]str | nomem) = {
	let rest: ^[]str = [];
	for (let a .. args) {
		append(rest, a)?;
		append(k.vals, a)?;
	}
	return rest;
}

export fn main() void = {
	let k = keeper { vals = [] };
	let args = ["a", "b"];
	let rest = keep_all(&k, args)!;
	assert(len(rest) == 2z && k.vals[0] == "a");
}

Disallowed Forms & Diagnostics

Passing overlapping mutable views to the same call (`L0201`)

If two arguments can reach the same field and at least one is mutable, the call is rejected.

L0201: Arguments 1 and 2 both reach `x.b`, and one can change it
lora Rejected 
type foo = struct { a: usize, b: u32 }
fn twice(f: *foo.{b}, b: *u32) void = void;

export fn main() void = {
	let x = foo { a = 1, b = 2 };
	twice(&x, &x.b); // error[L0201]: overlapping views on x.b
}
lora Allowed 
type foo = struct { a: usize, b: u32 }
fn disjoint(f: *foo.{b}, a: *usize) void = {
	f.b += 1;
	*a += 1;
}

export fn main() void = {
	let x = foo { a = 1, b = 2 };
	disjoint(&x, &x.a); // ok: {b} and a are disjoint
}

Using a slice view after `append` reallocates its owner (`L0609`)

append may reallocate the backing buffer, so any pre-existing view into it is invalidated.

L0609: `v` views `b`, which grew on an earlier line
lora Rejected 
export fn main() void = {
	let b: ^[]u8 = alloc([1u8], 1)!;
	let v = b[..1];
	append(b, 2)!;
	assert(v[0] == 1); // error[L0609]: source changed under view
}
lora Allowed 
export fn main() void = {
	let b: ^[]u8 = alloc([1u8], 1)!;
	append(b, 2)!;
	let v = b[..2]; // ok: take view after mutation
	assert(v[0] == 1 && v[1] == 2);
}

Constraints & Limits

  • Dynamic indirect calls (*fn, closure, interfaces) conservatively assume non-pure mutation over reachable owners; functions that retain arguments globally cannot become bare function values (L0608).
  • Static tracker limits in Cloans.c / Ceffects.c: MAXSOURCES = 1024 tracked loan sources, MAXPARAMS = 32 effect-tracked parameters.
