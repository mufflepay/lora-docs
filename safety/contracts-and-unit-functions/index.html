Safety

Contracts & Unit Functions

Function contracts (requires, ensures(r => ...)), --units=enforce|observe|ignore, typed failure results (T | unit::error), rt::on_unit_failure, and bounded retry waiting (@expect).

Overview

Any function with requires(...) or ensures([r =>] ...) is a unit function. The return type decides how failures behave:

SignatureFailure BehaviourBuild Mode (--units)
No unit::error in returnFailure is a bug: calls rt::on_unit_failure and abortsenforce (abort), observe (log & continue), ignore (skip)
unit::error in returnFailure is a value: returns precondition_failed / postcondition_failed / expectation_failedAlways active regardless of --units
  • @expect(within = ms [, every = ms]): Polls a block (performing I/O or state steps) until it succeeds or within ms elapse, yielding unit::expectation_failed on timeout.
  • Static Checks (L1000–L1004): Prevents dropping owners on failed contracts, owning error strings, missing unit::error for @expect, missing within, and calling @expect inside requires/ensures.

@unchecked removes bounds checks from indexing and slicing. An index out of range then reads or writes memory it shouldn't, so it is unsafe code, and the author's to get right.

Tags

A tag is a typed constant on a struct field, which a library defines and reads while compiling. A tag type is an ordinary struct, and @shorthand(name) gives it a short form. @name(...) is exactly a struct literal of it: positional arguments set its fields in order, name = value sets that field, and a bare field name sets a bool field to true.

lora 
export @shorthand(limit) type limit = struct {
	low: int = 0,
	high: int = 100,
	strict: bool = false,
}

type reading = struct {
	@limit(0, 10) level: int,                 // low = 0, high = 10
	@limit(high = 5, strict) count: int,
	@tag(limit { low = 1 }) rate: int,        // the long form
	other: int,
}

// A generator: expanded once per field, while compiling
fn valid[T](v: *const T) bool = {
	@for (f .. @fields(T)) {
		@if (@has_tag(f, limit)) {
			let t = @tag_of(f, limit);
			if (v.@(f) < t.low || v.@(f) > t.high) return false;
		}
	}
	return true;
}

export fn main() void = {
	let r = reading { level = 3, count = 5, rate = 1, other = -9 }
	assert(valid(&r));
	r.level = 11;
	assert(!valid(&r));
}

An unknown tag is an error, so a typo is never ignored:

lora 
export @shorthand(limit) type limit = struct { high: int = 100 }

type reading = struct {
	@limti(5) level: int, // error: @limti is an unknown tag
}

export fn main() void = void;

In a generator, @for (f .. @fields(T)) expands its body once per named field: f.name is the field's name, f.type its type, and x.@(f) that field of x. @if is a compile-time branch, and the branch not taken is not checked. @same(A, B), @kind(T), @owns(T), @borrows(T) (whether a value of T may view memory it doesn't own), @cycles(T), @has_zero(T), @implements(T, I), @sealed(T) (whether T is another module's @sealed type, whose fields only that module reads), @has_tag(f, tag) and @tag_of(f, tag) are constants, and @error("...") is a compile error when expanded. Tags emit nothing into the program, and are not in @typeinfo: generated code is direct field code, and an untagged type costs nothing. Tags are part of a struct's type, so two structs that differ only in tags are different, though @T(x) converts between them.

A generator that walks into the fields of whatever it is given asks @sealed(T) first, as another module's sealed type has fields it may not read:

lora 
use rt;
use time;

fn counted[T](v: *const T) usize = {
	@if (@kind(T) == rt::type_kind::STRUCT && !@sealed(T)) {
		let n = 0z;
		@for (f .. @fields(T)) {
			n += 1;
		}
		return n;
	} else {
		return 1; // a whole: its fields are its module's
	}
}

type pair = struct { a: int, b: int }

export fn main() void = {
	assert(counted(&pair { a = 1, b = 2 }) == 2);
	assert(counted(&time::now()) == 1);
}

@rule(fn) on a tag type names a function run at compile time for each struct using the tag, so a bad tag is an error at the field even if nothing reads it. See config and json in the standard library, and docs/tags.md for the rules in full.

An example of attributes

lora 
use fmt;

let ready = false;

@init fn setup() void = { ready = true; }
@fini fn teardown() void = fmt::println("bye")!;

export fn main() void = { assert(ready); }

24. Calling C

Declare a C function with @symbol and no body, and call it in unsafe { ... }: C doesn't follow Lora's rules, so the compiler can't check the call. C strings are *const u8: make one with strings::cstr, which gives an owned NUL-terminated copy, and pass &c[0]:

lora 
use strings;

@symbol("abs") fn c_abs(x: i32) i32;
@symbol("strlen") fn c_strlen(s: *const u8) usize;
@symbol("snprintf") fn snprintf(buf: *u8, n: usize, format: *const u8, ...) int;

export fn main() void = {
	assert(unsafe { c_abs(-4) } == 4);
	let c = strings::cstr("hello")!;
	assert(unsafe { c_strlen(&c[0]) } == 5);
	let buf: [32]u8 = [0...];
	let f = strings::cstr("%d")!;
	unsafe { snprintf(&buf[0], len(buf), &f[0], 42) }
	assert(buf[0] == @u8('4'));
}

Lora functions can be implemented with C variadics too:

lora 
fn total(n: int, ...) int = {
	let ap = vastart();
	defer vaend(ap);
	let t = 0;
	for (let i = 0; i < n; i += 1) t += vaarg(ap, int);
	return t;
}

export fn main() void = { assert(total(3, 1, 2, 3) == 6); }
  • export fn with @symbol("name") gives C code a Lora function to call.
  • A str cannot be cast to *u8: it is not NUL-terminated.
  • Limit: passing or returning structs of 16 bytes or less by value to or from C does not follow the C ABI (a QBE limit). Pass pointers to them instead.
  • C cannot call closures; only capture-free lambdas and functions convert to *fn.

25. Unit functions

A function can state what it needs and what it promises, which makes it a unit function. requires(condition) is checked when the function is entered; ensures(condition) when it returns. They go after the result type, before the body:

lora 
fn divide(dividend: int, divisor: int) int
	requires(divisor != 0)
= dividend / divisor;

fn absolute(n: int) int
	requires(n != -2147483648, "the smallest int has no absolute value")
	ensures(r => r >= 0)
= if (n < 0) -n else n;

export fn main() void = {
	assert(divide(9, 3) == 3 && absolute(-4) == 4);
}
  • ensures(r => condition) names the value returned r; ensures(condition)

Valid Usage & Examples

Returning `unit::error` as a typed value vs aborting on invariant bugs

Including unit::error in the return type turns requires/ensures failures into matchable error values.

lora Allowed 
use unit;

type account = struct { cents: i64 }

fn withdraw(a: *account, cents: i64) (i64 | unit::error)
	requires(cents > 0, "amount must be positive")
	requires(cents <= a.cents, "insufficient funds")
	ensures(r => r >= 0)
= {
	a.cents -= cents;
	return a.cents;
}

fn checked_half(n: int) int
	requires(n % 2 == 0)
= n / 2;

export fn main() void = {
	let a = account { cents = 100 };
	assert(withdraw(&a, 40)! == 60);
	match (withdraw(&a, 500)) {
		let e: unit::precondition_failed => assert(e.message == "insufficient funds"),
		i64 => abort("unexpected"),
		unit::postcondition_failed => abort("post"),
		unit::expectation_failed => abort("expect"),
	};
	assert(checked_half(8) == 4);
}

Polling eventual state with `@expect(within = ..., every = ...)`

@expect retries failed assert, as, or ? attempts until within ms elapse, using coro::sleep inside coroutines.

lora Allowed 
use unit;

type page = struct { left: int, id: str }

fn poll_page(p: *page) (str | void) = {
	if (p.left > 0) {
		p.left -= 1;
		return void;
	}
	return p.id;
}

fn wait_for(p: *page, want: str, ms: u64) (str | unit::error) = {
	return @expect(within = ms, every = 10) {
		let got = poll_page(p) as str;
		assert(got == want);
		yield got;
	};
}

export fn main() void = {
	let p = page { left = 3, id = "42" };
	assert(wait_for(&p, "42", 2000)! == "42");
}

Disallowed Forms & Diagnostics

Returning `unit::error` from a function that takes an owner (`L1000`)

A false requires returns before the body runs, which would leak or abandon an ^T parameter.

L1000: A requires clause can't return a failure from a function that takes an owner
lora Rejected 
use unit;

fn take(p: ^int, n: int) (int | unit::error) requires(n > 0) = { // error[L1000]: owner param cannot pair with unit::error
	free(p);
	return n;
}

export fn main() void = void;
lora Allowed 
fn take(p: ^int, n: int) int requires(n > 0) = {
	free(p); // ok: no unit::error, so false requires aborts cleanly
	return n;
}

export fn main() void = void;

Using `@expect` without `unit::error` in the return type (`L1002`)

When @expect times out it returns unit::expectation_failed, so the signature must include unit::error.

L1002: @expect needs unit::error in the function's result
lora Rejected 
fn ready() bool = true;

fn wait() void = {
	@expect(within = 100) { // error[L1002]: nowhere to return timeout
		assert(ready());
	}
}

export fn main() void = void;
lora Allowed 
use unit;

fn ready() bool = true;

fn wait() (void | unit::error) = { // ok: unit::error return type handles @expect timeout
	@expect(within = 100) {
		assert(ready());
	}
}

export fn main() void = wait()!;

Runtime Aborts

False `requires`, `ensures`, or `assert` without `unit::error`

Invokes rt::on_unit_failure and aborts under --units=enforce (default); logs and continues under --units=observe.

lora Aborts 
fn clamp_pct(x: int) int
	requires x >= 0 && x <= 100
= x;

export fn main() void = {
	let _ = clamp_pct(150); // runtime abort under --units=enforce: precondition failed
}
lora Allowed 
fn clamp_pct(x: int) int
	requires x >= 0 && x <= 100
= x;

export fn main() void = {
	assert(clamp_pct(85) == 85); // ok: argument satisfies requires(0..=100)
}

Status: phases 1 to 4 are built: requires, ensures, failures as values through unit::error, @expect, and reports that keep the values. Phase 5, optional test reports, is not built. The examples drive a small app of their own, a session whose screen changes as it loads, and each one runs as it is.

A unit function is any function that states what must hold before it runs and after. There is no marker for it: requires and ensures in a signature make a function a unit. They replace contracts: everything pre and post do today carries over, and units add what contracts cannot do. A unit's failure can be a value the caller handles, and a unit can wait for something that becomes true later.

lora 
use unit;

// a pure unit: a broken promise is a bug, as with contracts
fn divide(dividend: int, divisor: int) int
	requires(divisor != 0)
= dividend / divisor;

// a small app: its screen, and a detail that takes a few steps to load
type inventory_list = struct { count: int };
type inventory_detail = struct { product_id: str };
type loading = struct { product_id: str, left: int };
type screen = (inventory_list | loading | inventory_detail);
type session = struct { screen: screen };
type no_product = !struct { id: str } "no product {id}";

fn focus(s: *const session) screen = s.screen;

fn select_product(s: *session, id: str) (void | no_product) = {
	if (id != "1" && id != "2") return no_product { id = id };
	s.screen = loading { product_id = id, left = 3 };
};

// the app goes on: what it is loading appears after a few steps
fn step(s: *session) void = match (s.screen) {
	let l: loading => s.screen = if (l.left == 0) inventory_detail { product_id = l.product_id }
		else loading { product_id = l.product_id, left = l.left - 1 },
	inventory_list => void,
	inventory_detail => void,
};

// a unit over a running app: failure is a value, and it waits
fn open_inventory_detail(s: *session, id: str = "1")
		(inventory_detail | unit::error | no_product)
	requires(focus(s) is inventory_list, "on the inventory list")
= {
	select_product(s, id)?;
	return @expect(within = 2000) {
		step(s);
		let d = focus(s) as inventory_detail;
		assert(d.product_id == id);
		yield d;
	};
};

export fn main() void = {
	assert(divide(9, 3) == 3);
	let s = session { screen = inventory_list { count = 2 } };
	let d = open_inventory_detail(&s)!;
	assert(d.product_id == "1");
	// no longer on the list: the caller is told, and nothing is done
	match (open_inventory_detail(&s)) {
		let e: unit::precondition_failed => assert(e.message == "on the inventory list"),
		inventory_detail => abort("opened again"),
		unit::postcondition_failed => abort("broke a promise"),
		unit::expectation_failed => abort("waited"),
		no_product => abort("no product"),
	};
	let s = session { screen = inventory_list { count = 2 } };
	assert(open_inventory_detail(&s, "9") is no_product);
};

1. The idea

Contracts and the example step have one shape:

StageContracts todayThe exampleUnits
Beforepre(...)requires InventoryListrequires(...)
Dothe bodyact SelectProductthe body
Afterpost(...)expect InventoryDetailensures(...), or @expect

They differ in two ways, and those are what a unit adds:

Contracts todayWhat the example needs
A failure isa bug: the program stops, and ? never sees ita result: the app was on the wrong screen
The condition istrue now, or brokentrue soon: the app is still loading

So a unit is one mechanism with two additions, not a new system alongside contracts.

2. Syntax

text 
fn name(params) result
	requires(condition [, message])
	ensures([r =>] condition [, message])
= body;
  • requires replaces pre, and ensures replaces post, in the same place and with the same meaning. They are contextual, as pre and post are, so a field called requires stays valid.
  • There is no unit fn: any function may have them. Existing code changes by a rename, with no other edit.
  • They work where contracts work: lambdas, interface methods, impls, generics, and C wrappers.
  • pre and post are gone, and are ordinary names again.

Why clauses, and not requires and act statements in the body? They are where contracts already are, so one mechanism stays one mechanism. Callers and interfaces can see them in the signature and typedefs, which compile-time call checks depend on. And they need no act keyword, since doing something in Lora is just a call.

Why @expect, and not a keyword? It is a block with special rules, like @for and @if, and those live in the @ namespace. It adds no keyword, and expect stays free as a name.

3. Bug or result: the result type decides

The conflict between contracts and the example is settled by one rule, in the signature:

  • unit::error is not in the result type: a failure is a bug. It behaves exactly as a broken contract does today: a report, then the program stops, and ? never sees it.
  • unit::error is in the result type: a failure is a result. It is returned, and the caller handles it with ?, or or match.
lora 
use unit;

type account = struct { cents: i64 };

// a unit whose failures are results: unit::error is in its result type
fn withdraw(a: *account, cents: i64) (i64 | unit::error)
	requires(cents > 0, "the amount must be positive")
	requires(cents <= a.cents, "there is enough")
	ensures(r => r >= 0)
= {
	a.cents -= cents;
	return a.cents;
};

// the same promise, broken as a bug: no unit::error, so the program stops
fn checked_half(n: int) int
	requires(n % 2 == 0)
= n / 2;

export fn main() void = {
	let a = account { cents = 100 };
	assert(withdraw(&a, 40)! == 60);
	match (withdraw(&a, 500)) {
		let e: unit::precondition_failed => {
			assert(e.function == "withdraw");
			assert(e.message == "there is enough");
		},
		i64 => abort("withdrew too much"),
		unit::postcondition_failed => abort("broke a promise"),
		unit::expectation_failed => abort("waited"),
	};
	assert(a.cents == 60);                      // the body did not run
	assert((withdraw(&a, 0) or -1i64) == -1);   // a fallback, as for any error
	assert(checked_half(8) == 4);
};

The failures are λlib/unit.lora's:

lora 
type precondition_failed = !struct { function: str, predicate: str, message: str };
type postcondition_failed = !struct { function: str, predicate: str, message: str };
type expectation_failed = !struct { function: str, predicate: str, last: str, waited_ms: u64 };
type error = !(precondition_failed | postcondition_failed | expectation_failed);

Returning skips what a bug's report never needed, so two things become compile errors: a false ensures would lose an owner the function returned, and a false requires an owner passed to it.

A reader sees which it is from the signature, and the compiler checks it. An action's own failure needs no wrapper: select_product(s, id)? passes on its no_product, which is more precise than the action_failed in the example and already carries a trace. So a report still says where it broke:

It brokeThe failure is
The app was in the wrong placeunit::precondition_failed
The action failedthe action's own error
The result broke a promiseunit::postcondition_failed
The result never cameunit::expectation_failed

4. Waiting: @expect

lora 
use unit;

// a page that shows its product once it has loaded: until then, nothing
type page = struct { left: int, product_id: str };

fn shown(p: *page) (str | void) = {
	if (p.left > 0) {
		p.left -= 1;
		return void;
	};
	return p.product_id;
};

// waits, for at most ms, for the page to show id
fn wait_for(p: *page, id: str, ms: u64) (str | unit::error) = {
	return @expect(within = ms, every = 10) {
		let d = shown(p) as str;
		assert(d == id);
		yield d;
	};
};

export fn main() void = {
	let p = page { left = 3, product_id = "1" };
	assert(wait_for(&p, "1", 2000)! == "1");
	// the wrong product never becomes the right one: the time runs out
	let p = page { left = 0, product_id = "2" };
	match (wait_for(&p, "1", 50)) {
		let e: unit::expectation_failed => assert(e.waited_ms >= 50),
		str => abort("found it"),
		unit::precondition_failed => abort("required"),
		unit::postcondition_failed => abort("promised"),
	};
};

  • The block runs, and if it fails, runs again after every ms, until within ms have passed. within is required, so a wait is never hidden, and may be any expression: within = s.timeout. every defaults to 50.

  • A failure ends one attempt, not the program: a false assert, a failed as, or an error from ?, in the block itself. x!, a lambda's own assert and a requires broken in a call are still what they are anywhere.

  • Its value is what the block yields, so @expect gives the typed node.

  • After within, it fails with unit::expectation_failed, holding the last failure. For assert(a == b), it keeps both values, and for as and ?, what it found:

    text 
    error: open_inventory_detail: expected d.product_id == id, after 2000 ms:
  d.product_id is "2", id is "1"

  • It needs unit::error in the result type. Without one, a timeout would have nowhere to go, and that is a compile error.

  • Unlike conditions, the block may do I/O: it is ordinary code that runs again. Each attempt runs its defers and drops its owners.

  • break and continue can't leave it unless they name a loop around it, and a message in it is a plain str.

  • In a coroutine it waits with coro::sleep, so others keep running; otherwise it sleeps the thread.

All waiting is @expect. requires and ensures are checked once, and never wait. A precondition that may need time becomes the first @expect in the body:

lora 
use unit;

type inventory_detail = struct { product_id: str };
type cart = struct { items: int };
type loading = struct { left: int };
type screen = (loading | inventory_detail | cart);
type session = struct { screen: screen };

fn focus(s: *const session) screen = s.screen;

// the app goes on: what is loading appears after a few steps
fn step(s: *session) void = match (s.screen) {
	let l: loading => s.screen = if (l.left == 0) inventory_detail { product_id = "1" }
		else loading { left = l.left - 1 },
	inventory_detail => void,
	cart => void,
};

fn add(s: *session) void = {
	s.screen = cart { items = 1 };
};

fn add_to_cart(s: *session) (cart | unit::error) = {
	// a precondition that may take time: the first @expect in the body
	@expect(within = 500, every = 10) {
		step(s);
		assert(focus(s) is inventory_detail);
	};
	add(s);
	return @expect(within = 2000) {
		yield focus(s) as cart;
	};
};

export fn main() void = {
	let s = session { screen = loading { left = 2 } };
	assert(add_to_cart(&s)!.items == 1);
};

5. Typed states

The example wants typed nodes and chains the compiler can check. Lora's nominal types already give this, with no new feature:

lora 
use unit;

type inventory_list = struct { count: int };
type inventory_detail = struct { product_id: str };
type cart = struct { items: int };
type session = struct { opened: int };

fn open_detail(s: *session, from: inventory_list, id: str) (inventory_detail | unit::error) =
	inventory_detail { product_id = id };

fn add_to_cart(s: *session, from: inventory_detail) (cart | unit::error) =
	cart { items = 1 };

fn shop(s: *session, list: inventory_list) (cart | unit::error) = {
	let detail = open_detail(s, list, "1")?;
	let c = add_to_cart(s, detail)?;
	let wrong = add_to_cart(s, list)?; // error: Argument type inventory_list is not assignable
	return c;
};

export fn main() void = void;

A chain in the wrong order is an ordinary type error, and a typo in a node's name is an unknown type. No strings are involved. Taking the state as an owner, from: ^inventory_list, goes further: using a stale state is L0600, because it moved.

6. What carries over from contracts

Each of these stays as it is:

Contracts todayAs a unit
pre run on entry, post on every return after defersthe same
post(r => ...), skipped when an error is returnedensures, the same
Conditions only look: no assigning, allocating, or movingthe same; @expect is where effects go
Calls with constant arguments checked while compilingthe same, in every module
Contracts in @comptimethe same
Interface contracts hold for all impls; an impl may add ensures, not requiresthe same
Generics, lambdas, C wrappersthe same
assert in a bodythe same, except in @expect (above)

Names change:

TodayBecomes
pre, postrequires, ensures
--contracts=, LORA_CONTRACTS--units=, LORA_UNITS
rt::on_contract_violation, rt::contract_violationrt::on_unit_failure, rt::unit_failure
kind of PRE, POST, ASSERTREQUIRES, ENSURES, ASSERT, EXPECT

Build modes keep their meaning for failures that are bugs. enforce reports and stops, observe reports and carries on, and ignore does not check. Failures that are results ignore the mode, because they are how the function works: a caller is handling them. @expect always runs, as assert does in ignore builds, since its block has effects.

9. How to build it

Each phase is useful alone.

  1. Rename. requires and ensures in the parser, on the contract machinery (parse_contracts, check_contract, gen_posts, Ccomptime.c). Rename the modes and the handler. Move the 9 uses in the library and 25 in tests and docs. Grammar, language server, docs. Behaviour is unchanged.
  2. Results. λlib/unit.lora with the error types. When the result has unit::error, a failed condition returns instead of calling rt.contract_failed.
  3. @expect. Lowered to a labelled loop around rt::expect_next, with failures in the block noted and continuing it. Waits use coro::sleep in a coroutine, through rt::expect_sleep.
  4. Good reports. assert(a == b) in @expect keeps both values. The runtime's printer writes them to a buffer in the attempt's state, with no allocating, and a timeout copies the text to one of 32 fixed places: a failure stays a plain value, so unit::error costs its users no owner to drop.
  5. Test reports (optional). lora test listing each unit that ran, with its stage and time, as the example's reporter does.
