Getting Started

Toolchain & Editors

Complete reference for the lora driver, build modes, QBE backend, runtime diagnostics (LORA_LEAKS, LORA_UNITS, LORA_FAIL_ALLOC), language server (lora lsp), VS Code, and Zed.

The lora driver

cmd/lora is a POSIX shell script that orchestrates the four compilation steps (compiler → QBE → assembler → linker) and wires up the module typedef search paths. There is nothing magical about it; every step can be run by hand (see docs/runtime.md).

text 
usage:
  lora run [--leaks | --guard] [--units=<mode>] <file.lora> [args...]
  lora build [-o <output>] [--units=<mode>] <file.lora> [file.lora...]
  lora check <file.lora> [file.lora...]
  lora test [-run <pat>] [-j <n>] [--leaks | --guard] [--bench] [--fuzz] [--time <dur>] [--json] [file...]
  lora sql schema <url> [file]  write lora.schema, which @sql is checked against
  lora explain <code>        what a diagnostic such as L0003 means
  lora lsp                   the language server, on stdin and stdout (for editors)
  lora init [directory]
  lora version
  lora help

Testing, benchmarks, and fuzzing (lora test)

Functions marked @test, @bench, and @fuzz are discovered automatically by lora test (even in files without main(), for which the driver synthesizes a runner):

  • @test fn name(t: *testing::t) void or @test fn name() (void | E) — runs unit tests with -run <pat>, -j <n> parallelism, --leaks / --guard heap checking, and --json output.

  • @bench fn name(b: *testing::b) void — runs with --bench (--time <dur>).

  • @fuzz fn name(f: *testing::f) void — runs with --fuzz (--time <dur>).

  • The core library is built automatically on first use (incremental via make stdlib); set LORA_NO_BUILD=1 to skip that step.

  • All intermediates live under .build/; final binaries link against every core module object, and namespace-qualified symbols keep them collision-free.

  • The QBE target is chosen from uname -m: arm64_apple or amd64_apple.

Diagnostics

On a terminal, compiler errors and warnings are drawn in color: the file and position; a red ERROR or yellow WARNING badge with the kind of problem and its code; what happened, in a sentence; the line with the ones around it and the span underlined; why it matters, when that is not obvious; then the fixes, each on one line with the code to write; and a note pointing at lora explain <code>. A summary ends the output:

text 
main.lora:15:10
 WARNING   Dropped error · L0006
This `_ =>` arm drops or hides a strconv::invalid_number error.
14 │     let n: int => void,
15 │     _ => void,
   │     ~
16 │ };
  The program goes on (or stops) without knowing why strconv::parse_int failed.
  fix: Name the error and report it:  let e: strconv::invalid_number => fmt::eprintln($"{e}")!,
   or: Give a fallback value:  strconv::parse_int(...) or 0
   or: handle it where it happens with `or |e|`
  note: `lora explain L0006` says more

⚠ 1 warning  1 file · 58ms

Run-time failures are reported the same way: on a terminal, the place, a red ABORT badge with what went wrong, the message, the source lines with the place underlined, the trace and fix: lines. When stderr is not a terminal (an editor, a pipe, CI), the output is plain: path:line:col: error[L0001]: message from the compiler, followed by = why: lines and = help: label<TAB>code lines, which tools parse, and path:line:col: abort: message from a program, followed by the line with a ^ under the place. A failed program exits with status 134. NO_COLOR=1 turns colors off; LORA_COLOR=1 (compiler) and LORA_COLOR=1 (programs) force them on.

Installing on PATH

The driver lives at cmd/lora inside the project, so lora is not a command until you install it:

sh 
scripts/install-driver.sh     # symlinks into /opt/homebrew/bin (or /usr/local/bin)

The driver resolves symlinks to find the project root, so the symlink can live anywhere on PATH. Remove it any time with rm /opt/homebrew/bin/lora.

Build targets

At the project root:

  • make / make all — build the compiler (if needed) and the core library
  • make stdlib — just rt + the modules in lib/
  • make check — stdlib + ./cmd/lora test
  • make clean — remove .build/

In compiler/:

  • make — build the compiler binary to compiler/.bin/lorac
  • make check — run the compiler test suite (compiler/tests/*.lora, 40 suites covering literals through the match patterns)

Compiler pipeline

text 
file.lora ──compiler/.bin/<platform>-<arch>/lorac──▶ .ssa (QBE IL)
        ──qbe-darwin (macOS) / qbe (Linux)──▶ .s
        ──darwin-as (macOS) / as (Linux)──▶ .o ──cc──▶ executable (+ .build/*.o core modules)

Every build output goes under a directory for its platform and architecture (compiler/.bin/darwin-aarch64/, .build/linux-x86_64/, and so on), so one checkout serves macOS and Linux machines, on arm64 and x86_64, at once. make -C compiler needs no setup: compiler/configs/default.mk finds the platform and architecture.

  • QBE is vendored in qbe/ (see qbe/VERSION for the upstream commit and Lora's changes) and built by make -C compiler as compiler/.bin/qbe, so Lora needs no system QBE. Its own tests run with make -C qbe check.
  • compiler/scripts/qbe-darwin runs that QBE (target arm64_apple/amd64_apple) and post-processes its output: QBE emits GNU-as style quoted .section directives, which the Mach-O assembler rejects, so they are rewritten to Mach-O sections; Mach-O thread-local variable (TLV) descriptors are synthesized for TLS data.
  • compiler/scripts/darwin-as concatenates its input assembly files and assembles them with cc -c (the Apple toolchain assembler).
  • On Linux QBE targets arm64 or amd64_sysv and its output goes to as as it is. The compiler puts each function and datum in a section of its own (.text.<name>, .data.<name>), and programs are linked with --gc-sections, so the linker keeps only what the program reaches, as on macOS; the runtime's linker script (runtime/+linux/lora.ld) keeps the @init, @fini and @test arrays. Hello world is about 320 KB on x86_64 and 370 KB on arm64 instead of 9.7 MB.
  • On macOS programs are linked with -dead_strip: qbe-darwin ends each file with .subsections_via_symbols, making every function and datum an atom of its own, so the linker keeps only what the program reaches, though every core module is linked. Hello world is about 240 KB. The @init, @fini and @test arrays, reached only through their section bounds, are marked no_dead_strip.

Stack overflow check

Stacks have a fixed size and a 16 KiB guard page below them, so a program that uses too much stack stops, saying which stack (main, a thread's or a coroutine's) ran out; frames larger than a page are entered a page at a time, so none steps over the guard. The compiler estimates each function's stack use when it checks a program. It reports code that would overflow as a compile error, which also shows in the editor as you type.

Entry pointStack
main, @init, @fini8 MiB, whatever ulimit -s says
@all, @first, @scope children, coro::detach256 KiB
coro::detach_sized(n, ...)n rounded up to 16 KiB
thread::spawn, coro::blocking512 KiB
  • Error: the deepest call chain from an entry point needs more stack than the entry point gets. The message names the chain, for example a lambda (1 KiB) -> handle (1 KiB) -> parse (301 KiB), and says what to do (use a larger detach_sized, or move large arrays to the heap with alloc).
  • Warning: an entry point (main, @init, @fini, a coroutine or a thread) calls a recursive function, so its stack use has no bound. @depth bounds a recursion; the warning names the recursive function and the chain to it.
  • Warning: a function with @depth changes its depth parameter or takes its address, so @depth no longer bounds its recursion.

main's 8 MiB holds on every machine: lora build links macOS programs with an 8 MiB main stack, and on Linux the runtime raises the soft stack limit to 8 MiB more than the stack holds at start (the program's arguments and environment), as far as the hard limit allows. Programs the program starts inherit the raised limit.

A function's frame is estimated from its parameters, local bindings and aggregate temporaries, plus a fixed amount for saved registers. What may share space is counted once (the arms of a match, the branches of an if); what may not is counted in full: copies of large arguments, one for each argument position, and the slot of a large result of a call in a branch within a match arm, one for each arm. scripts/test-stack-frames.py checks every library function's estimate against the frame it gets. Constants (def) and static bindings take no stack. Calls through function pointers or closures, and calls into C or into the runtime (alloc, append, free and so on), count as 16 KiB. The estimate errs on the high side, so it may report code that would only just fit.

Typedefs record each exported function's estimate as @stack(bytes), so the check also follows calls into other modules. They record its effects as @effects(keeps, returns, frees, into...) too: bit i of each says what the function does with its i-th parameter, so that calls into other modules are checked for dangling pointers and use after free.

Leak checks

Two checks find memory that is never freed (see "Finding leaks" in language.md):

  • Compile time. Ccompiler/src/leak.c follows each local holding new memory along every path out of its scope and warns where it is certainly unfreed: a return (a failed ? included), a break or continue leaving its loop, the end of its block, or an overwrite. These are warnings, shown in the editor with a quick fix adding defer free(x);.
  • Run time. lora run --leaks file.lora, or LORA_LEAKS=1 with any built program, reports at exit every allocation not freed, grouped by where they were made and the functions that were running, and exits with status 23. LORA_LEAKS=report keeps the exit status. lora run --guard (LORA_LEAKS=guard) also stops at the first read or write of freed memory, and at any access past a block's end, saying where the block was allocated and freed: each block has pages of its own, so it is slow, for when a test or unsafe code is suspect.

scripts/test-leaks.py tests both, and that the test programs which free their memory pass the run-time check.

Debugging

Most Lora bugs are found before the program runs, and the rest say where and why when they happen. In order of how often each helps:

1. Before it runs: let the compiler find it

  • In the editor (VS Code or Zed), diagnostics appear as you type; hover one for why it happened and the fixes. In a terminal, lora check file.lora checks without building, and lora explain L0104 explains a code.
  • Unhandled errors, leaks (L0100), use after free (L0102), dangling pointers (L0104), data races (L0700), constant overflow and values outside a pattern type are compile errors or warnings, not run-time surprises.

2. When it fails: read what it prints

A failing program stops with where it failed and the values involved:

text 
app.lora:12:9
 ABORT   Out of bounds
index 5 is out of bounds for length 3
11 │     let i = 5;
12 │     let v = xs[i];
   │             ~~
13 │ };

  fix: check the index is less than len(...) first

The same goes for slices, integer overflow (250 + 10 is 260, which is out of range for u8 (0 to 255)), division by zero, a string slice cutting a character, a null raw pointer, stack overflow and a value no match arm covers.

An error that reaches main, or fails an x!, is printed with the notes added on its way up and where it came from:

text 
error: cannot open /etc/app.toml: No such file or directory (ENOENT, errno 2)
  which happened while loading the settings
  trace:
    fs::read_file  lib/fs.lora:20:27  error made here
    load           app.lora:5:33
    main           app.lora:13:13

The note comes from ? with a message. Add one where the caller's context matters: it is the cheapest debugging there is.

lora 
use fs;

fn load(path: str) (void | fs::error | nomem) = {
	let data = fs::read_file(path) ? "loading the settings";
}

export fn main() void = assert(load("/nonexistent/app.toml") is fs::error);

3. Make assumptions checkable

assert(cond, "why") inside a function, and requires(...) and ensures(...) on its API, turn a wrong assumption into a report naming the condition, at the place it first goes wrong rather than where the damage shows. lora run --units=observe app.lora reports every false condition and keeps running, to see them all in one run (see the language reference, "Unit functions").

4. Memory

lora run --leaks app.lora, or LORA_LEAKS=1 ./app for a built program, lists the memory never freed, with where each allocation was made and the calls that led there; it exits with status 23 when there are leaks. The same mode reports writes to freed memory (see Leak checks).

5. Print what you need to see

{:?} formats any value for debugging, fields included; $"..." interpolates:

lora 
type point = struct { x: int, y: int }

export fn main() void = {
	let s = point { x = 1, y = 2 }
	let n = 3, xs = [1, 2];
	fmt::eprintfn("state: {:?}", s)!;           // state: point { x = 1, y = 2 }
	fmt::eprintln($"n = {n}, len = {len(xs)}")!; // n = 3, len = 2
}

For messages worth keeping, log::debug(...) is skipped unless log::set_level(log::level::DEBUG) turns it on, so they can stay in the code. Once a bug is understood, a program under tests/ that asserts on the result keeps it fixed (lora test).

6. Look at what the compiler made

Every lora build and lora run keeps what it compiled the program to, replaced by the next build:

sh 
lora build app.lora
less .build/app/program.ssa    # QBE's intermediate code
less .build/app/program.s      # the assembly

Functions are symbols named after their module: _main, _fmt.println, and _.half for a program's private half. Reading the code Lora generates walks through both files for hello world, line by line. The core library's are in .build/<module>.ssa and .s. To run the steps by hand, see Compiler pipeline; cmd/lora shows the exact commands and the LORA_TD_<module> variables they need.

7. Native debuggers

lldb ./app works at the level of symbols and instructions: b main, b fmt.println, stepping, registers and memory. Limit: it cannot show source lines or Lora variables yet. The compiler emits line tables, but no DWARF compile-unit or function entries, so the linker writes no debug map (dsymutil reports no debug symbols) and backtraces show symbols, not file:line. The error traces and abort messages above carry file:line instead.

If lldb fails to start with a missing Python.framework, reinstall the Xcode Command Line Tools (xcode-select --install).

A workflow

  1. Read the diagnostic, or the abort message and its values.
  2. Add a note at the ? above the failure, or an assert where the assumption breaks, and run again.
  3. Write the failing case as a test under tests/.
  4. Fix it, and run lora test and lora run --leaks.

Module typedef environment

The compiler resolves imported modules through environment variables of the form LORA_TD_<module> pointing at a .td typedef file. The root Makefile builds one per core module into .build/ and the driver exports all of them:

sh 
LORA_TD_rt=.build/rt.td
LORA_TD_strings=.build/strings.td
...

Adding a core module

  1. Create λlib/mymod.lora with exported declarations.
  2. Add mymod to MODULES in both the root Makefile and cmd/lora.
  3. Add its dependency rules: $(BUILD)/mymod.ssa: $(BUILD)/<deps>.td in the Makefile.
  4. Rebuild: make stdlib.

Editor support

A full-featured VS Code extension ships in editors/vscode-lora: syntax highlighting, a dependency-free language server (JSserver/lora-lsp.js), run/build/check commands, and the Lora Vesper color theme. The server gives:

  • diagnostics from the compiler as you type;
  • types from the compiler too: each check writes an index of what the checker inferred (LORA_IDE_INDEX, Ccompiler/src/ide.c): every binding and name with its type, and each type's fields, methods and parts. The server keeps the last one of a file that parsed, so x. completes what the checker says x is (an inferred let, a for-each element, an unpacked tuple, a generic instance, a type parameter through its constraint) while the line being written does not parse, and works it out from the text where the checker has not yet seen it;
  • completion, hover, signature help and inlay hints with those types;
  • go to definition, type definition and implementation (an interface to its impls), the call hierarchy, references, rename and highlights;
  • document and workspace symbols, folding, selection ranges, links from use, semantic tokens, formatting (on save), quick fixes and organize imports.

Install with:

sh 
scripts/install-vscode.sh

which packages the extension as a .vsix and installs it through code --install-extension (registered as λlora-lang.lora in code --list-extensions), then prints the reload hint. The language server speaks plain LSP over stdio and can be used from other editors directly. See editors/vscode-lora/README.md for details.

Zed has an extension too, in editors/zed-lora: highlighting from a tree-sitter grammar (editors/tree-sitter-lora), the same language server (started as lora lsp), and the Lora Vesper themes, including frosted glass variants that use Zed's window blur. Install with scripts/install-zed.sh, then Zed's zed: install dev extension; see editors/zed-lora/README.md. Any editor that speaks LSP can run lora lsp the same way.

After changing the grammar, check it still parses every Lora file:

sh 
cd editors/tree-sitter-lora && tree-sitter generate
python3 scripts/test-tree-sitter.py

Regenerate the intellisense data after changing the core library or runtime signatures:

sh 
python3 scripts/gen-lsp-data.py
python3 scripts/test-lsp.py         # exercises the server over stdio
python3 scripts/test-lsp-types.py   # completion with the compiler's types, as an editor meets it

Tests

Six layers:

  1. Compiler tests — compiler/tests/*.lora, run with make -C compiler check. Test the checker, parser and codegen directly, including λtests/14-match.lora (language semantics) and λtests/39-patterns.lora (structural patterns: tuples, structs, arrays, enums, strings, ranges, refs, @ bindings, guards).
  2. End-to-end tests — tests/*.lora, run with ./cmd/lora test. Compile and execute real programs against the core library (λcore.lora, λpatterns.lora, λnet.lora).
  3. Leak checks — scripts/test-leaks.py (see "Leak checks").
  4. Documentation — scripts/check-doc-examples.py compiles and runs every example in docs/language.md, errors.md, idioms.md, tooling.md, reading-generated-code.md, sql.md and encodings.md, and checks each marked error, warning and abort.
  5. Examples — scripts/check-examples.py runs every examples/*.lora with leak checks; the servers (echo, coro_echo, http_server), which wait for connections, are only compiled.
  6. C interop — tests/interop/run.sh compiles a Lora unit to a bare object and links it into C and C++ (extern "C") hosts: scalars, floats, aggregates > 16 bytes by value, strings via pointer-out, allocation and bounds-checked functions (linked against runtime objects built without λstart.lora), and the runtime abort path under a C host. Composites ≤ 16 bytes by value are the one gap — QBE returns them via a hidden sret pointer instead of AAPCS x0:x1 registers (see the shortcut note in λtests/interop/interop.lora).
